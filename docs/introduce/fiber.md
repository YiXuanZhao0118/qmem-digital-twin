# Fiber — optical fibre (single object + per-instance spline)

> Related: [optics.md](optics.md) (how the coupling physics enters the trace), [anchors.md](anchors.md) (the endpoint anchors are derived from the spline), [kinds.md](kinds.md) (fiber / fiber_coupler), [cable.md](cable.md) (RF cables use the same spline/endpoint architecture).
> Code: `optical/fiber/`, `three/loadAsset/fiber/`, `utils/fiber{Alignment,BodyEndpointResolver,AnchorResolver}.ts`, backend `optical/anchor_ops/fiber.py`.

## Data model (single-object model, post-0056)

One fibre = **one SceneObject** (one row in the Outliner). The poses of both ends A/B are embedded in `PE.kindParams.endA` / `endB` (body-local):

- `posMm` — **the back of the connector (the junction between wire and ferrule) = the spline endpoint = the mesh origin**.
- `tensionHandleMm` — the **single source of truth** for the outward direction and the Bezier tangent (it also sets the ferrule's orientation).
- `rotDeg` — **only the ferrule's visual roll**; it does not rotate the wire tangent.
- Plus the per-end physics fields: `numericalAperture`, `modeFieldDiameterUm`, `coreDiameterUm`, `connectorType` (FC/SC/…), `polish` (PC/APC/UPC), …

> **The optical tip ≠ posMm**: `tip = posMm + outward · FIBER_FERRULE_TIP_MM`, with `outward = -unit(tensionHandleMm)` and `FIBER_FERRULE_TIP_MM = 36.28 mm` (the housing length of the Thorlabs FC 30126A9). All anchor positions and directions are derived from the spline by `resolveAnchorPosition()` / `resolveAnchorDirection()` in `fiberAnchorResolver.ts` (those anchors are marked `derivedFromFiberEndpoint`).

**Migration history**: `0052` split one fibre into three SceneObjects (`fiber_end_a` / body / `fiber_end_b`) → `0056` **collapsed it back to a single object**, baking the endpoint poses into kindParams and deleting the fiber_end objects. Moving or rotating the fibre now carries both ends with it.

## Rendering (`three/loadAsset/fiber/`)

`createFiberSplineObject()` (`spline.ts`) builds a Group:
- **The tube**: `buildFiberCurvePath()` (`curve.ts`) assembles CubicBeziers from `FiberNode[]` (each with `handleInMm` / `handleOutMm`) → a `TubeGeometry` (radius `radiusMm`). The jacket colour follows fiberType (SM yellow, PM blue, MM orange).
- **The two FC connectors**: a cached STL from `thorlabs_30126a9_fc_connector.ts`, with `applyFiberFerruleOrientation()` mating the connector's +Y to outward.
- **Endpoint locking**: capability profile `fiber: { endpointSplineNodesLocked: true }` — the spline endpoints (node 0 / N−1) can only be moved with the **Align End A / B** buttons, while intermediate nodes drag freely.
- `refreshFiberWrapperGeometry()` swaps the tube in place when nodes or radius change, instead of rebuilding the whole wrapper.
- **Jacket radius belongs to the Component layer** (2026-08-14): it is adjusted only in the COMPONENT editor's `CableAppearanceEditor` (`Component.properties.cableAppearance.radiusMm`, `ComponentsEditor.tsx:1224`); the Object panel's `FiberEditor` no longer has a per-instance "Jacket radius" slider (nor `sceneStore.updateFiberRadius`). Reading still falls through `cableAppearance.radiusMm` → `SceneObject.properties.radiusMm` (legacy leftover data) → `Component.properties.radiusMm` → 1.0 (`spline.ts:167`).

## Alignment (`utils/fiberAlignment.ts`)

`computeFiberEndAlignment()` / `findFiberEndAlignmentCandidates()`: project the ferrule's current **tip** onto each beam segment, keep the candidates within `toleranceMm` (25 mm), and back out the new spline node (End A entering with `outward=-beam_tangent`, End B exiting with `outward=+beam_tangent`, `node = tip - outward·36.28`), with the Bezier handle aligned to the beam direction. The other end and the body pose stay put. The projection math is a pure function shared by Align A/B and the per-end port editor.

**The lab RENDERER goes through the same precedence since 2026-08-21** — `bindingRendererGate` rebuilds the spline from the fibre PE when neither `SceneObject.properties.fiberNodes` nor `Component.properties.fiberNodes` holds ≥2 nodes. Before that it passed `SceneObject.properties` straight to `createFiberSplineObject`, whose own fallback is a hard-coded 0→300 mm run — so an un-edited cable was drawn at the origin rather than at its endpoints (see [known-issues.md](known-issues.md)). It calls `utils/fiberAnchorResolver` directly rather than the store, to keep `three/` from importing `store/` (`sceneStore` → `three/photoRoom` would close the cycle).

**The single entry point for reading endpoints is `sceneStore.resolveEffectiveFiberNodes(obj, component, physicsElements)`**: it prefers `SceneObject.properties.fiberNodes` (≥2) → `Component.properties.fiberNodes` (≥2) → otherwise rebuilds them from the fiber PE's `kindParams.endA/endB` via `syncFiberNodesFromKindParams()`. **This step is what makes a connector-component fibre alignable at all** — freshly instantiated it has only `kindParams.endA/endB` and no cached `fiberNodes` (the backend's `default_kind_params_for_component` seeds only kindParams), so the old code, which read `properties.fiberNodes` directly, hit its `length<2` early return and Align did "absolutely nothing". `findFiberAlignmentCandidates`, `applyFiberAlignmentCandidate`, `setFiberPortLabPose`, `FiberPortPoseEditor` and FiberEditor's node count all go through this resolver.

**Writes must be double writes**: endpoint edits (applying an Align, or editing the port pose) must, besides writing `properties.fiberNodes`, also sync the endpoint into `kindParams.endA/endB` (`posMm` = junction, `tensionHandleMm` = handle) — done by the shared helper `sceneStore.syncFiberEndpointToKindParams()`. Writing only `fiberNodes` is a dead end: on load, `syncFiberNodesFromKindParams()` overwrites the endpoints from kindParams and the edit springs back.

## Plugging a patch cable into an instrument — the endpoint link (2026-08-21)

Until this landed, "connect a fibre to a device" had no representation at all. The only alignment a fibre end had was `computeFiberEndAlignment` above, which projects the ferrule tip onto a **beam segment** — it pins the end to wherever the light happened to be at that moment, not to the part. Move the instrument and the fibre stays behind; the coupling silently becomes a coincidence of geometry. **A `fiber_connector` sub-component under the instrument does not help**: `_connector_tip_and_aperture` reads the connector bound to the *fibre*, and `connect_in/out` are not in `PRIMARY_ANCHOR_IDS`, so a connector hanging off a device is geometry the physics never looks at.

The fix is the optical twin of [cable.md](cable.md)'s `rfCableEndpoints`, and it copies that design deliberately:

- **The fibre vocabulary, in one table (alembic `0133` + `0135`, 2026-08-23).** Read every name from the FIBRE's point of view, never the light's — both ends of a patch cable use the same connector asset, so one end's `fiber_out` emits and the other's receives; direction is carried by each anchor's axisX.

  | anchor | where the fibre is | lives on | gender | in `PRIMARY_ANCHOR_IDS`? |
  |---|---|---|---|---|
  | `fiber_in` | goes INTO an instrument | device asset (chassis socket) | female | **yes** — the only fibre id in the set |
  | `fiber_out` | comes OUT of its connector | `fiber_connector` asset (mating face) | male | no — passthrough |
  | `fiber_root` | anchored into the cable | `fiber_connector` asset (spline junction) | — | no — passthrough |

  Coax deliberately kept `connect_in` / `connect_out` for the last two: a `fiber_*` id would be a lie on an SMA, and forking the shared code (`connectorBake`, `bindingTreeObject`, the viewer's connector resolvers) was judged worse than one lookup that takes both spellings — `utils/connectorAnchors.ts` on the frontend, `db_scene_loader._find_anchor` on the backend. Both are covered by `test_both_spellings_of_the_mating_face_give_the_same_port`.

  **Why only `fiber_in` is primary**: the connector is passthrough, and a patch cable's traced coupling happens on the SYNTHESIZED `intercept_in/out` that `_synth_fiber_slot` derives FROM the mating face. Making `fiber_out` hit-testable too would put two anchors at the same point in space with undefined hit order. (0133 briefly had `fiber_out` as a second chassis bulkhead; it never got a user and 0135 took the id for the connector face instead.)

- **A bulkhead has its own anchor — `fiber_in` (alembic `0133`, 2026-08-23).** It used to be an `intercept_in` that happened to carry `connectorType: "fc_pc"`, which conflated two different things: an **intercept** is an optical FACE you can fly a free-space beam onto (that is exactly what `alignVariant: "translate_anchor_to_beam"` does with it), while a **bulkhead** is a CONNECTION — a female socket a male ferrule mates into, that light only ever reaches down a patch cable. Coax never overloaded an optical face and always had `rf_in` / `rf_out`; fibre now matches. It is in `anchor_tracer.PRIMARY_ANCHOR_IDS` (`backend/app/optical/anchor_tracer.py:152`) because the ~10 µm mating-gap segment has to terminate on something hit-testable, and ops dispatch **per kind, not per anchor id**, so `fiber_in` on a detector lands in `_terminal_sink_op` with no new wiring. Invariant, pinned by `test_a_fiber_in_bulkhead_is_hit_by_the_tracer_and_absorbs` (`backend/tests/optical/test_fiber_port_mating_gap.py`): drop `fiber_in` from `PRIMARY_ANCHOR_IDS` and the tracer silently skips the port while every pure-geometry test keeps passing.
- **The connector type is GENDERED, and only `*_female` is a port.** `fc_pc_female` / `fc_apc_female` is a bulkhead on a chassis; `fc_pc_male` / `fc_apc_male` is the plug terminating a cable or a pigtail. `isFiberPortConnectorType` (`utils/fiberAlignment.ts:138`) matches `/^(fc|sc|lc|st)_.*_female$/`, and `isFiberReceptacleAnchor` treats **`fiber_in` and only `fiber_in`** as a socket by id — a `fiber_*` prefix test there would hand back every cable end as a port, since `fiber_out` / `fiber_root` are the male plug; `Anchor.connector_type`'s Literal in `backend/app/schemas.py:239` is the vocabulary. **Why the gender matters and is not decoration:** `collectFiberPortsLab` (`store/sceneStore.ts:382`) filters candidate ports on that predicate **alone** and never looks at the anchor id, so a gender-blind test would advertise every patch-cable end as a socket and let two cables be plugged into each other. A free-space face (a mirror, a lens) leaves `connectorType` null and is therefore never offered as a port.
- **The link record**: `SceneObject.properties.fiberEndpoints[A|B]` = `FiberEndpointLink { targetObjectId, targetAnchorId, targetAnchorName }`.
- **Two surfaces, one mechanism.** From the CABLE: `findFiberPortAlignmentCandidates` merges into the SAME list `findFiberAlignmentCandidates` already returns, so the FiberEditor's Align End A/B button gained port targets without a second UI. From the INSTRUMENT: `FiberPortsEditor` (`components/ComponentPanel.tsx`) puts a **Fibre ports** section in the Object panel listing each receptacle with what is plugged into it and a Plug in… / Unplug pair — because "what is connected to this box?" is the question the user has when they click the receiver, and answering it by making them find and select the cable is backwards. It runs `findFiberEndsForPort`, which calls the same helper against the one port, so a cable connected from either surface lands in byte-identical geometry. The section is **self-gating on the receptacle, not on a kind list**: it renders only when the object's binding tree exposes an optical anchor with a female fibre `connectorType`. "Who is plugged in here" is a reverse lookup (`fiberPluggedIntoPort`) because the link record lives on the cable — a cable has two ends and one identity, a port has many possible cables, and the cable is what moves.
- **A fibre-fed part loses its Align button.** `canAlignToBeam` (`components/ComponentPanel.tsx:2303`) returns false when EVERY optical face a part exposes is a receptacle, tested per-anchor by `isFiberReceptacleAnchor` (`utils/fiberAlignment.ts`) over `OPTICAL_PORT_ANCHOR_IDS` = `intercept_in/out` + `fiber_in/out`. **Both spellings must be in that id list** — this regressed once (2026-08-23, caught before shipping): once the RXM15EF's bulkhead became `fiber_in`, a scan for `intercept_*` alone came back EMPTY, failed the `length > 0` test, and handed the meaningless button straight back. A `fiber_*` anchor is a receptacle by construction and needs no `connectorType` test; pinned by the `isFiberReceptacleAnchor` cases in `utils/__tests__/fiberPortAlignment.test.ts`. `detector` is in `OPTICAL_ALIGN_KINDS`, so the RXM15EF used to offer "Align" — translating the whole box onto a free-space beam line, which is meaningless for something light reaches down a patch cable, and actively misleading next to a port that is the real connection. A part with both a bulkhead and a bare face keeps Align for the bare one. Port entries are prefixed 🔌; only a port candidate carries `port`, which is what makes `applyFiberAlignmentCandidate` persist a link. A **beam** candidate deliberately CLEARS the link — parking a face on a beam is a free-space placement, not a connection — and so does a hand-drag of the endpoint (`updateFiberNodes(…, clearEndpointLink)`), the same manual-override-beats-link rule the cable follows. `clearFiberEndpointLink` unplugs in place; note it does **not** delete the cable the way `clearRfCableEndpointLink` does, because a patch cable dangling off a bulkhead is a real bench state and a one-ended coax was judged never to be.
- **Following the instrument**: `resolveLinkedFiberEndpoint` (`utils/fiberAnchorResolver.ts`) re-derives the node from the target's live lab pose, and `sceneStore.resnapFibersLinkedTo` persists it on every committed pose change (single, group, and the ASSET3D anchor editor, which moves the port itself).

**Two places where fibre is NOT a copy of coax, and both bite if you assume otherwise:**

1. **The write-through is load-bearing, not cosmetic.** RF propagation is a BFS over the link records, so a stale `rfCableNodes` is only a first-paint artefact. The optical solver never sees the link: `_synth_fiber_slot` reads `PE.kindParams.endA/endB`. A link that skipped the double write would look plugged in and trace unplugged. That is why `applyFiberAlignmentCandidate` still calls `syncFiberEndpointToKindParams`, and why `resnapFibersLinkedTo` routes through it rather than writing nodes directly.
2. **Mating is NOT anti-parallel.** An RF port's `direction` is a mechanical outward normal, so a plug always faces into it. An optical anchor's axisX is the **propagation direction** ([anchors.md](anchors.md)), so the face orientation follows the same rule the beam path uses: **End A (an entry) faces −axisX, End B (an exit) faces +axisX**, regardless of the port's id. Plugging End B into a detector's `intercept_in` therefore points the cable the way the light travels; plugging End A into a source's `intercept_out` points it back at the source. Copying the RF anti-parallel rule points the cable away from the part — it was written that way first and the sign is pinned by `utils/__tests__/fiberPortAlignment.test.ts`.

**The mating gap — do not "simplify" it away.** The optical face lands `FIBER_MATING_GAP_MM = 0.01` **short** of the port plane, so `node = port − outward·(tip + gap)`. Mate the faces exactly and `nearest_anchor_hit` drops the hit: it rejects `t < t_min` (1e-9), and a ray emitted from the exit anchor's own position reaches the receiving plane at t = 0. The symptom is a fibre-fed detector reading nothing, with no error anywhere. 10 µm is ~10⁷ × `t_min` (far above the ~1e-12 mm float noise of the body↔lab round trip) and optically nothing — an OM1 core at NA 0.275 widens ~2.8 µm across it. Pinned from the backend side by `backend/tests/optical/test_fiber_port_mating_gap.py`, including the wrong-sign case.

**`tipMm` must come from the bound connector asset**, not the 36.28 mm constant: `fiberConnectorTipMmFromAnchors` reads `|connect_in − connect_out|`, the same derivation `_connector_tip_and_aperture` uses, so the face the frontend mates is the face the solver couples through. **Resolving *which* binding is that end must match `_synth_fiber_slot._connector_asset` exactly, and that accepts two different keys**: `properties.splineEnd === "A"|"B"` OR `role === "end_a"|"end_b"`. The catalog is genuinely inconsistent — `Fiber SM PC` uses the roles, `Fiber PM PC-APC` binds `pm_780_pc` / `pm_780_apc` and carries `splineEnd` in the binding properties. Matching only on `role` silently falls back to 36.28 mm where the real tips are 59.5 / 59.3 mm: a ~23 mm gap between where the UI mates the face and where the solver couples, i.e. a cable that looks plugged in and reads nothing. This is the identical trap the RF side hit with its hard-coded family constants (~10 mm SMA / ~16 mm BNC overshoot) — see [cable.md](cable.md).

**Verified end to end on the live scene (2026-08-21)**, which is worth recording because every piece above can be individually right and still not couple. A patch cable's End A parked on the 492.19 mW TA output beam and End B plugged into the RXM15EF's port produced, on both the backend `run-from-db` trace and the frontend `__rayTraceDebug`: the beam's 1000 mm escape tail replaced by a `fiber` segment terminating at End A's face; and one `detector` segment **0.00999553 mm long** — the mating gap, and the shortest segment in the scene — delivering **459.29 mW**, with nothing continuing past it. η = 0.93315 against the two-surface Fresnel prediction (1−R)² = 0.93352 for n = 1.4506, the remainder being the 0.3 m of attenuation and the Marcuse overlap. **The follow-the-instrument path is verified the same way**: the receiver was then dragged 183 mm down the table and the cable came with it — still lit at 459.203 mW across a 0.010000 mm gap at the port's new position, with `resnapFibersLinkedTo` idempotent (re-running it moves nothing).

**Not done yet**: the fibre does **not** follow live *during* a drag the way an rf_cable does (the viewer has no fibre equivalent of `DigitalTwinViewer`'s `applyLink` pass); it re-snaps when the move commits, so a dragged instrument pulls its cable along in one step on release. There is also no connector **compatibility** check — an APC fibre will happily mate a PC bulkhead, and the fibre end's own `connectorType`/`polish` (`kindParams.endX`) are not compared against the port's. Both are additive.

## Optical physics (backend `anchor_ops/fiber.py`)

Two anchors: `intercept_in` (A) / `intercept_out` (B). Closed-form v1 coupling, with no internal ray tracing. The coupling efficiency is `η = η_mode · η_Fresnel · η_α`:
- `η_mode` — the Marcuse Gaussian overlap: `exp(-r²/w₀²)·exp(-θ²/θ_NA²)`, with `w₀ = MFD/2`, `θ_NA = asin(NA)`, and r/θ taken from the hit's transverse offset and tilt.
- `η_Fresnel` — the two air-glass surfaces: `(1-R)²`, `R=((n-1)/(n+1))²`.
- `η_α` — Beer-Lambert: `10^(-α·L/10)`, with `α=attenuationDbPerKm` and `L=lengthM`.

The outgoing ray: origin = the exit anchor's position, direction = the exit anchor's axisX (**the fibre forces the fundamental mode and erases the incoming tilt**), q reset to purely imaginary (the exit face is the waist), power ×= η.

### The intercept slot of a connector-component fibre is *synthesized* by the backend (2026-06-13)

`fiber_anchor_op` only fires when a ray hits an anchor whose id is `intercept_in` / `intercept_out`. But the new connector-component fibre binds two `fiber_connector` assets (whose anchors are `connect_in` / `connect_out`, whose op is passthrough, and whose `connect_*` are not in `anchor_tracer.PRIMARY_ANCHOR_IDS`) — so there is **no** `fiber`-kind slot with `intercept_in/out` anywhere in the scene, and the beam sails straight through without coupling.

The fix lives in the backend loader: for every object with `comp.kind_id=="fiber"`, `db_scene_loader.load_anchor_scene_from_db` **synthesizes a `fiber`-kind slot** (`_synth_fiber_slot`) from that fibre's PhysicsElement `kindParams.endA/endB`:
- `intercept_in` ← endA, `intercept_out` ← endB; `position = posMm + outward·tip_mm`, `outward = −unit(tensionHandleMm)`. `posMm` (the junction) and outward come from the **per-instance truth Align wrote into kindParams** (where the connector actually sits — the loader does not read the static Asset3D anchor).
- **Both the optical-face offset `tip_mm` and the hit aperture come from the `connect_in` anchor of that end's bound connector asset** (`_connector_tip_and_aperture`): `tip_mm = |connect_in − connect_out|`, `aperture = connect_in.apertureMm`. **That is, the synthesized `intercept_in/out` land exactly on the `connect_in` you defined on the asset (= the fibre's collection face = the beam waist)** — editing the asset's connect_in position/aperture moves the optical face and the acceptance window together. With no connector it falls back to 36.28 / `endX.apertureDiameterMm`. The aperture only decides whether something counts as a hit; η is still set by the Marcuse overlap.
- `default_params` are mapped from kindParams into the keys the op reads: `coreMfdUm←modeFieldDiameterUm`, `numericalAperture`, `coreRefractiveIndex←glassIndexAtDesignLambda`, `attenuationDbPerKm←attenuationCurve[0].dbPerKm`, `lengthM←` the spline length.
- The two `fiber_connector` passthrough slots still exist and are harmless (`connect_*` is never hit).
- Scope: currently Lab only (`run-from-db`); the COMPONENT preview (`load_anchor_scene_from_component`) does not synthesize yet. `fiber_coupler` (a single anchor) takes the original path. Tests: `backend/tests/optical/test_fiber_connector_coupling.py`.

## Kinds: fiber vs fiber_coupler

| kind | Role | Anchors | Alignment |
|---|---|---|---|
| `fiber` | A bidirectional patch cable (two optical ports) | `intercept_in` + `intercept_out` | per-end Align buttons (`align_variant: none`, tol 25 mm) |
| `fiber_coupler` | Free-space ↔ fibre coupling / collimation | `intercept_in` only | translate-to-beam (single anchor) |

The two **share** `fiber_anchor_op` (backend `register_anchor_op("fiber"/"fiber_coupler", …)`); they differ in anchor count and alignment method. Representative fiber defaultParams: PM, NA 0.13, MFD 5.3 µm, design 780 nm, 5 dB/km, min bend 25 mm.

## Polarization through a PM patch cord (2026-08-20)

Until this landed, `fiber_anchor_op` passed the Jones vector through **untouched** and the synthesized anchors' axisY came from `_ortho_basis` — an arbitrary perpendicular. So `endX.slowAxisDegInBodyFrame` (a per-end kindParam the Object panel's port editor already wrote and the viewer already drew the connector key along) and `polarizationExtinctionRatioDb` (25 dB on the kind) were **declared but never read** — the connector-refactor plan even said "the PM key PER penalty lives in the coupling op", and it did not. Two changes closed that:

- **`db_scene_loader._slow_axis_basis`** puts the synthesized anchor's **axisY on the slow axis**: `_ortho_basis(outward)` rotated about the ferrule axis by that end's `slowAxisDegInBodyFrame`. The coupling maths only ever used `r = √(off_y²+off_z²)`, which is rotation-invariant, so no geometry moved — the op just gained an axis to resolve against. `_synth_fiber_slot` also now maps `fiberType` and `polarizationExtinctionRatioDb` into the slot's `default_params`.
- **`fiber.py::_pm_transfer`** resolves the incoming Jones on the **entry** end's slow axis, applies the crosstalk, and re-expresses it on the **exit** end's slow axis. That last step is the point: **a patch cord whose two connector keys are twisted relative to each other rotates the polarization by that twist**, which is what a real one does and what finally makes the key angle worth setting.

**A PM fibre is not a polarizer** — it is a two-eigen-axis guide, so a launch on the *fast* axis is not a loss either, it just exits on the fast axis. The crosstalk is a small **unitary** mixing angle `ε = atan(10^(−PER/20))`, not an in-phase addition: an addition creates power on a two-axis launch (a 45° input came out 0.4 dB up during development), whereas a rotation is exactly power-preserving for every input and still puts leak² on the orthogonal axis for a single-axis launch, which is what the spec number means. One visible consequence: ε **adds to** the key twist (both are rotations about the propagation axis), so at 25 dB the delivered polarization sits 3.22° off the exit key.

**Not modelled — read this before trusting an off-axis launch.** The differential phase between the two axes is ~10⁶ rad over a metre of PM fibre at 852 nm (Δn ≈ 5e-4) and drifts with temperature, so no fitted number would mean anything and none is applied. Launch **on an axis** — how PM fibre is meant to be used — and the model is exact. Launch at 45° and only the **power split** is meaningful: the twin hands back the input ellipticity unchanged where a real fibre would hand back something arbitrary. SM / MM fibre is passed through untouched for the same reason (a real one scrambles, but a scramble the user cannot control is worse than none). Tests: `backend/tests/optical/test_fiber_pm_polarization.py`.

**The zero of `slowAxisDegInBodyFrame` is `_ortho_basis`'s reference, which has NOT been reconciled with the ferrule orientation the viewer draws.** So trust the angle *between* two ends, and between an end and another element's axisY; do not trust the absolute number against the drawn key mark. For an end whose outward runs along ±X that reference is horizontal (lab ±Y), so `90` puts the slow axis vertical.

## Fibre-pigtailed DEVICES are not fibres (2026-08-20)

A pigtailed part — the first is the EOSpace EOM, `eospace_az_0s5_20_pfa_pfa_850_900` — is **not** modelled as a fibre. Its asset is just the housing, and **its two ports are `fiber_connector` assets bound in the Component**, tagged `properties.portAnchor = "intercept_in" / "intercept_out"`; `_port_connector_anchors` re-seats the housing's `intercept_*` anchors onto each connector's `connect_in`, so the bulkhead is the port (details and the reason it must be a derivation: [component.md](component.md)). **Those two connectors are bound in the COMPONENT editor's "Pigtail connectors" picker since 2026-08-21** (it was called "Fiber ports" until 2026-08-23, a name that wrongly made it look like the RXM15EF's chassis bulkhead; the two are compared side by side in [component.md](component.md)) — one connector per port, seeded so `connect_in` lands on the anchor it replaces and no traced number moves; see [component.md](component.md). The patch cords are then ordinary `fiber` objects aligned onto those ports with **Align End A / B**, so everything on this page applies to them unchanged — and PM key vs PM key now actually means something on both sides of the mate. **Since 2026-08-21 the DEVICE side has its own Align End A / B too** (`PigtailEndAlignControls`), so the mate can be made from either direction: the cable's end moves to the device, or the device's pigtail moves to a beam / another receptacle. They are different mechanisms for the same gesture — a cable end is a spline endpoint, a device end is a connector binding moved by an `ObjectBinding` delta while the instrument stays put; the device side is written up in [component.md](component.md). What the device owns is only the guided path *between* its own two ports: its op re-emits at `intercept_out` as the pigtail's fundamental mode (waist `coreMfdUm/2` on the exit face, incoming tilt erased) instead of propagating a free-space beam the length of the package — the same exit contract as `fiber_anchor_op` above, reached through the kind's `fiberPigtailed` param rather than through `_synth_fiber_slot`. See the EOM section of [optics.md](optics.md).
