# The kind taxonomy and the per-kind contract

> Related: [optics.md](optics.md) (how the solver dispatches a PhysicsOp), [asset.md](asset.md) (where defaultParams live), [object-sense-kinds.md](../object-sense-kinds.md).

## Kind taxonomy (live `kinds.json` `element_kinds`: 31)

- **Emitters**: `laser_source`, `tapered_amplifier`.
- **Passive optics**: `mirror`, `dichroic_mirror`, `lens_biconvex` / `lens_plano_convex` / `lens_cylindrical`, `waveplate`, `polarizer`, `glan_polarizer`, `beam_splitter` (including PBS), `fiber` / `fiber_coupler`, `isolator` (composite), `faraday_rotator`, `aom`, `eom`, `nonlinear_crystal`, `saturable_absorber`, `fiber_connector` (cable connector).
- **Sinks**: `detector`, `camera`, `spectrometer`, `wavemeter`, `beam_dump`. `detector` is the one sink that also has an **RF** side — see the photoreceiver bullet under [the per-kind contract](#the-per-kind-contract).
- **RF kinds**: `rf_source` (AD9959 DDS, Arb Rider AWG-7172), `rf_amplifier`, `rf_cable`, `rf_cable_connector` (cable connector), `rf_switch`, `programmable_pulse_generator` (TTL), `horn_antenna` (sink).
- Plus 24 purely mechanical `passive_plugins` (mounts / posts / chassis / optical_table, …) with no physics.
- **DB-only passive kinds** (rows in `kinds`, deliberately absent from `kinds.json` because they have no code op): `unclassified` (0110), `optical_table`, the `isolator` housing, and `mechanical` (0121 — the kind for mounts/posts/holders; see the passive-kind bullet below). The live `kinds` table therefore holds more rows than `element_kinds` does — **37 as of alembic 0126**: the 31 physics kinds (0126 inserted the last 4, see the manifest-sync section below), 3 passive-plugin rows (`optical_table`, `rect_annotation`, `text_annotation`), and these 3 DB-only ones.

> Note: `backend/data/kinds.json` is the authoritative source of per-kind physics parameters. The v3 design documents once simplified the three lens kinds into a single `lens` and folded Glan into polarizer, but the live `element_kinds` really is 31. `test_kinds_manifest::TestElementKinds` pins that number (currently 31).

**The cable-connector kinds (`fiber_connector` / `rf_cable_connector`, 2026-06-12, alembic `0114`)**: first-class catalog kinds for the connector at the end of a cable (an FC ferrule, or SMA/BNC coax); the 9 physical connectors became Asset3D rows underneath them in `0115`. Each carries two geometric anchors — the cable/spline junction (at the origin, −X) and the mating / ferrule face (at `tipMm`, +X), which since alembic `0134` declares the **male** connector type `fc_pc_male` / `fc_apc_male`, derived from the row's own `default_params.polish` (the junction stays null: it mates with nothing). **Fibre spells the pair `fiber_root` / `fiber_out` since alembic `0135`** so the whole fibre vocabulary agrees (`fiber_root` → `fiber_out` → `fiber_in`, see [fiber.md](fiber.md)); **coax keeps `connect_out` / `connect_in`**, and both spellings resolve through one lookup (`utils/connectorAnchors.ts`, `db_scene_loader._find_anchor`) — and the cable-level port anchors, `intercept_in/out` (optical) and `rf_in/out` (RF), are derived from the end connector's `connect_in` (replacing the hard-coded 36.28 / 15.5 / 27 mm tip constants; landed in P2/P3). **The physics is passthrough**: a connector never takes part in a trace on its own — `connect_in/out` are not in `PRIMARY_ANCHOR_IDS`, so the tracer's `nearest_anchor_hit` can never hit them. `optical/anchor_ops/connector.py` still registers a **defensive** pass-through op (`return [ray_in]`, keyed by kind name because the tracer dispatches on kind name and a primary-anchor hit with no op is treated as a light-absorbing sink), so that even if a connector were given a primary anchor in future it would pass light through rather than swallow it. The real coupling physics is read by the cable body's op from both ends' connector params. Detail in the connector-refactor plan (2026-06-12).

**The formal definition of the connector kinds / assets (settled 2026-06-13, alembic `0117`) — this is the current single truth**:

- **The geometry's single truth is the `connect_out` / `connect_in` anchors** (there is no `tipMm` field any more). connect_out = the cable-side junction, connect_in = the outward mating / ferrule tip; both live in **each asset's own mesh frame** (the real GLBs differ per axis: fiber = Z, sma = X, bnc = Z), and the render bake normalizes the connect_out→connect_in vector (see "anchor-driven", below). connect_in's axisY is the PM slow-axis key; a fiber connect_in carries `apertureMm` (the core).
- **`fiber_connector` default_params (physically required)**: `polish` / `polishAngleDeg` / `fiberType` / `mfdUm` / `na` / `slowAxisKeyed` / `returnLossDb` (the kind also carries the column-owned `wavelengthRangeNm`; on an asset that lives in the `wavelength_range_nm` column).
- **`rf_cable_connector` default_params**: `family` / `gender` / `impedanceOhm` / `maxFreqGhz`.
- **9 assets** (`tunable_params=[]`, `locked=false`): fiber = `pm_apc_780` / `pm_pc_780` / `sm_apc_780` / `sm_pc_780` (real GLBs) plus `mm_pc_780` (a placeholder borrowing the FC STL); RF = `sma_male` / `bnc_male` (real GLBs) plus `sma_female` / `bnc_female` (placeholders, `primitive://`). Naming scheme: fiber `{fiber type}_{polish}_{wavelength}`, RF `{family}_{gender}`.
- 0117 removed `tipMm` and the pure metadata from the kind and from every asset's default_params (fiber: housing / coreUm / claddingUm / apertureDiameterMm / glassIndexAtDesignLambda; RF: couplingType).

**Cable Component-layer behaviour (2026-06-13)**: a cable Component (`kind_id` `fiber` / `rf_cable`) uses the "bind two connector assets to define the two ends" model. On the render side, `buildSceneObjectFromBindings` (lab) and the ComponentsEditor preview **special-case cables**: rather than rendering per binding node (which would draw one spline per connector asset node = overlapping splines), `deriveCablePropsFromConnectorBindings()` (`utils/componentBindings.ts`) derives both ends from the two connector bindings (fiber: fiberType + per-end polish; RF: gendered endA/endB tokens), injects them into properties, and draws the spline exactly once. End A/B is decided by `binding.properties.splineEnd "A"/"B"` (otherwise by sortOrder). **New-component wizard**: ComponentsEditor's "New Component" first picks a profile (general / cable / fiber); cable/fiber then picks two connector assets (which may be the same) → automatically creating the `kind_id` plus two bindings carrying splineEnd. For a cable, the Bindings panel shows a condensed read-only **Ends** summary (End A/B + connector, hiding pose/parent/+Add). **Appearance (§5.5)**: `properties.cableAppearance {jacketColorHex?, radiusMm?}` (`loadAsset/cableAppearance.ts`) overrides the fiberType colour table / RG-316 and the radius — **purely visual, never touching physics; the connector shell colour is unchanged** (the jacket colours only the Tube, while the boot keeps the fiberType default); edited by `CableAppearanceEditor` (currently at the Component layer; per-instance still to be wired). **Alignment**: cables have **no component-layer align** — alignment is defined by the connector asset's `connect_in` anchor, so ComponentsEditor **hides the "Align (body mm)" block** for fiber/rf_cable. **The COMPONENT preview shows the real GLBs too**: connector GLBs load asynchronously (`buildRf/FiberConnectorGroup` returns the procedural fallback first and loads in the background) and the preview is a static consumer, so ComponentsEditor calls `setRf/FiberConnectorAssetResolver` itself (as DigitalTwinViewer does) plus `subscribeRf/FiberConnectorLoaded` → bumping `connectorEpoch` (which is in the preview effect's deps) → redrawing once the GLB lands and replacing the procedural model.

**The mating compatibility matrix (plan §4.3)**: `backend/app/optical/connector_compat.py` and `frontend/src/utils/connectorCompat.ts`, one implementation each, sharing the fixture `frontend/src/utils/__tests__/connector_compat_cases.json` (parity, the same pattern as `rf_resolve.py` ↔ `rfPropagation.ts`). `evaluateConnectorMating(out, in, {keyAngleDeg?})` returns `{status: allow|warn|reject, codes[]}`: RF = families must match and genders must be opposite (otherwise reject `rf_family_mismatch` / `rf_gender_same`); fiber = polish must match (APC↔APC, PC↔PC, otherwise reject `fiber_polish_mismatch`), MM(out)→SM(in) warns `fiber_mm_to_sm_loss` (SM→MM is allowed), and PM↔PM with a key angle > `PM_KEY_TOLERANCE_DEG` (5°) warns `fiber_pm_key_misaligned`. **It only gates (link validation + filtering the Align picker); it computes no physics numbers** — the PM PER penalty and the MM→SM mode-mismatch loss stay in the coupling op (`anchor_ops/fiber.py`, P4). The Align-picker integration point is `utils/rfCableAlignment.ts` (a policy wrapper, not yet connected).

## Domain and Category (two independent axes)

Both are "just classification", but they belong to different layers, come from different kinds, and **never override each other**:

| Axis | Belongs to | Source | Used for |
|---|---|---|---|
| **Domain** (physical behaviour) | the **Asset3D** layer | `Asset3D.kind_id` → `kind.domains` | which physics runs, the PHY Editor domain rail, kind filtering |
| **Category** (catalog classification) | the **Component** layer | `Component.properties.category` (a direct field; unset = Uncategorized) | which section of the parts library it appears in |

- **Domain**: the only legal values are `optical` / `rf` / `mechanical` (DB `kinds.domains`, with CHECK `<@ {optical,rf,mechanical}` and cardinality ≥ 1, `models/hardware.py`). It is **fully kind-authoritative**: an asset's domain is its `kind.domains` (multi-domain is expressed directly by the array, e.g. `aom=['optical','rf']`), with **no** per-asset override — `properties.domains` is no longer read (the `domainAssets` / `assetDomains` override and the `faces[].domain` branch were removed on 2026-06-11, and the existing `properties.domains` in the DB was cleared). To change a domain, change the kind. There are also `primary_domain` (a single principal domain), `default_physics` (which solvers run, possibly including thermal and so on) and `port_domains` (per port, for hybrids like the AOM).
- **Category**: 6 CategoryKeys (Optical / Electronics & RF / Mounts & Mechanics / Workspace / Annotations / Uncategorized). The parts-library panel's `categoryForComponent` (`AssetLibraryPanel.tsx`) **reads `component.properties.category` directly and no longer derives it from the kind** (2026-06-11; it used to be derived automatically from the plugin's `assetCategory`): unset = Uncategorized. It is written by the `category` dropdown on the PHY Editor's COMPONENT tab (empty = Uncategorized). The parts library's second-level grouping still uses `Component.kind_id` (the finer `catalogGroup` is only for the kinds list). It is **decoupled from domain** — `physicsCapabilities` no longer takes part in category.

→ In one sentence: **Category is decided by the component's own `category` field (with the parts library sub-grouping by `Component.kind_id`), and Domain is decided by the asset's kind** — the two were never in sync (see [component.md](component.md), [asset.md](asset.md)) and never override each other.

## The `kinds` table must equal the manifest (alembic `0126`, 2026-08-20)

**The invariant**: for every row whose `name` matches a physics plugin, the manifest owns five columns outright — `display_name`, `default_params`, `anchor_template`, `needs_aperture`, `description` (the list is `kinds_manifest.MANIFEST_OWNED_KIND_COLUMNS`). They must equal `backend/data/kinds.json` exactly. Deliberately **not** owned, each with a source that outranks the manifest: `op_set_name` (a user variant repoints it), `domains` (editable in the Kinds editor; 0092 backfilled user kinds from the retired scalar column), `locked`, and `wavelength_range_nm` / `frequency_range_mhz` (the export does not emit them — they are hand-entered).

**Why this needed a migration and a test.** Alembic `0086` created the table and backfilled it from the manifest **once**, inlining the derivation in the migration body so nothing could re-run it. The frontend plugin registry — the actual source of truth — kept moving; the table did not. By the time the two were first diffed (2026-08-20) **29 of the 31 plugin-backed rows were out of sync** — 25 with a drifted column, 4 with no row at all. Per column: `default_params` 20, `anchor_template` 18, `description` 4, and `display_name` / `needs_aperture` 0. Only **`dichroic_mirror` and `mirror`** matched on all five:

- **6 values silently wrong**, all on `locked` rows: `laser_source.spatialModeX/Y` **swapped** (so the kind template disagreed with its own plugin about which axis is the 2.2 µm one — a *second*, independent instance of the X↔Y swap the per-kind-contract section below records for the `dbr_tosa` asset); `beam_splitter.polarizing` false where the plugin now defaults to a PBS, plus a stale `coatingNormalBodyLocal`; `aom.crystalLengthMm` 25 where 0120 had settled on 22.4; `aom.rfPowerMaxW` 2 vs 2.2.
- **1 stale key name**: `aom.acousticVelocityMPerS`. Alembic `0101` renamed this to `acousticVelocityMps` in `assets_3d` and `physics_elements` but **missed `kinds`** — so the exact bug 0101 existed to kill ("edit the velocity, the trace never sees it") survived untouched in the template.
- **20 params missing / 68 undeclared**, the latter mostly leftovers of `routers/components.py::DEFAULT_KIND_PARAMS` (line 143) — **not a retired table: it is still live**, seeding `physics_elements.kind_params` for a new Component via `default_kind_params_for_component` (`components.py:495`, gated at `:663`). It is the legacy v2 kindParams floor, which the anchor tracer never reads (`RfLinkPanel.tsx:1087`) — so its keys leaked into the kind template without ever being physics (`aom.figureOfMeritM2`, `aom.deflectionPerMhzUrad`, the whole `rf_switch` datasheet blob, …), including renames the DB never followed: `focalMm`→`focalLengthMm`, `transmission`→`transmittance`, `retardanceLambda`→`retardanceDeg` (½λ → 180°).
- **18 stale `anchor_template` blobs** — and this column is *not* inert. `Asset3DEditor` builds its anchor-id picker from it and auto-seeds a new asset's anchor rows (`Asset3DEditor.tsx:2847`), so a stale template silently shapes every asset created under it. The `aom` template predated the `acoustic_axis` anchor entirely, which is why `aa_mt80_a1_5_ir` never had one (alembic `0127` backfilled it; see [aom-model.md](../aom-model.md)).
- **4 plugins with no row at all** — `fiber`, `fiber_coupler`, `glan_polarizer`, `rf_cable`. They held zero assets, but the editor's kind dropdown is built from this table, so those kinds were simply **unpickable**.

**What 0126 changed and what it left alone**: it rewrote the five owned columns on the 25 drifted rows and inserted the 4 missing ones. Rows with no matching plugin (`isolator`, `mechanical`, `unclassified`, the 3 passive-plugin rows, and any user-created variant) were never touched. Forward-only — the pre-image was stale by construction, so `downgrade` is a no-op, the same call `0101` made.

⚠️ **It also rewrote 14 `locked` rows** (`aom`, `beam_splitter`, `faraday_rotator`, `fiber_connector`, `laser_source`, `lens_cylindrical`, `lens_plano_convex`, `programmable_pulse_generator`, `rf_amplifier`, `rf_cable_connector`, `rf_source`, `rf_switch`, `tapered_amplifier`, `waveplate`), which the AI rule below forbids. This was done with the user's **explicit authorisation** and is recorded, not assumed: 5 of the 6 wrong values sat on locked rows, so honouring the flag would have left the worst of the drift in place, and the values installed are the plugin defaults the solver already runs on — the write makes the table agree with behaviour rather than changing behaviour. `lock_guard` is an API-layer guard, so a migration bypasses it silently; treat that as a reason for deliberate care, never as permission.

**What now stops it recurring**:

- `app/kinds_manifest.py::kind_rows_from_manifest()` is the **single derivation** of "what should this row be", shared by the migration, the test and the audit script. 0086's mistake was inlining it.
- `backend/tests/test_kind_manifest_sync.py` asserts the invariant per-column, plus: every plugin has a row; no row carries an undeclared `default_params` key; the unbacked-row set is exactly `{isolator, mechanical, unclassified}` **with a documented reason for each**; and any unbacked row has `op_set_name='none'` (a row naming a real op set with no plugin behind it would pass the membership check and then fail at trace time).
- `backend/scripts/audit_kind_param_drift.py` is the report form — same invariant, printed all at once, exit 1 on drift. Distinct from the older `audit_kind_drift.py`, which only compares the *set* of kind names across the registry tables and so never looked at a single param value.

**The consequence for editing**: the Kinds editor is **not** where you change a built-in kind's defaults or anchor template — that edit will be reverted by the next resync and fails the test meanwhile. Edit `frontend/src/kinds/<kind>/index.ts` → `npm run export:kinds` → add a resync migration. The editor stays free for user-created variants, which have no plugin and are skipped by the invariant.

## The per-kind contract

Each kind's contract is: a frontend renderer registration (`kinds/<kind>/`) + backend physics (**live: the anchor op in `optical/anchor_ops/<kind>.py`**; the face-based `optical/kinds/<kind>/physics.py` is retired) + its parameters in `kinds.json`. Representative defaultParams: laser 852.347 nm / 50 mW (astigmatic: `spatialModeX` waist 2.2 µm with M² 1.15, `spatialModeY` waist 0.52 µm with M² 1.08, **the plugin is the truth**; note that 097d003 (2026-06-11) once swapped X↔Y on the DB side for dbr_tosa/LASER_SOURCE0 to X 0.52 / Y 2.2 **without changing the plugin**, desyncing plugin from DB — the DB has since been reverted back into agreement with the plugin; the **`kinds.laser_source` template carried the same swap independently** and was only corrected by alembic `0126`, so between those dates the asset and the kind template disagreed in opposite directions); AOM v = 4200 m/s, n = 2.26, baseEfficiency 0.85; glan_polarizer wedge 38.5°, ER 55 dB; TA gain 30 dB, sat 500 mW. A lens defaults to a thin lens (`focalLengthMm`); when the asset additionally carries `radiusFrontMm` + `refractiveIndex` + `centerThicknessMm` it switches automatically to the **thick-lens ABCD** (short focal lengths and aspheres, e.g. the A230TM-B, see [optics.md](optics.md)).

**The asset ↔ kind parameter invariant**: every asset's `default_params` must cover all of its kind's required parameters (`physics.defaultParams`, minus the column-owned `wavelengthRangeNm`), and may only use keys the kind declares (required + `physics.optionalParams`). For that to work, a kind's schema has to be "completed" with the physics parameters its op / assets actually use — model-specific and spec-sheet fields are declared with `optionalParams` (frontend-only, opt-in, not in the manifest, never force-seeded): **lens** thick-lens geometry (`radiusFrontMm` / `refractiveIndex` / `centerThicknessMm` / `radiusBackMm`). **faraday_rotator has no optionalParams**: its `defaultParams` is exactly the set the live op (`anchor_ops/misc_ops.py`) actually uses — `rotationDeg` / `lengthMm` / `refractiveIndex` (plus the column-owned `wavelengthRangeNm`); the earlier spec fields `VerdetConstantRadPerTeslaMm` / `arResidualR` / `material` / `reciprocal` were never read by the live op and have been removed. A Glan-Laser prism asset has `polarizing=true`, with `coatingNormalBodyLocal` = the axisX of its `intercept_face` anchor. **beam_splitter has no optionalParams**: its `defaultParams` is exactly what the live op (`anchor_ops/pbs.py`) uses — `lengthMm`, `refractiveIndex_o` (the reflected o-ray), `refractiveIndex_e` (the transmitted e-ray), `extinctionRatioPpDb` (the transmitted P port) / `extinctionRatioSpDb` (the reflected S port; real dB, so 100000:1 → 50 dB), `coatingNormalBodyLocal` (→ the anchor axisX reflection axis), `transmissionAxisDegBeamLocal` (→ the fast axis), `polarizing`, `splitRatioTransmitted` (2026-08-18 — the transmitted power fraction, read **only** when `polarizing` is an explicit `false`; see [optics.md](optics.md)), and the column-owned `wavelengthRangeNm`. The slab refractive index is per branch (a PBS cube that sets only an isotropic `refractiveIndex` makes the op fall back to the same value for both). **Removed** were the old fields the live op never read: `airGapAngleDeg` / `airGapThicknessMm` / `B_x_mm` / `B_y_mm` / `E_x_offset_coef` / `transmissionAxisDegBodyLocal` (only ever used by the retired face-based TS solver).

**`detector` is a sink with an electrical output (alembic `0131`, 2026-08-21)**: light stops at `intercept_in` (`_terminal_sink_op` in `anchor_ops/misc_ops.py:611` returns no continuation) but what leaves the part is a voltage, and the kind had no way to say so — one optical role, one param (`wavelengthRangeNm`). It now also declares **`rf_out`** (`min: 0`, domain `rf`, needs a direction; `frontend/src/kinds/detector/index.ts`), so a fibre-coupled photoreceiver can carry the coax jack its signal leaves on. **Since alembic `0133` (2026-08-23) it also declares `fiber_in`** (`min: 0`, domain `optical`, needs direction + aperture) — the fibre bulkhead of a fibre-coupled build — and `intercept_in` drops to `min: 0` alongside it, because the two builds are mutually exclusive: a free-space head has a bare active area and no socket, a fibre-coupled receiver has a socket and no free-space face. That leaves the kind with **zero required anchors while still being alignable**, which `plugin_exhaustiveness.test.ts` forbids in general; `detector` is in that test's explicit `ALIGNABLE_WITHOUT_REQUIRED_ANCHOR` exemption, guarded by a second test that removes the entry the moment it stops being true. Nothing is lost at runtime — `canAlignToBeam` already refuses a part whose every optical face is a receptacle. `min: 0` because a bare photodiode has no connector of its own, and — exactly like the AOM's `rf_in` — the anchor is **cable-routing geometry only**: there is no optical→RF conversion in the solver, so `responsivityAPerW` / `conversionGainVPerW` / `bandwidthHz` / `nepWPerRtHz` are spec-sheet record, not something the tracer reads. All four are intrinsic; a detector has no knob to dial, so the kind has no `stateParamKeys`. `conversionGainVPerW` is **signed** — negative means an inverting output. `default_physics` gained `rf` to match. First user: the `rxm15ef` device (below).

**The `wavelengthRangeNm` hard invariant**: **every optical kind except the two emitters (`laser_source`, `tapered_amplifier`) must carry `wavelengthRangeNm` in its `defaultParams`** — even when its live op never reads it (e.g. `faraday_rotator`, `mirror`), it is still the column-owned working band (stored in the `wavelength_range_nm` column for the UI and band validation), so it is always present in `defaultParams` and never counts as "a parameter the op actually reads" (in the strict editor it is edited through the lambda min/max fields and does not appear among the ordinary scalar fields). The two emitters carry `centerWavelengthNm` (a centre wavelength) instead of a range. The rule is enforced by `backend/tests/test_kinds_manifest.py::TestOpticalCoverage`: `test_every_non_emitter_optical_has_wavelength_range` (non-emitters must have `wavelengthRangeNm`) plus `test_emitters_have_center_wavelength` (emitters must have `centerWavelengthNm`); source spec `docs/optical-kinds-spec.md` R1/R2.

**The `locked` freeze flag (alembic 0112; `devices` 0123, `components` 0128)**: `kinds.locked` / `assets_3d.locked` / `devices.locked` / `components.locked` (BOOLEAN NOT NULL DEFAULT false) = a human has confirmed the row is "complete, not to be adjusted". Each row in the PHY Editor's KIND / ASSET3D left-hand list has a lock button on the right (`KindsEditor.tsx` / `Asset3DEditor.tsx`): once locked, that row's Edit/Delete are disabled and the right-hand form goes read-only (an asset uses `pointerEvents:none` over the whole block), leaving only the unlock button clickable. The backend blocks writes outright: `PATCH /api/kinds/{id}`, `PUT /api/v3/assets3d/{key}`, `PUT /api/assets/{id}` and the corresponding deletes return **422** whenever row.locked is set and the request changes any field other than `locked` (guard: `backend/app/lock_guard.py`); the sole exception is a request that toggles `locked` alone (unlocking). Both `KindOut` and `Asset3DV3Out` expose `locked`. **Filtering by lock state**: every catalog list now carries the same `lock: all / 🔒 locked / 🔓 unlocked` dropdown, all driven by the shared helper `components/lockFilter.ts` (`LOCK_FILTER_OPTIONS` / `matchesLockFilter`) — ASSET3D and the BUILD tab's two asset pickers since 2026-08-18 (see [build.md](build.md)), and KIND / DEVICE / COMPONENT since 2026-08-20. It is a view filter only — it never writes `locked`.

**Component joined the lock in alembic `0128` (2026-08-20)** — and this was finishing a job, not starting one. Component already had *half* a lock: `routers/components.py::is_component_locked` read a `properties['locked']` JSONB flag, that flag guarded **delete only**, and it raised **409** where every other table raises 422. Nothing in the frontend wrote it and nothing else read it; two rows carried it by hand. 0128 adds the real `locked` BOOLEAN NOT NULL DEFAULT false, moves the flag into it, strips the key so no second source of truth survives, and routes both `PUT /api/components/{id}` and the delete through the shared `assert_update_allowed` / `assert_delete_allowed`. `is_component_locked` is gone. **The frontend had three private copies of the same predicate** (`AssetLibraryPanel.tsx`, `ComponentPanel.tsx`, `sceneStore.ts`), each reading `properties.locked` — all three would have gone silently false once 0128 stripped the key (a dead "locked" badge in the catalog panel and a dead delete guard in the store). They are now one exported `isComponentLocked` in `utils/components.ts` reading `component.locked`. The UI matches the other lists: a per-row 🔒 toggle in the COMPONENT aside, an amber "locked, read-only" banner, the detail form blocked with `pointerEvents` (the Asset3DEditor device), and the Delete button hidden. Covered by `backend/tests/test_lock_guard.py` (edit → 422, delete → 422 **not** 409, pure unlock → 200, then edit succeeds).

**Filtering the KINDS list by usage (2026-08-20)**: alongside the lock dropdown, KIND has an `assets: all / ✓ has assets / ∅ none yet` dropdown (`components/usageFilter.ts`, the same three-option shape and the same view-only contract), and each row shows its Asset3D count. This exists because the `kinds` table is a catalog of what the twin **can** model, not of what is on the table right now: 15 of the 37 rows have no asset pointing at them. **Those rows are not dead** — every one has a physics plugin and a registered anchor op (e.g. `register_anchor_op("fiber_coupler", fiber_anchor_op)` in `anchor_ops/fiber.py:131`) — and deleting one would make its kind unpickable in the Asset3D editor's dropdown, which is exactly the state alembic 0126 had to repair for `fiber` / `fiber_coupler` / `glan_polarizer` / `rf_cable`. So the answer to "the list is too long" is a filter, never a delete. **AI rule (see [CLAUDE.md](../../CLAUDE.md)): never modify or delete a locked kind/asset — ask the user to unlock it first.**

**The guard is API-layer only — an Alembic migration goes straight past it.** Three changes have written locked rows anyway, each with the user's explicit authorisation and each recorded where it happened: `pbs122` and the `TS-2000-A` / `dbr_tosa` spatial-mode fit (below) went through the auditable unlock → `PUT` → relock path with a full-row diff pinning the changed fields; alembic **0126** (14 locked kinds) and **0127** (the locked `aa_mt80_a1_5_ir`) bypassed the guard outright, which is a heavier step and is argued for in the manifest-sync section above. The rule to carry forward: bypassing the lock is a decision the **user** makes and the change **documents**, never something a migration does quietly because it was convenient.

- **`op_set_name` (the indirection from kind to code op)**: kind metadata lives in the DB, but the physics op implementation always lives in code (`optical/registry.py`). Each kind row uses `op_set_name` to point at a registered set of code ops. For built-in kinds `op_set_name == name`; a UI-created variant can point at an existing op set to **reuse** its physics (e.g. `my_custom_lens` → `op_set_name='lens_biconvex'`) without touching code. Dispatch: `get_op(kind, op)` checks the registry first and only then falls back to `op_set_name` (`optical/db_kinds.py`).
- **Passive / placeholder kinds**: `op_set_name='none'` = no physics op, so the tracer runs nothing for it (e.g. the isolator housing). **`isolator` is hand-authored, not a leftover** — it is in no migration and no commit, so it was created through the Kinds editor, and it is `locked` with `domains=['mechanical']` and its own description ("Composite isolator housing — sub-components (faraday + polarizers) carry the physics. This kind is a mechanical wrapper; no anchors needed"). That is accurate: the isolator IS a Component composition — a Glan prism asset on `beam_splitter` plus a rod on `faraday_rotator` — and this kind exists to label the four leftover housing shells (`TORNOS_isolator_front/back_piece`, `IO-5-850-HP-front/back`: zero anchors, zero params, no scene object) with something better than the generic `mechanical`. It is also **load-bearing**: `devices.behavioral_kind='isolator'` on those four devices is what writes the kind onto the assets (`v3_catalog.py`'s write-through), so deleting the row would strand them. It looks like an orphan from a plugin rename and is not one — `test_kind_manifest_sync.py` records the distinction so the next reader does not re-derive it. `unclassified` (migration `0110`) is one of these: `domains=['optical','rf','mechanical']` all selected, params and anchors empty, serving as the **default kind for a fresh BUILD import** (see [build.md](build.md)) so an unclassified asset appears in all three domain rails at once. **`mechanical` (migration `0121`, `backend/alembic/versions/0121_mechanical_kind.py`) is the mechanical-domain sibling**: `op_set_name='none'`, `domains=['mechanical']`, empty params/anchors, no wavelength or frequency band — the kind for structural hardware (optical mounts, posts, post holders, clamps, pedestals, adapters). It is the asset-layer counterpart of the frontend's mechanical `passive_plugins` (which are *componentType* catalog entries, not kinds): pointing a mount asset at it moves the asset off the all-domain `unclassified` placeholder onto the PHY Editor's mechanical rail alone. It intentionally has **no frontend physics plugin** — an orphan kind disables the per-anchor direction/aperture fields (see [asset.md](asset.md)), which is correct for a part that never touches a beam. 0121 is additive: no existing asset was reassigned (e.g. `KS1T` is still `unclassified` until a human repoints it in the ASSET3D kind dropdown). **Invariant: `assets_3d.kind_id` is NOT NULL (migration `0111`)** — an asset has no "no kind" state and is at minimum `unclassified`; `components.kind_id` may still be NULL (a composite component).
