# The kind taxonomy and the per-kind contract

> Related: [optics.md](optics.md) (how the solver dispatches a PhysicsOp), [asset.md](asset.md) (where defaultParams live), [object-sense-kinds.md](../object-sense-kinds.md).

## Kind taxonomy (live `kinds.json` `element_kinds`: 31)

- **Emitters**: `laser_source`, `tapered_amplifier`.
- **Passive optics**: `mirror`, `dichroic_mirror`, `lens_biconvex` / `lens_plano_convex` / `lens_cylindrical`, `waveplate`, `polarizer`, `glan_polarizer`, `beam_splitter` (including PBS), `fiber` / `fiber_coupler`, `isolator` (composite), `faraday_rotator`, `aom`, `eom`, `nonlinear_crystal`, `saturable_absorber`, `fiber_connector` (cable connector).
- **Sinks**: `detector`, `camera`, `spectrometer`, `wavemeter`, `beam_dump`.
- **RF kinds**: `rf_source` (AD9959 DDS), `rf_amplifier`, `rf_cable`, `rf_cable_connector` (cable connector), `rf_switch`, `programmable_pulse_generator` (TTL), `horn_antenna` (sink).
- Plus 24 purely mechanical `passive_plugins` (mounts / posts / chassis / optical_table, …) with no physics.
- **DB-only passive kinds** (rows in `kinds`, deliberately absent from `kinds.json` because they have no code op): `unclassified` (0110), `optical_table`, the `isolator` housing, and `mechanical` (0121 — the kind for mounts/posts/holders; see the passive-kind bullet below). The live `kinds` table therefore holds more rows than `element_kinds` does.

> Note: `backend/data/kinds.json` is the authoritative source of per-kind physics parameters. The v3 design documents once simplified the three lens kinds into a single `lens` and folded Glan into polarizer, but the live `element_kinds` really is 31. `test_kinds_manifest::TestElementKinds` pins that number (currently 31).

**The cable-connector kinds (`fiber_connector` / `rf_cable_connector`, 2026-06-12, alembic `0114`)**: first-class catalog kinds for the connector at the end of a cable (an FC ferrule, or SMA/BNC coax); the 9 physical connectors became Asset3D rows underneath them in `0115`. Each carries two geometric anchors — `connect_out` (at the origin, −X, the cable/spline junction) and `connect_in` (at `tipMm`, +X, the mating / ferrule face) — and the cable-level port anchors, `intercept_in/out` (optical) and `rf_in/out` (RF), are derived from the end connector's `connect_in` (replacing the hard-coded 36.28 / 15.5 / 27 mm tip constants; landed in P2/P3). **The physics is passthrough**: a connector never takes part in a trace on its own — `connect_in/out` are not in `PRIMARY_ANCHOR_IDS`, so the tracer's `nearest_anchor_hit` can never hit them. `optical/anchor_ops/connector.py` still registers a **defensive** pass-through op (`return [ray_in]`, keyed by kind name because the tracer dispatches on kind name and a primary-anchor hit with no op is treated as a light-absorbing sink), so that even if a connector were given a primary anchor in future it would pass light through rather than swallow it. The real coupling physics is read by the cable body's op from both ends' connector params. Detail in the connector-refactor plan (2026-06-12).

**The formal definition of the connector kinds / assets (settled 2026-06-13, alembic `0117`) — this is the current single truth**:

- **The geometry's single truth is the `connect_out` / `connect_in` anchors** (there is no `tipMm` field any more). connect_out = the cable-side junction, connect_in = the outward mating / ferrule tip; both live in **each asset's own mesh frame** (the real GLBs differ per axis: fiber = Z, sma = X, bnc = Z), and the render bake normalizes the connect_out→connect_in vector (see "anchor-driven", below). connect_in's axisY is the PM slow-axis key; a fiber connect_in carries `apertureMm` (the core).
- **`fiber_connector` default_params (physically required)**: `polish` / `polishAngleDeg` / `fiberType` / `mfdUm` / `na` / `slowAxisKeyed` / `returnLossDb` (the kind also carries the column-owned `wavelengthRangeNm`; on an asset that lives in the `wavelength_range_nm` column).
- **`rf_cable_connector` default_params**: `family` / `gender` / `impedanceOhm` / `maxFreqGhz`.
- **9 assets** (`tunable_params=[]`, `locked=false`): fiber = `pm_apc_780` / `pm_pc_780` / `sm_apc_780` / `sm_pc_780` (real GLBs) plus `mm_pc_780` (a placeholder borrowing the FC STL); RF = `sma_male` / `bnc_male` (real GLBs) plus `sma_female` / `bnc_female` (placeholders, `primitive://`). Naming scheme: fiber `{fiber type}_{polish}_{wavelength}`, RF `{family}_{gender}`.
- 0117 removed `tipMm` and the pure metadata from the kind and from every asset's default_params (fiber: housing / coreUm / claddingUm / apertureDiameterMm / glassIndexAtDesignLambda; RF: couplingType).

**Cable Component-layer behaviour (2026-06-13)**: a cable Component (`kind_id` `fiber` / `rf_cable`) uses the "bind two connector assets to define the two ends" model. On the render side, `buildSceneObjectFromBindings` (lab) and the ComponentsEditor preview **special-case cables**: rather than rendering per binding node (which would draw one spline per connector asset node = overlapping splines), `deriveCablePropsFromConnectorBindings()` (`utils/componentBindings.ts`) derives both ends from the two connector bindings (fiber: fiberType + per-end polish; RF: gendered endA/endB tokens), injects them into properties, and draws the spline exactly once. End A/B is decided by `binding.properties.splineEnd "A"/"B"` (otherwise by sortOrder). **New-component wizard**: ComponentsEditor's "New Component" first picks a profile (general / cable / fiber); cable/fiber then picks two connector assets (which may be the same) → automatically creating the `kind_id` plus two bindings carrying splineEnd. **The mating compatibility matrix (plan §4.3)**: `backend/app/optical/connector_compat.py` and `frontend/src/utils/connectorCompat.ts`, one implementation each, sharing the fixture `frontend/src/utils/__tests__/connector_compat_cases.json` (parity, the same pattern as `rf_resolve.py` ↔ `rfPropagation.ts`). `evaluateConnectorMating(out, in, {keyAngleDeg?})` returns `{status: allow|warn|reject, codes[]}`: RF = families must match and genders must be opposite (otherwise reject `rf_family_mismatch` / `rf_gender_same`); fiber = polish must match (APC↔APC, PC↔PC, otherwise reject `fiber_polish_mismatch`), MM(out)→SM(in) warns `fiber_mm_to_sm_loss` (SM→MM is allowed), and PM↔PM with a key angle > `PM_KEY_TOLERANCE_DEG` (5°) warns `fiber_pm_key_misaligned`. **It only gates (link validation + filtering the Align picker); it computes no physics numbers** — the PM PER penalty and the MM→SM mode-mismatch loss stay in the coupling op (`anchor_ops/fiber.py`, P4). The Align-picker integration point is `utils/rfCableAlignment.ts` (a policy wrapper, not yet connected).

## Domain and Category (two independent axes)

Both are "just classification", but they belong to different layers, come from different kinds, and **never override each other**:

| Axis | Belongs to | Source | Used for |
|---|---|---|---|
| **Domain** (physical behaviour) | the **Asset3D** layer | `Asset3D.kind_id` → `kind.domains` | which physics runs, the PHY Editor domain rail, kind filtering |
| **Category** (catalog classification) | the **Component** layer | `Component.properties.category` (a direct field; unset = Uncategorized) | which section of the parts library it appears in |

- **Domain**: the only legal values are `optical` / `rf` / `mechanical` (DB `kinds.domains`, with CHECK `<@ {optical,rf,mechanical}` and cardinality ≥ 1, `models/hardware.py`). It is **fully kind-authoritative**: an asset's domain is its `kind.domains` (multi-domain is expressed directly by the array, e.g. `aom=['optical','rf']`), with **no** per-asset override — `properties.domains` is no longer read (the `domainAssets` / `assetDomains` override and the `faces[].domain` branch were removed on 2026-06-11, and the existing `properties.domains` in the DB was cleared). To change a domain, change the kind. There are also `primary_domain` (a single principal domain), `default_physics` (which solvers run, possibly including thermal and so on) and `port_domains` (per port, for hybrids like the AOM).
- **Category**: 6 CategoryKeys (Optical / Electronics & RF / Mounts & Mechanics / Workspace / Annotations / Uncategorized). The parts-library panel's `categoryForComponent` (`AssetLibraryPanel.tsx`) **reads `component.properties.category` directly and no longer derives it from the kind** (2026-06-11; it used to be derived automatically from the plugin's `assetCategory`): unset = Uncategorized. It is written by the `category` dropdown on the PHY Editor's COMPONENT tab (empty = Uncategorized). The parts library's second-level grouping still uses `Component.kind_id` (the finer `catalogGroup` is only for the kinds list). It is **decoupled from domain** — `physicsCapabilities` no longer takes part in category.

→ In one sentence: **Category is decided by the component's own `category` field (with the parts library sub-grouping by `Component.kind_id`), and Domain is decided by the asset's kind** — the two were never in sync (see [component.md](component.md), [asset.md](asset.md)) and never override each other.

## The per-kind contract

Each kind's contract is: a frontend renderer registration (`kinds/<kind>/`) + backend physics (**live: the anchor op in `optical/anchor_ops/<kind>.py`**; the face-based `optical/kinds/<kind>/physics.py` is retired) + its parameters in `kinds.json`. Representative defaultParams: laser 852.347 nm / 50 mW (astigmatic: `spatialModeX` waist 2.2 µm with M² 1.15, `spatialModeY` waist 0.52 µm with M² 1.08, **the plugin is the truth**; note that 097d003 (2026-06-11) once swapped X↔Y on the DB side for dbr_tosa/LASER_SOURCE0 to X 0.52 / Y 2.2 **without changing the plugin**, desyncing plugin from DB — the DB has since been reverted back into agreement with the plugin); AOM v = 4200 m/s, n = 2.26, baseEfficiency 0.85; glan_polarizer wedge 38.5°, ER 55 dB; TA gain 30 dB, sat 500 mW. A lens defaults to a thin lens (`focalLengthMm`); when the asset additionally carries `radiusFrontMm` + `refractiveIndex` + `centerThicknessMm` it switches automatically to the **thick-lens ABCD** (short focal lengths and aspheres, e.g. the A230TM-B, see [optics.md](optics.md)).

**The asset ↔ kind parameter invariant**: every asset's `default_params` must cover all of its kind's required parameters (`physics.defaultParams`, minus the column-owned `wavelengthRangeNm`), and may only use keys the kind declares (required + `physics.optionalParams`). For that to work, a kind's schema has to be "completed" with the physics parameters its op / assets actually use — model-specific and spec-sheet fields are declared with `optionalParams` (frontend-only, opt-in, not in the manifest, never force-seeded): **lens** thick-lens geometry (`radiusFrontMm` / `refractiveIndex` / `centerThicknessMm` / `radiusBackMm`). **faraday_rotator has no optionalParams**: its `defaultParams` is exactly the set the live op (`anchor_ops/misc_ops.py`) actually uses — `rotationDeg` / `lengthMm` / `refractiveIndex` (plus the column-owned `wavelengthRangeNm`); the earlier spec fields `VerdetConstantRadPerTeslaMm` / `arResidualR` / `material` / `reciprocal` were never read by the live op and have been removed. A Glan-Laser prism asset has `polarizing=true`, with `coatingNormalBodyLocal` = the axisX of its `intercept_face` anchor. **beam_splitter has no optionalParams**: its `defaultParams` is exactly what the live op (`anchor_ops/pbs.py`) uses — `lengthMm`, `refractiveIndex_o` (the reflected o-ray), `refractiveIndex_e` (the transmitted e-ray), `extinctionRatioPpDb` (the transmitted P port) / `extinctionRatioSpDb` (the reflected S port; real dB, so 100000:1 → 50 dB), `coatingNormalBodyLocal` (→ the anchor axisX reflection axis), `transmissionAxisDegBeamLocal` (→ the fast axis), `polarizing`, `splitRatioTransmitted` (2026-08-18 — the transmitted power fraction, read **only** when `polarizing` is an explicit `false`; see [optics.md](optics.md)), and the column-owned `wavelengthRangeNm`. The slab refractive index is per branch (a PBS cube that sets only an isotropic `refractiveIndex` makes the op fall back to the same value for both). **Removed** were the old fields the live op never read: `airGapAngleDeg` / `airGapThicknessMm` / `B_x_mm` / `B_y_mm` / `E_x_offset_coef` / `transmissionAxisDegBodyLocal` (only ever used by the retired face-based TS solver).

**The `wavelengthRangeNm` hard invariant**: **every optical kind except the two emitters (`laser_source`, `tapered_amplifier`) must carry `wavelengthRangeNm` in its `defaultParams`** — even when its live op never reads it (e.g. `faraday_rotator`, `mirror`), it is still the column-owned working band (stored in the `wavelength_range_nm` column for the UI and band validation), so it is always present in `defaultParams` and never counts as "a parameter the op actually reads" (in the strict editor it is edited through the lambda min/max fields and does not appear among the ordinary scalar fields). The two emitters carry `centerWavelengthNm` (a centre wavelength) instead of a range. The rule is enforced by `backend/tests/test_kinds_manifest.py::TestOpticalCoverage`: `test_every_non_emitter_optical_has_wavelength_range` (non-emitters must have `wavelengthRangeNm`) plus `test_emitters_have_center_wavelength` (emitters must have `centerWavelengthNm`); source spec `docs/optical-kinds-spec.md` R1/R2.

**The `locked` freeze flag (alembic 0112)**: `kinds.locked` / `assets_3d.locked` (BOOLEAN NOT NULL DEFAULT false) = a human has confirmed the row is "complete, not to be adjusted". Each row in the PHY Editor's KIND / ASSET3D left-hand list has a lock button on the right (`KindsEditor.tsx` / `Asset3DEditor.tsx`): once locked, that row's Edit/Delete are disabled and the right-hand form goes read-only (an asset uses `pointerEvents:none` over the whole block), leaving only the unlock button clickable. The backend blocks writes outright: `PATCH /api/kinds/{id}`, `PUT /api/v3/assets3d/{key}`, `PUT /api/assets/{id}` and the corresponding deletes return **422** whenever row.locked is set and the request changes any field other than `locked` (guard: `backend/app/lock_guard.py`); the sole exception is a request that toggles `locked` alone (unlocking). Both `KindOut` and `Asset3DV3Out` expose `locked`. **Filtering by lock state (2026-08-18)**: the ASSET3D list has a `lock: all / 🔒 locked / 🔓 unlocked` dropdown between the kind filter and the id search (`Asset3DEditor.tsx`), and the BUILD tab has the same dropdown over its two asset pickers (see [build.md](build.md)); both use the shared helper `components/lockFilter.ts` (`LOCK_FILTER_OPTIONS` / `matchesLockFilter`). It is a view filter only — it never writes `locked`. **AI rule (see [CLAUDE.md](../../CLAUDE.md)): never modify or delete a locked kind/asset — ask the user to unlock it first.**

- **`op_set_name` (the indirection from kind to code op)**: kind metadata lives in the DB, but the physics op implementation always lives in code (`optical/registry.py`). Each kind row uses `op_set_name` to point at a registered set of code ops. For built-in kinds `op_set_name == name`; a UI-created variant can point at an existing op set to **reuse** its physics (e.g. `my_custom_lens` → `op_set_name='lens_biconvex'`) without touching code. Dispatch: `get_op(kind, op)` checks the registry first and only then falls back to `op_set_name` (`optical/db_kinds.py`).
- **Passive / placeholder kinds**: `op_set_name='none'` = no physics op, so the tracer runs nothing for it (e.g. the isolator housing). `unclassified` (migration `0110`) is one of these: `domains=['optical','rf','mechanical']` all selected, params and anchors empty, serving as the **default kind for a fresh BUILD import** (see [build.md](build.md)) so an unclassified asset appears in all three domain rails at once. **`mechanical` (migration `0121`, `backend/alembic/versions/0121_mechanical_kind.py`) is the mechanical-domain sibling**: `op_set_name='none'`, `domains=['mechanical']`, empty params/anchors, no wavelength or frequency band — the kind for structural hardware (optical mounts, posts, post holders, clamps, pedestals, adapters). It is the asset-layer counterpart of the frontend's mechanical `passive_plugins` (which are *componentType* catalog entries, not kinds): pointing a mount asset at it moves the asset off the all-domain `unclassified` placeholder onto the PHY Editor's mechanical rail alone. It intentionally has **no frontend physics plugin** — an orphan kind disables the per-anchor direction/aperture fields (see [asset.md](asset.md)), which is correct for a part that never touches a beam. 0121 is additive: no existing asset was reassigned (e.g. `KS1T` is still `unclassified` until a human repoints it in the ASSET3D kind dropdown). **Invariant: `assets_3d.kind_id` is NOT NULL (migration `0111`)** — an asset has no "no kind" state and is at minimum `unclassified`; `components.kind_id` may still be NULL (a composite component).

## The device registry and per-role anchor specs (the RF architecture, 2026-06-14; 1:1 device coverage 2026-06-15)

> Plan: `RF_ARCHITECTURE_PLAN.md` (three axes: a **closed small set of behavioural kinds** / an **open flat set of devices** / **catalog & instances**). **The dependency is one-way, `device → behavioural kind`, and never the reverse** — "adding instrument number N = adding one device file, touching no behaviour, schema, Python or tests".
>
> **Progress**: Phases 1+2 (the 6 RF kinds) landed 2026-06-14; **Phase 3a (same day) converted all optical and connector kinds to `roles` as well** → all 31 physics kinds now use per-role specs (the purely mechanical `passive_plugins` have no physics and carry no roles). The optical conversion was **zero-regression**: the derived legacy `anchors` array is **set-equal** to the pre-conversion one for every kind and `port_domains` is bit-identical (a verification script compared against `git show HEAD:…/kinds.json`), with the whole test suite green (including `TestOpticalCoverage` and the optical golden fixtures). **Phase 3b (1:1 device coverage completed 2026-06-15)**: first two optical device examples `bb1_e03` / `la1509_b` were added, then **every existing Asset3D got a matching device** (the device registry holds 29 = 7 RF + 4 coax connectors + 18 optical). Device-template coordinates and scalar params were **lifted from the live assets' confirmed anchors** (a one-shot bootstrap script, since deleted). **All 23 assets now carry a `device_id`** (including the 17 originally locked rows). The write flow for a locked row was **unlock → `PUT {deviceId, anchors:<existing>}` → relock**: because the same payload carries explicit anchors, the seeder does **not** re-materialize them (the confirmed coordinates are unchanged to the digit, since the `AnchorV3` schema round-trips losslessly), so only the `device_id` column changes; and because the device's `defaultParams` were lifted from the same asset, the `setdefault` merge is a no-op. **The axisY restriction on polarization-sensitive optical devices has been lifted** (see below — a device anchor may declare an explicit `axisYBodyLocal`). **Not done**: an isolator composite device (today two leaf devices `io5_850_front` / `io5_850_back` each carry the `isolator` kind; the composite `{subDevices[],ownedAnchors[]}` shape is still TODO), and §7 stage 2.

- **Per-role anchor specs (`roles`, `kinds/_plugin.ts`)**: these replace the old 5 parallel arrays (`required` / `optional` / `needsDirection` / `needsAperture` / `needsFastAxis`) plus `portDomains`. `RoleSpec = { min, max?, domain, direction?, aperture?, fastAxis? }`: `min≥1` = required, `min:0` = optional; **an omitted `max` = a single port (1)**, `null` = unbounded multi-port (the DDS's 4×CH, a switch's RF1/RF2), a number = bounded. `domain` absorbs `portDomains`. **All 31 physics kinds treat `roles` as the single truth**, with the legacy `anchors` derived by `anchorContractFromRoles()` at the plugin definition site (`needsFastAxis` is derived alongside — the fast-axis gating for waveplate / eom / beam_splitter / polarizer / glan_polarizer / laser_source / tapered_amplifier depends on it; **note the manifest does not emit `needs_fast_axis`, so it is outside the set-equal comparison and had to be preserved case by case during the conversion**). **`portDomains` was deliberately left conservative**: RF kinds derive it with `portDomainsFromRoles()`, while optical kinds **keep their original hand-written value or stay empty** (most optical kinds have no portDomains and rely on `resolvePortDomain`'s `intercept_*→optical` heuristic), so the manifest's `port_domains` is bit-unchanged. Every existing consumer (`rfLinkPorts.ts`, the manifest, the editor gating) reads the same array — zero regression. Every physics plugin carries `roles` in the manifest, read by `kinds_manifest.roles_by_kind()`.
- **The device registry — a DB table since alembic `0123` (2026-08-18)**: devices used to be `frontend/src/devices/<slug>.ts`, a `DEVICES` tuple in `_registry.ts` exported into `backend/data/kinds.json::devices[]` by `npm run export:kinds`. Adding the 40th instrument therefore meant editing two TS files, re-running the exporter and restarting the backend, and the PHY Editor could only ever *pick* a device — never create or correct one. They are now rows in **`devices`** (`slug` = the value `assets_3d.device_id` stores, `display_name`, `behavioral_kind` nullable, `component_type`, `mesh`, `anchors` JSONB, `default_params` JSONB, `locked`), written through **`/api/devices`** (`routers/devices.py`) and edited in the PHY Editor's **DEVICE** section (`components/DevicesEditor.tsx`); the frontend reads them from `store/devicesStore.ts` instead of a compile-time barrel. `devices.anchors` deliberately keeps the exporter's snake_case shape (`role` / `position_mm_body_local` / `direction_body_local` / `axis_y_body_local` / `connector_type` / `aperture_*`) so `materialize_device_anchors` consumes a row unchanged; the API aliases it to camelCase. `slug` is **not** patchable (it is what `assets_3d.device_id` points at), `locked` obeys the same `lock_guard` as Kind / Asset3D, and DELETE is refused with 409 while any Asset3D still references the slug. The migration seeds all 39 rows from `0123_devices_seed.json` — a snapshot next to the migration, not `kinds.json`, because that manifest loses its `devices[]` block in the same change. - **The `component_anchor_contracts` derivation rule (for anchor locking; avoids collisions)**: `app/components/anchor_contracts.py` derives `componentType → [AnchorTemplate]` from the `devices` table **only when `component_type !== behavioral_kind`** (i.e. this device is a *concrete model* such as `dds_ad9959_pcb` / `rf_generator`, not a generic kind-shaped one like `mirror` / `rf_amplifier`) — otherwise several devices of the same kind would collide on the key and overwrite each other. Generic devices (all the optical ones plus the RF placeholders) only go into `devices[]`; their anchors can still be seeded, they just don't take part in anchor locking. The AD9959's 4×CH template **moved out of `rf_source.componentAnchorContracts` into the device**. **The seeder reads the device row (`services/device_seed.load_device_record`), not component_anchor_contracts.** Until alembic 0123 this map was materialised by `scripts/export_kinds_manifest.ts` into `kinds.json::component_anchor_contracts` and read by `kinds_manifest.component_anchor_contracts()`; with devices in the DB the exporter has no source for it, so both that manifest key and the synchronous `COMPONENT_ANCHOR_CONTRACTS` module constant are gone — the accessor is `async all_anchor_contracts(session)` / `get_anchor_contract(session, componentType)`. Verified identical across the move (`{dds_ad9959_pcb, rf_generator}` before and after); covered by `backend/tests/test_devices.py`.
- **`assets_3d.device_id` (alembic `0118`, nullable Text)**: a pointer into the device registry — it holds `devices.slug`, and is deliberately **not** a declared FK (an asset may point at a slug that no longer exists; a 404 from the seeder beats a cascade through the asset catalog). When set, that asset's anchors are a **materialized view** of the device template (one-click seed/refresh in the PHY Editor, replacing `upsert_dds_chassis_1u.py`), and `kind_id` is **written through** from the device's `behavioralKind`. On the write path `PUT /api/v3/assets3d/{key}` with a `deviceId`, `v3_catalog.py` loads the row with `services/device_seed.py:load_device_record()` and calls `materialize_device_anchors()` to turn the device anchors into tri-axis form (`positionMmBodyLocal` + `axisX/Y/Z`: axisX is derived from `direction_body_local`; axisY takes the device's explicit `axis_y_body_local` after Gram-Schmidt orthogonalization with Z = X×Y, or an arbitrary orthogonal complement when absent; `aperture_shape` / `width` / `height` are carried across) and writes them into `row.anchors`, sets `row.kind_id=behavioral_kind`, and merges the device's `defaultParams`. When the same payload carries explicit `anchors` / `kind_id`, those win (the user has already fine-tuned the coordinates — this is the path taken when giving a locked row a device, which is why its existing anchors are unchanged to the digit). **The tracer still reads `asset.anchors` unchanged** — this is a metadata-only column addition, with no read-path change and no backfill (existing assets stay device-less until a human assigns one in the editor). §7 has two stages: this was stage 1 (add the column + write-through seeding); deriving the kind at load time and removing the `kind_id` column is a separate later migration.
