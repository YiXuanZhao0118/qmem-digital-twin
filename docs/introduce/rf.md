# RF subsystem overview (source → cable → amp/switch → AOM)

> This file is **the index and panorama of the whole RF subsystem**. The details are spread across [cable.md](cable.md) (coax + RF graph propagation), [kinds.md](kinds.md) (the device registry / per-role contracts), [timing.md](timing.md) (PPG / TimingProgram) and [optics.md](optics.md) (the AOM Bragg drive). Read this first for the whole picture, then jump to the detail file you need.
>
> **The one-sentence mental model**: RF is **not ray tracing**; it is a BFS over a port adjacency graph. Each `rf_out` of a source seeds one signal, which travels along `rf_cable`s (transparent edges) through amplifiers (adding gain) and switches (routing by TTL) until it reaches the `rf_in` of an `aom` / `eom` (a sink) and becomes a Bragg / EO drive. The frontend's `rfPropagation.ts` and the backend's `rf_resolve.py` are **the same model and must stay at parity**.

---

## 1. Behavioural kinds (the RF "things")

Each kind uses a per-role anchor spec (`roles`, see [kinds.md](kinds.md)). The RF Link panel only accepts ports whose `domain ∈ {rf, ttl, trigger, rfout}`.

| kind | Role | RF role / domain | File |
|---|---|---|---|
| `rf_source` | DDS / synth, the emitting end | `rf_out` (multi-port CH0..CH3) `rf` | `kinds/rf_source/index.ts` |
| `rf_amplifier` | `rf_in → rf_out`, applying `gainDb` (clamped at `outputPowerMaxDbm`) | `rf_in`/`rf_out` `rf` | `kinds/rf_amplifier/index.ts` |
| `rf_switch` | A shared `rf_in` → N `rf_out`s (RF1/RF2…), routed by TTL | `rf_in`/`rf_out` `rf` + `ttl_in` `ttl` | `kinds/rf_switch/index.ts` |
| `programmable_pulse_generator` (PPG) | One `rf_out` gate (TTL/Trigger), bound to a TimingProgram | `rf_out` → `rfout` (a special case, see below) | `kinds/programmable_pulse_generator/index.ts` |
| `horn_antenna` | Transmit / receive antenna | sink/emitter | `kinds/horn_antenna/index.ts` |
| `rf_cable` | An **edge** of the graph (transparent, lossless) | `rf_in`/`rf_out` (derived from the spline) | `kinds/rf_cable/index.ts` |
| `rf_cable_connector` | Connector geometry (sma/bnc × male/female), passthrough | `connect_in`/`connect_out` (not primary) | `kinds/rf_cable_connector/index.ts` |
| `aom` / `eom` | `rf_in` is a **sink** → Bragg / EO drive | `rf_in` `rf` | `kinds/aom`, see [optics.md](optics.md) |

**Signal domains and compatibility rules** (`utils/rfLinkPorts.ts`): `RfLinkSignalDomain = "rf"|"ttl"|"trigger"|"rfout"`. `domainsAreCompatible` (`rfLinkPorts.ts:28`): the same domain always connects; `rfout` (a PPG output) is compatible with `ttl` and `trigger` but never crosses into analogue `rf`. **The PPG's `rf_out` special case**: `resolveRfLinkPortDomain` (`rfLinkPorts.ts:48`) maps it to `rfout`, so the `ttl` its role declares only affects the generic heuristics, not the connection type.

## 3. The RF Link panel (UI, `components/RfLinkPanel.tsx`)

Three columns bucketed automatically (source / transducer / sink); nodes are the RF-bearing SceneObjects and edges are each `rf_cable`'s `rfCableEndpoints.{A,B}`.

- **Where the nodes come from**: the `nodes` useMemo (`RfLinkPanel.tsx:825`) → `kindParticipatesInRfLink` (`rfLinkPorts.ts:114`) gates out non-RF kinds → `rfLinkPortsOf` (`RfLinkPanel.tsx:208`) derives the ports from the **asset's anchors**. The asset is resolved with `primaryAsset` (the binding tree, not `comp.asset3dId`). **When there genuinely is no asset** it falls back to `rfLinkRoleAnchors(kind)` (`rfLinkPorts.ts:134`), synthesizing ports from the role contract (displayed as "NO CONN" and not draggable). Detail in "Where the RF Link panel's nodes come from" in [cable.md](cable.md).
- **Per-port editing**: a DDS `rf_out` row can edit Freq/Vpp; an AOM `rf_in` shows the incoming signal plus **η%** (see below); an amp shows its gain and Vpp_in→Vpp_out. **Channels are both read and written through the ownership chain** (fixed 2026-08-14): display goes through `channelsByObjectId` (`RfLinkPanel.tsx:918`), resolving `dynamicSources` > the Asset's `defaultParams` > `kindParams`, and writes go through `updateSceneObject` into **`dynamicSources.channels`** (the same path as `Ad9959ObjectControls.updateChannel`). **Never write `kindParams`** — the ad9959 asset authors `channels` itself (and marks it tunable), the asset layer always beats kindParams, and the result is "the panel's numbers changed but propagation didn't", with the downstream AOM stuck on the asset's 80 MHz / 1.0 Vpp.
- **The AOM `rf_in` η readout shares the solver's source (fixed 2026-08-14)**: `aomDriveReadout` (`RfLinkPanel.tsx:344`) calls `diffractionEfficiency` / `rfPowerForPeakEfficiencyW` from `optical/kinds/aom/physics.ts` directly — the same datasheet model the tracer runs (`η = baseEfficiency·sin²((π/2)√(P/P_peak(λ)))·G(f)`, `P_peak(λ)=rfPowerForPeakW·(λ/peakRefWavelengthNm)²`). Three alignment points are all required: ① the **parameter layer** uses the asset's `defaultParams` + `dynamicSources` (what the tracer sees), not the PhysicsElement `kindParams`; ② the **wavelength** comes from the scene emitter's `centerWavelengthNm` (`sceneWavelengthNm`, falling back to a constant only with multiple wavelengths) — since `P_peak ∝ λ²`, 780 vs 852 differ by 19%; ③ **G(f)'s design centre** stays the AOM's own `centerFreqMhz` (passed as `designCenterFreqMhz`), or treating the carrier as the centre makes G ≡ 1 and detuning costs no efficiency. The badge is graded on `η / baseEfficiency` (<0.5 under, <0.9 off-peak, otherwise OK), because overdriving pushes past the sin² inflection so more power means *less* efficiency — something a Vpp threshold cannot express.
- **Dragging a connection**: pointer-dragging from a port dot calls `createRfCableBetweenPorts` (`store/sceneStore.ts:2422`), which creates a new `rf_cable` and links both ends. Rules: different objects, opposite roles, compatible domains, defined connectors, and both ports free. **Automatic cable-variant selection**: the two ports' own `connectorType` (`sma_*` / `bnc_*`, `connectorFamilyFromAnchor`) is matched against the three catalog cables (SMA-SMA / BNC-SMA / BNC-BNC), trying direct and reverse (A/B swapped); a cross-family SMA↔BNC uses the asymmetric `RF cable BNC SMA`. **Each end's family is derived from that end's bound connector asset** (`end_a` / `end_b` binding → the `rf_cable_connector` asset's `defaultParams.family`, via `deriveCablePropsFromConnectorBindings`), **not** from the component's `properties.endAConnector` (which is empty on the catalog rows).
- **Right-click**: on an empty `ttl_in` / `trigger_in` → "Create Pulse & Timing here" spawns a PPG; on a connected port → "Disconnect cable".
- Nodes are draggable and their positions are stored in localStorage.

## 4. The RF propagation BFS (the physics graph, frontend/backend parity)

**Frontend**: `buildRfPropagation` in `utils/rfPropagation.ts` (`rfPropagation.ts:440`); `rfPropagationSchedule.ts` precomputes one snapshot per timing section (`buildRfPropagationSchedule:84`), and scrubbing does an O(log N) lookup with `getRfSnapshotAt:114`.
**Backend (authoritative)**: `build_rf_propagation` in `backend/app/optical/rf_resolve.py` (:372); `load_rf_inputs` (:593) fetches the scene; `resolve_aom_rf_drive` (:690) → `hydrate_aom_rf_drive` (:732) resolves the signal arriving at an AOM's `rf_in` into `{aomFreqMhz, rfDrivePowerW=vpp²/(8·50Ω)}` and feeds it into the Bragg solution (`/api/v3/solver`).

- **Node asset/anchor resolution (the parity invariant)**: a node's "device asset" (which supplies the `rf_out` / `rf_in` anchors and specs such as `fullScaleVpp`) is obtained as **the single root binding with `targetKind="asset"` → that asset; otherwise the legacy `component.asset3dId`**. That is exactly the semantics of the frontend's `componentBindings.primaryAsset` (`componentBindings.ts:104`). Connectors and sub-assets are **children** of the binding tree and are **never** a node's primary asset. **Both sides must pick the primary by the same rule or the BFS desyncs** — which is now the case: the frontend's `buildAnchorsByObject` / `buildAssetParamsByObject` (`rfPropagation.ts:200/219`) call `primaryAsset`, and the backend's `load_rf_inputs` calls the corresponding `_primary_asset_id` (`rf_resolve.py`, aligned line for line with the frontend). **A parity subtlety**: `primaryAsset` does not honour `ObjectBinding.asset_3d_id_override` (its frontend signature does not even take objectBindings), so the backend deliberately doesn't either — both sides consistently use the root binding / legacy column.
- **Seed Vpp** = `amplitudeScale × fullScaleVpp` (both `fullScaleVpp` and `channels[]` are **asset coefficients**, overridable per instance through `dynamic_sources`).
- **Passthrough parameter ownership (fixed 2026-08-13)**: the parameters an amp's or switch's transfer sees are `dynamicSources` > the Asset's `defaultParams` > the PhysicsElement's `kindParams`, matching the ownership chain recorded in [object.md](object.md). Frontend `resolveElementParams` (`rfPropagation.ts:499`), backend `_resolved_params` (`rf_resolve.py:393`); all three of the TTL pre-pass's manual `ttlState`, the PPG's `restState` / `timingProgramId`, and the BFS's transfer calls go through it. **It previously read only `kindParams`**, so every switch/amp knob an asset author had written or a user had tuned per instance was ignored — most visibly, the `rf_switch` plugin declares `ttlState` tunable (writing it into `dynamicSources`) yet it could never be read, so manual TTL switching did nothing at all.
- Cables pass through transparently; an amp applies `gainDb` (exceeding `outputPowerMaxDbm` → `saturated`); a switch picks the path by TTL (a bound PPG's timing or a manual `ttlState`) plus insertion loss.
- **The PPG gate level = `inInterval XOR (restState === "HIGH")` (fixed 2026-08-14)**: a gate pre-pass computes every PPG's level across the scene first (frontend `rfPropagation.ts:528`, backend `rf_resolve.py:421`), and the TTL pre-pass is then just a lookup. Invariant: `restState` is **the level *outside* the drawn blocks**, so rest = HIGH turns the user's blocks into LOW pulses (negative logic); `idleRestMode` (scrub stopped) ignores intervals, which is the degenerate case of the XOR. A plugged-in PPG **always owns that line**, using its rest level even with no program bound (it used to fall through to the switch's manual `ttlState`). The contract is written down in `types/digitalTwin.ts` `ProgrammablePulseGeneratorParams.restState` and `schemas.py` `rest_state`.
- **Whether an AOM is RF-driven is topology, not the presence of a carrier**: only "something is plugged into `rf_in`" (`connectedPorts` / `connected_ports` = every port key in the adjacency table) hands control to the RF link; an AOM with nothing plugged in keeps the asset's rated operating point. Writing the test as "some timing section delivers a carrier" would make an AOM that is **wired but never receives a signal** (a switch parked on the other throw, a powered-off source) look unwired, fall back to the rated drive, and draw a full set of sidebands with no RF at all.
- **First-arrival-wins, no superposition.** Powered-off sources/amps/switches are excluded from the BFS (consistent with the Instrument Power panel).
- `/api/rf-chains` (`routers/rf_chains.py`, Phase RF.2) stores per-terminal RF chain **metadata**, **not** propagation truth — don't confuse it with the BFS.

## 5. RF cable geometry / rendering

A single object plus a per-instance spline (`rfCableNodes`). Each end binds one `rf_cable_connector` asset (the end_a/end_b bindings). Connector models: the device GLB (`sma_male` and friends) or the procedural fallback; `bakeConnectorByAnchors` (`three/loadAsset/connectorBake.ts`) puts `connect_out` on the spline node and `connect_in` at +tip. **Alignment**: `resolveLinkedRfCableEndpoint` (`utils/rfCableAnchorResolver.ts:248`) pushes the node back by the connector tip so `connect_in` lands on the target port. **The tip is derived from the anchors**, `connectorTipMmFromAnchors` (`rfCableAnchorResolver.ts:71` = `|connect_in − connect_out|`), not from hard-coded family constants (`RF_CONNECTOR_TIP_MM=15.5` / `RF_BNC=27` are only true of the procedural connectors). Full detail in [cable.md](cable.md).

## 6. Other related features

- **The Asset3D editor**: a per-anchor `connector_type` dropdown (the 4 gendered values), editable on unlocked rows (a `locked` row is entirely read-only). `components/Asset3DEditor.tsx`.
- **Pulse & Timing**: PPG ↔ TimingProgram is one-to-one; `rf_out` emits the TTL/Trigger gate; the channel index follows the ordering of the PPGs in the scene. See [timing.md](timing.md).
- **Instrument Power**: switching off a laser/source cascades downstream (source → no RF → the AOM has no drive).

✅ **A PPG sitting too deep is the PPG's own male-pin length, not the port anchor's problem (2026-08-14)**: `computePpgMountedThreePose` mates the PPG's `rf_out` anchor onto the target port's anchor.   - **Iron rule: this offset must be fixed on the PPG side, never by moving the instrument's port anchor.** `ttl_in` is a **shared contract** that the cable endpoint solver also reads; moving it to accommodate the PPG would silently move every cable plugged into the same port — which is exactly what caused the amp's cable to sit 8.3 mm off after the ZYSWA/ZHL anchors were changed in this same round.
  - **Implementation**: `matingProtrusionMm(ppgAsset)` reads the asset's `defaultParams.matingProtrusionMm`, and the mount retreats the body along the mating axis by that distance so the **male pin's tip**, rather than the anchor, lands on the port face. An asset without the annotation returns 0 → the original anchor-on-anchor behaviour, with no guessing. How to measure: take the outermost mesh extent along the `rf_out` axis and subtract the anchor coordinate (for this asset, 13.8 − 4.8 = 9.0). Test M6 in `ppgMounting.test.ts` verifies both "an annotated asset retreats" and "an unannotated one doesn't move".

✅ **Cables misaligned after editing anchor coordinates (2026-08-14)**: after moving the ZYSWA / ZHL port anchors from the seeder template values onto the measured connector faces, the cable ends plugged into them did not follow. Root cause: `resnapRfCablesLinkedTo` **only hangs off pose commit points** (`updateSceneObject` / `updateSceneObjects`), whereas editing an anchor is "the port moved but no SceneObject pose changed" → nothing triggered a recompute and the stored `rfCableNodes` stayed at the old port position. Measured error: RF_CABLE1.B → the amp's `rf_in` was off by **8.3 mm** (= the amp anchor's 47.2→55.5 shift); the switch's ends happened to be 0 only because the user had moved the switch afterwards and the pose commit incidentally triggered a re-snap. The fix: after a successful save in the Asset3D editor (and after `loadScene()`, so the new coordinates are published), find every object whose `primaryAsset` points at that asset and `resnapRfCablesLinkedTo` them. ⚠️ Editing anchors by hitting the API directly (a script) still bypasses the frontend, and afterwards needs one manual move or another asset save to trigger it.

✅ **The AOM's `rf_in` was a template placeholder, not a measurement (2026-08-14)**: the `RF_CABLE2.B ⛓ AOM0·rf_in` connector was buried entirely inside the AOM's housing. **The cable end was not miscalculated** — the field data matches to floating-point precision: node B relative to the AOM0 body = `(40.45, 0, 0)` = `rf_in(15,0,0)` + `25.45` (= the bound `sma male` asset's `|connect_in − connect_out|`), i.e. `applyLink` (`DigitalTwinViewer.tsx:3685`, already binding-aware with `connectorTipMmFromAnchors`) does place the male mating face exactly on the anchor.   - **Another landmine in the same area (fixed at the same time)**: the viewer's AOM drive loop (`DigitalTwinViewer.tsx:1594`) still read the legacy `comp.asset3dId` to get the asset → always null in a binding scene → `rf_in` was never found → every AOM hit `continue` → `aomOverrides` was permanently `{}`. ✅ **PPGs now attach directly, with no cable (2026-08-14)**: `createPpgAtPort` used to create a real rf_cable as the graph edge and then have the viewer force-hide it. Three problems: ① it was a first-class SceneObject — invisible yet selectable, deletable (taking the PPG with it) and permanently hideable beyond recovery; ② **the genders don't work** — a PPG's `rf_out` is `bnc_male` and all three catalog cables are male at both ends, so male-to-male: that cable physically cannot exist; ③ it contradicted the "a PPG plugs directly into the instrument" design.

  - **Four readers**: the frontend BFS's `readPpgAttachmentEdges` (`rfPropagation.ts`, merged into the same edge set as `readCables`), the backend's `_read_ppg_attachments` (`rf_resolve.py`, with `RfNode.ppg_attachment` fetched from `properties` by the loader), the RF Link panel's three memos `edges` / `occupiedPortKeys` / `cableByPortKey`, and `ppgMounting.findMatingPort`.   - **Deletion cascade**: `deleteObjects` now uses `ppgsAttachedTo` (the main instrument enters the doomed set → the PPGs plugged into it follow). ⚠️ The old cable-orphan test ("all cables on rf_out are doomed → delete the PPG") **must gain a `cables.length === 0 → continue` guard**, or a cable-less PPG reads as "all its cables are gone" and any unrelated deletion takes it too.
  - **Right-click Disconnect**: `cableByPortKey` maps both of a PPG's ends onto **the PPG's own id**, so the existing "remove" handler simply deletes the PPG — which is also exactly the only permitted PPG removal path.

✅ **The AOM's RF didn't follow the RF Link (2026-08-14)**: editing CH0's Freq/Vpp in the RF Link panel changed the numbers but moved the AOM's drive not at all. Root cause: `commitChannelEdit` wrote the edit into `PhysicsElement.kindParams.channels`, while the BFS's seed loop resolves in the order `dynamicSources` > the Asset's `defaultParams` > `kindParams`, and **the ad9959 asset carries `channels` itself** (`tunable_params = ["channels","fullScaleVpp"]`), so the asset layer always shadowed kindParams and nobody could read what had been written. ✅ **The `⚠ under` on the AOM row was a false alarm (2026-08-14)**: the RF Link panel labelled AOM0 "need ≥ 92.68 V ⚠ under" while the solver was actually running at η ≈ 0.82 (close to the 0.85 peak). Root cause: the panel computed the threshold with **its own old closed-form formula** (`aomRequiredPowerW`: `P = W·λ²/(2·M²·L²)`, using `figureOfMeritM2` / `acousticBeamWidthMm`) and **hard-coded 780 nm** for the wavelength; those parameters exist only in the PhysicsElement `kindParams`, which **the tracer never reads** (the anchor op looks only at the asset's `default_params` + `dynamic_sources`), and the formula isn't the datasheet model the tracer uses either. Hence "the panel says underdriven while it is in fact near full efficiency". The fix: that whole block now calls the shared functions in `optical/kinds/aom/physics.ts` (see §3), so the panel no longer computes physics itself. The field numbers: `P_peak(852.347 nm) = 2.2·(852.347/1100)² = 1.3209 W → 22.99 Vpp` (the old value said 92.68 Vpp) and `η = 0.8151 → displayed as 82%`, digit for digit identical to the backend's `first_order_efficiency`. **The general rule**: when a panel needs to display a physical quantity, call the kind's physics module — never write a second copy of the formula in a UI file, because it will drift from the solver and when it does the user only ever sees the UI's copy.
