# RF subsystem overview (source → cable → amp/switch → AOM)

> This file is **the index and panorama of the whole RF subsystem**. The details are spread across [cable.md](cable.md) (coax + RF graph propagation), [kinds.md](kinds.md) (the device registry / per-role contracts), [timing.md](timing.md) (PPG / TimingProgram) and [optics.md](optics.md) (the AOM Bragg drive). Read this first for the whole picture, then jump to the detail file you need.
>
> **The one-sentence mental model**: RF is **not ray tracing**; it is a BFS over a port adjacency graph. Each `rf_out` of a source seeds one signal, which travels along `rf_cable`s (transparent edges) through amplifiers (adding gain) and switches (routing by TTL) until it reaches the `rf_in` of an `aom` / `eom` (a sink) and becomes a Bragg / EO drive. The frontend's `rfPropagation.ts` and the backend's `rf_resolve.py` are **the same model and must stay at parity**.

---

## 1. Behavioural kinds (the RF "things")

Each kind uses a per-role anchor spec (`roles`, see [kinds.md](kinds.md)). The RF Link panel only accepts ports whose `domain ∈ {rf, ttl, trigger, rfout}`.

| kind | Role | RF role / domain | File |
|---|---|---|---|
| `rf_source` | DDS / synth, the emitting end | `rf_out` (multi-port CH0..CH3) `rf` | `kinds/rf_source/index.ts` |
| `rf_amplifier` | `rf_in → rf_out`, applying `gainDb` (clamped at `outputPowerMaxDbm`) | `rf_in`/`rf_out` `rf` | `kinds/rf_amplifier/index.ts` |
| `rf_switch` | A shared `rf_in` → N `rf_out`s (RF1/RF2…), routed by TTL | `rf_in`/`rf_out` `rf` + `ttl_in` `ttl` | `kinds/rf_switch/index.ts` |
| `programmable_pulse_generator` (PPG) | One `rf_out` gate (TTL/Trigger), bound to a TimingProgram | `rf_out` → `rfout` (a special case, see below) | `kinds/programmable_pulse_generator/index.ts` |
| `horn_antenna` | Transmit / receive antenna | sink/emitter | `kinds/horn_antenna/index.ts` |
| `rf_cable` | An **edge** of the graph (transparent, lossless) | `rf_in`/`rf_out` (derived from the spline) | `kinds/rf_cable/index.ts` |
| `rf_cable_connector` | Connector geometry (sma/bnc × male/female), passthrough | `connect_in`/`connect_out` (not primary) | `kinds/rf_cable_connector/index.ts` |
| `aom` / `eom` | `rf_in` is a **sink** → Bragg / EO drive | `rf_in` `rf` | `kinds/aom`, see [optics.md](optics.md) |

**Signal domains and compatibility rules** (`utils/rfLinkPorts.ts`): `RfLinkSignalDomain = "rf"|"ttl"|"trigger"|"rfout"`. `domainsAreCompatible` (`rfLinkPorts.ts:28`): the same domain always connects; `rfout` (a PPG output) is compatible with `ttl` and `trigger` but never crosses into analogue `rf`. **The PPG's `rf_out` special case**: `resolveRfLinkPortDomain` (`rfLinkPorts.ts:48`) maps it to `rfout`, so the `ttl` its role declares only affects the generic heuristics, not the connection type.

## 3. The RF Link panel (UI, `components/RfLinkPanel.tsx`)

Three columns bucketed automatically (source / transducer / sink); nodes are the RF-bearing SceneObjects and edges are each `rf_cable`'s `rfCableEndpoints.{A,B}`.

- **Where the nodes come from**: the `nodes` useMemo (`RfLinkPanel.tsx:825`) → `kindParticipatesInRfLink` (`rfLinkPorts.ts:114`) gates out non-RF kinds → `rfLinkPortsOf` (`RfLinkPanel.tsx:208`) derives the ports from the **asset's anchors**. The asset is resolved with `primaryAsset` (the binding tree, not `comp.asset3dId`). **When there genuinely is no asset** it falls back to `rfLinkRoleAnchors(kind)` (`rfLinkPorts.ts:134`), synthesizing ports from the role contract (displayed as "NO CONN" and not draggable). Detail in "Where the RF Link panel's nodes come from" in [cable.md](cable.md).
- **Per-port editing**: a DDS `rf_out` row can edit Freq/Vpp; an AOM `rf_in` shows the incoming signal plus **η%** (see below); an amp shows its gain and Vpp_in→Vpp_out. **Channels are both read and written through the ownership chain** (fixed 2026-08-14): display goes through `channelsByObjectId` (`RfLinkPanel.tsx:918`), resolving `dynamicSources` > the Asset's `defaultParams` > `kindParams`, and writes go through `updateSceneObject` into **`dynamicSources.channels`** (the same path as `Ad9959ObjectControls.updateChannel`). **Never write `kindParams`** — the ad9959 asset authors `channels` itself (and marks it tunable), the asset layer always beats kindParams, and the result is "the panel's numbers changed but propagation didn't", with the downstream AOM stuck on the asset's 80 MHz / 1.0 Vpp.
- **The AOM `rf_in` η readout shares the solver's source (fixed 2026-08-14)**: `aomDriveReadout` (`RfLinkPanel.tsx:344`) calls `diffractionEfficiency` / `rfPowerForPeakEfficiencyW` from `optical/kinds/aom/physics.ts` directly — the same datasheet model the tracer runs (`η = baseEfficiency·sin²((π/2)√(P/P_peak(λ)))·G(f)`, `P_peak(λ)=rfPowerForPeakW·(λ/peakRefWavelengthNm)²`). Three alignment points are all required: ① the **parameter layer** uses the asset's `defaultParams` + `dynamicSources` (what the tracer sees), not the PhysicsElement `kindParams`; ② the **wavelength** comes from the scene emitter's `centerWavelengthNm` (`sceneWavelengthNm`, falling back to a constant only with multiple wavelengths) — since `P_peak ∝ λ²`, 780 vs 852 differ by 19%; ③ **G(f)'s design centre** stays the AOM's own `centerFreqMhz` (passed as `designCenterFreqMhz`), or treating the carrier as the centre makes G ≡ 1 and detuning costs no efficiency. The badge is graded on `η / baseEfficiency` (<0.5 under, <0.9 off-peak, otherwise OK), because overdriving pushes past the sin² inflection so more power means *less* efficiency — something a Vpp threshold cannot express.
  - ⚠️ **② has drifted on the live bench (found 2026-09-22)**: `sceneWavelengthNm` (`RfLinkPanel.tsx:1140`) counts **every** `laser_source` and `tapered_amplifier`, so since the Sacher TA (nominal `centerWavelengthNm` 852) joined the 852.347 nm DBR, the set has two members and the badge is evaluated at the **780 nm** fallback — while the tracer's rays at the AOM stay at 852.347 (a seeded TA emits nothing of its own; `solver.solve_anchor_scene` only emits ASE from unseeded TAs). `P_peak` is then 1.11 W instead of 1.32 W. The backend readout (`aomDrives[*].eta`, §4) counts the emitters the way the tracer emits them and so reports the 852.347 value; the web badge has not been changed to match.
- **Dragging a connection**: pointer-dragging from a port dot calls `createRfCableBetweenPorts`, which since wave 3b is one `POST /api/v3/rf-cables/connect` plus the local store update — every rule and every millimetre of it is `flows.plan_connect`. Rules (the panel's drop gate, `RfLinkPanel.tsx:1525-1534`, transcribed as `flows.connect_gate`): different objects, opposite roles, the **same** signal domain, defined connectors on both, and a free drop target — the panel does not check the source port on pointer-down (`:1976`), though its cursor marks a busy one "not-allowed"; **the endpoint refuses both, so a drag out of a busy port now creates nothing instead of a second cable on it.** **Automatic cable-variant selection**: the two ports' own `connectorType` (`sma_*` / `bnc_*`) is matched against the three catalog cables (SMA-SMA / BNC-SMA / BNC-BNC), trying direct and reverse (A/B swapped); a cross-family SMA↔BNC uses the asymmetric `RF cable BNC SMA`. **Each end's family is derived from that end's bound connector asset** (`end_a` / `end_b` binding → the `rf_cable_connector` asset's `defaultParams.family`), **not** from the component's `properties.endAConnector` (which is empty on the catalog rows).
- **Right-click**: on an empty `ttl_in` / `trigger_in` → "Create Pulse & Timing here" spawns a PPG; on a connected port → "Disconnect cable".
- **The same flows, served (2026-09-22) and then CALLED (wave 3b)**: drag-to-connect, disconnect, the cable re-snap, the loose-end align and the PPG create / remove were ported to the backend as `POST /api/v3/rf-cables/*` and `POST /api/v3/ppg/*` for the qmem-blender add-on (shapes and error codes in [api.md](api.md); code `backend/app/optical/rf_cables/`), and the web now calls them and has deleted its copy — **one implementation, no parity to maintain**. The drop gate above (`RfLinkPanel.tsx:1525`) and `canSpawnPpgHere` (`:1910`) stay in the panel as the UI's own affordance (a drop target that lights up), but the decision is `flows.connect_gate` (`flows.py:150`) / `flows.ppg_gate` (`:498`), run over the same port list (`ports.panel_ports_of`, the transcription of `rfLinkPortsOf` + `rfLinkFallbackPorts`) and occupancy (`ports.occupied_port_keys` = `occupiedPortKeys`). `backend/tests/fixtures/rf_cables/` remains as the frozen golden the TypeScript wrote before it went, so a Python change still has to be a deliberate fixture update. What the port carries over, quirks included, is §7's last entries.
- Nodes are draggable and their positions are stored in localStorage.

## 4. The RF propagation BFS (the physics graph, frontend/backend parity)

**Frontend**: `buildRfPropagation` in `utils/rfPropagation.ts` (`rfPropagation.ts:440`); `rfPropagationSchedule.ts` precomputes one snapshot per timing section (`buildRfPropagationSchedule:84`), and scrubbing does an O(log N) lookup with `getRfSnapshotAt:114`.
**Backend (authoritative)**: `build_rf_propagation` in `backend/app/optical/rf_resolve.py` (:366); `load_rf_inputs` (:583) fetches the scene; `resolve_aom_rf_drive` (:695) → `hydrate_aom_rf_drive` (:764) resolves the signal arriving at an AOM's `rf_in` into `{aomFreqMhz, rfDrivePowerW=vpp²/(8·50Ω)}` and feeds it into the Bragg solution (`/api/v3/solver`).
**The readout endpoint (2026-09-22)**: `POST /api/v3/rf/propagation` (`backend/app/routers/v3_rf.py:109`, request/response shapes in [api.md](api.md)) returns the whole map — `signalAtPort`, `connectedPorts`, `ppgGateHighObjectIds`, the per-AOM `aomDrives` and the `sectionStartsNs` — for one `scrubTimeNs`, so a second client (the qmem-blender add-on) reads the backend's BFS instead of growing a third copy of `rfPropagation.ts`. Invariant: **the readout and the trace pick their snapshot in one place.** `rf_snapshot_at` (:674) is the snapshot rule (one snapshot per section start, plus the rest snapshot that `scrubTimeNs = null` selects), `aom_drives_from_snapshot` (:714) is the drive rule, and both `resolve_aom_rf_drive` (the solver) and `rf_readout_at` (:748, the endpoint) are just those two composed — so `aomDrives` equals, key for key, what the solver merged onto the AOM slots at that time. Pinned by `backend/tests/optical/test_rf_propagation_endpoint.py::test_aom_drives_equal_the_solver_path`, which calls the real `hydrate_aom_rf_drive`.
  - **`aomDrives[*].eta` (2026-09-22)** — what that drive buys: the on-Bragg first-order efficiency, computed by the AOM op's own `on_bragg_first_order_efficiency` (`anchor_ops/aom.py:139`, extracted from `aom_anchor_op` so both call one function) over the AOM slot as `load_anchor_scene_from_db` builds it at the same `scrubTimeNs` (`app/optical/aom_readout.py`). The one per-ray input, λ, is the scene's emitter wavelength (`scene_emitter_wavelength_nm`, `aom_readout.py:42`): the §3 rule — one wavelength, else 780 nm — over the emitters **as the tracer emits them** (laser sources via `emit_anchor_source_rays`; a TA's own wavelength only with no laser emission). So on the live bench it is 852.347 nm where the web badge currently uses 780 (§3). No per-order angle detune (only a trace knows the incidence). Pinned end to end by `backend/tests/optical/test_aom_readout.py::test_endpoint_eta_equals_what_the_tracer_applies` (a DB scene traced by `solve_anchor_scene`, the op's call spied — bit-identical).

- **Node asset/anchor resolution (the parity invariant)**: a node's "device asset" (which supplies the `rf_out` / `rf_in` anchors and specs such as `fullScaleVpp`) is obtained as **the single root binding with `targetKind="asset"` → that asset; otherwise the legacy `component.asset3dId`**. That is exactly the semantics of the frontend's `componentBindings.primaryAsset` (`componentBindings.ts:104`). Connectors and sub-assets are **children** of the binding tree and are **never** a node's primary asset. **Both sides must pick the primary by the same rule or the BFS desyncs** — which is now the case: the frontend's `buildAnchorsByObject` / `buildAssetParamsByObject` (`rfPropagation.ts:200/219`) call `primaryAsset`, and the backend's `load_rf_inputs` calls the corresponding `_primary_asset_id` (`rf_resolve.py`, aligned line for line with the frontend). **A parity subtlety**: `primaryAsset` does not honour `ObjectBinding.asset_3d_id_override` (its frontend signature does not even take objectBindings), so the backend deliberately doesn't either — both sides consistently use the root binding / legacy column.
- **Seed Vpp** = `amplitudeScale × fullScaleVpp` (both `fullScaleVpp` and `channels[]` are **asset coefficients**, overridable per instance through `dynamic_sources`).
- **Passthrough parameter ownership (fixed 2026-08-13)**: the parameters an amp's or switch's transfer sees are `dynamicSources` > the Asset's `defaultParams` > the PhysicsElement's `kindParams`, matching the ownership chain recorded in [object.md](object.md). Frontend `resolveElementParams` (`rfPropagation.ts:499`), backend `_resolved_params` (`rf_resolve.py:386`); all three of the TTL pre-pass's manual `ttlState`, the PPG's `restState` / `timingProgramId`, and the BFS's transfer calls go through it. (The Pulse & Timing rest pill reads and writes `restState` through the same chain since 2026-09-22 — it writes `dynamicSources.restState`, see [timing.md](timing.md).) **It previously read only `kindParams`**, so every switch/amp knob an asset author had written or a user had tuned per instance was ignored — most visibly, the `rf_switch` plugin declares `ttlState` tunable (writing it into `dynamicSources`) yet it could never be read, so manual TTL switching did nothing at all.
- Cables pass through transparently; an amp applies `gainDb` (exceeding `outputPowerMaxDbm` → `saturated`); a switch picks the path by TTL (a bound PPG's timing or a manual `ttlState`) plus insertion loss.
- **The PPG gate level = `inInterval XOR (restState === "HIGH")` (fixed 2026-08-14)**: a gate pre-pass computes every PPG's level across the scene first (frontend `rfPropagation.ts:528`, backend `rf_resolve.py:414`), and the TTL pre-pass is then just a lookup. Invariant: `restState` is **the level *outside* the drawn blocks**, so rest = HIGH turns the user's blocks into LOW pulses (negative logic); `idleRestMode` (scrub stopped) ignores intervals, which is the degenerate case of the XOR. A plugged-in PPG **always owns that line**, using its rest level even with no program bound (it used to fall through to the switch's manual `ttlState`). The contract is written down in `types/digitalTwin.ts` `ProgrammablePulseGeneratorParams.restState` and `schemas.py` `rest_state`.
- **Whether an AOM is RF-driven is topology, not the presence of a carrier**: only "something is plugged into `rf_in`" (`connectedPorts` / `connected_ports` = every port key in the adjacency table) hands control to the RF link; an AOM with nothing plugged in keeps the asset's rated operating point. Writing the test as "some timing section delivers a carrier" would make an AOM that is **wired but never receives a signal** (a switch parked on the other throw) look unwired, fall back to the rated drive, and draw a full set of sidebands with no RF at all.
- **First-arrival-wins, no superposition.**
- `/api/rf-chains` (`routers/rf_chains.py`, Phase RF.2) stores per-terminal RF chain **metadata**, **not** propagation truth — don't confuse it with the BFS.

## 5. RF cable geometry / rendering

A single object plus a per-instance spline (`rfCableNodes`). Each end binds one `rf_cable_connector` asset (the end_a/end_b bindings). Connector models: the device GLB (`sma_male` and friends) or the procedural fallback; `bakeConnectorByAnchors` (`three/loadAsset/connectorBake.ts`) puts `connect_out` on the spline node and `connect_in` at +tip. **Alignment**: `resolveLinkedRfCableEndpoint` (`utils/rfCableAnchorResolver.ts:248`) pushes the node back by the connector tip so `connect_in` lands on the target port. **The tip is derived from the anchors**, `connectorTipMmFromAnchors` (`rfCableAnchorResolver.ts:71` = `|connect_in − connect_out|`), not from hard-coded family constants (`RF_CONNECTOR_TIP_MM=15.5` / `RF_BNC=27` are only true of the procedural connectors). Full detail in [cable.md](cable.md).

## 6. Other related features

- **The Asset3D editor**: a per-anchor `connector_type` dropdown (the 4 gendered values), editable on unlocked rows (a `locked` row is entirely read-only). `components/Asset3DEditor.tsx`.
- **Pulse & Timing**: PPG ↔ TimingProgram is one-to-one; `rf_out` emits the TTL/Trigger gate; the channel index follows the ordering of the PPGs in the scene. See [timing.md](timing.md).
- **Instrument Power (removed 2026-08-24)**: the on/off panel and its solver gating (a powered-off source dropped its RF chain from the BFS; `RfInputs.powered_off`) were deleted. Sources/amps/switches are now always energised; the RF BFS no longer excludes anything on a power flag.

✅ **The two cascade quirks are fixed, now that there is one copy of the cascade (wave 3b, 2026-09-23)**: both were single-pass artefacts kept for parity while the TypeScript existed. `flows.plan_delete_objects` now runs its three passes **to a fixpoint** — repeat {linked cables, attached PPGs, orphaned legacy PPGs} until none of them adds anything, which converges because the doomed set only grows. Each pass still walks the scene in order, so the DELETE order stays deterministic.
  - **A PPG that is attached AND still wired by an rf_cable** used to go with its host while the cable on its `rf_out` stayed behind, dangling: the cable pass ran before the attached PPGs were added, so the cable never saw its PPG doomed. Now the next round catches it. (PPGs are either attached — since 2026-08-14 — or legacy, so this needs a hand-made scene; it is fixed because "delete leaves a cable pointing at a row that is gone" is never the answer anyone wants.)
  - **A cable whose end names another cable** was caught only if the scene listed the target cable first.
