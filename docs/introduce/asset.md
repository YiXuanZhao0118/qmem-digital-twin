# Asset3D — the geometry + physics ground-truth layer

> Layer 1 of the [core data model](data-model.md). Related: [anchors.md](anchors.md) (anchor annotation), [kinds.md](kinds.md) (per-kind physics parameters), [rendering.md](rendering.md) (how it is rendered).

**Asset3D** — a reusable 3D model plus its physics defaults. DB table `assets_3d`, storing: `file_path` (.glb/.stl, `filePath` in the API; older docs called it geometryRef), `kind_id` (**NOT NULL, migration 0111**; defaults to `unclassified`, so there is no "no kind" state), `device_id` (**nullable, migration 0118**; holds a `devices.slug` — the device registry became a DB table in migration 0123 — when set, the anchors are a materialized view of the device template and kind_id is written through from the device's behavioralKind, see the device section of [kinds.md](kinds.md)), `anchors[]` (optical interfaces: each anchor carries a direction and an aperture), `default_params` (that part's intrinsic physics, e.g. the focal length of one particular Thorlabs lens), `wavelength_range_nm`, and `properties.viewerHints`. **Physics defaults exist only here.**

## Related concepts

- **anchors[]** — replaces the old `faces[]` / `transitions[]`: each anchor is itself an optical interface carrying its own **direction** (tri-axis) and **aperture**. Structure and tracer usage in [anchors.md](anchors.md).
- **defaultParams** — the representative physics defaults per kind (laser 780.241 nm / 50 mW, AOM v = 4200 m/s, …) are listed in [kinds.md](kinds.md).
- **tunableParams** (migration 0113) — the asset author's marking of which top-level defaultParams keys may be tuned per instance (the checkbox after each param in the PHY Editor). Only checked keys show up in the SceneObject's per-instance editor, with values stored in `SceneObject.dynamic_sources`; every other coefficient is decided purely by the Asset. The seed default comes from the kind's `state_param_keys`.
- **Editing defaultParams: strictly by the KIND schema (same as for objects)** — the Asset3DEditor's defaultParams is **no longer free-form JSON**: when the kind has an editable scalar schema (lens / mirror / polarizer / laser_source, …) it renders **structured fields** (`DefaultParamsKindFields`, `Asset3DEditor.tsx`) and the user can only set **parameters the kind defines** — mistyping a key (`focalMm`, `transmission`) is now impossible. It renders **recursively** (`ParamTree`): a scalar gets one input, nested objects/arrays expand down to every leaf (number/string/bool) labelled by dotted path (`spatialModeX.waistUm`, `spectrum.components.0.fwhmMhz`), so a mostly-nested kind like laser_source shows all of its parameters (rather than only 5 scalars). Arrays cannot be grown or shrunk — only existing leaves are edited. Leaf edits go through `setLeafInParams` (a strict clone keeping only kind keys, with missing required ones filled from kind defaults). On save, `toAssetUpdate` uses `strictDefaultParamsForKind` to **drop every top-level key the kind does not declare** (nested structure is preserved; a kind with an empty schema keeps the free textarea so nothing is deleted by accident). (The old "Kind definitions" reference panel `KindGuidePanel` / `KIND_GUIDES` — which still described the retired faces/transitions — has been removed.)
  - **Required vs optional parameters**: a kind's `physics.defaultParams` are required (always written, seeded from the kind defaults); `physics.optionalParams` (added in `_plugin.ts`, **frontend-only, not in the manifest**) are opt-in: the structured form renders **blank fields**, where leaving one blank means omitted and filling it means written — the *absence* itself is meaningful. The classic case is the lens: required = `focalLengthMm` + `transmittance` (what the op actually reads, `backend/app/optical/anchor_ops/lens.py:167,109`); optional thick-lens geometry = `radiusFrontMm` / `refractiveIndex` / `centerThicknessMm` (+ `radiusBackMm`) — **leave all three of `radiusFrontMm` + `refractiveIndex` + `centerThicknessMm` blank and you get the thin-lens approximation (focus at nominal f); fill them all and it switches to the exact thick-lens ABCD (focus at back-vertex + BFL, the op's `_is_thick`)**. A blank `radiusBackMm` means a flat back (a true plano-convex); a value means a curved back, used for aspheres represented as a fitted thick-lens equivalent (e.g. the A230TM-B: `radiusFrontMm=2.3244` / `radiusBackMm=10.308` / `refractiveIndex=1.59` / `centerThicknessMm=2.75` → EFL 4.51 mm, see [optics.md](optics.md)). optionalParams are not seeded into the asset and do not pollute the object's coefficient baseline, so a plano-convex still defaults to the generic thin lens and only gains accuracy when you fill in R/n/d for that particular one (the BeamScope's q / focus reflects the difference).
- **wavelengthRangeNm (invariant: on an asset it lives only in the `wavelength_range_nm` column, never in asset.defaultParams)** — edited through the Asset3DEditor's lambda min/max fields; on save the column is authoritative (`toAssetUpdate` builds it from the lambda fields and v3_catalog writes `row.wavelength_range_nm`), and the v3 anchor tracer reads only that column, never defaultParams. **The KIND template** still declares `wavelengthRangeNm` (the optical-kinds spec invariant requires it on every non-emitter optical kind, and the legacy PhysicsElement seed reads it, `components.py:667`), but the asset side excludes it everywhere: both `kindScalarParamKeys` and `kindAllParamKeys` strip it → it isn't shown as a structured field and strict-save drops it; kind seeding (`Asset3DEditor.tsx:~2397`) pours the value into the lambda fields rather than the defaultParams JSON; and `draftFromAsset` (`Asset3DEditor.tsx:~280`) lifts any legacy `wavelengthRangeNm` left in defaultParams up into the lambda fields and strips it from the JSON when the row is opened.
- **The ASSET3D preview's coordinate frame (Z-up) and the rotation of procedural assets** — the editor viewport rotates the grid onto the X–Y plane (`Asset3DEditor.tsx:1677`), i.e. **Z-up**, with contents in raw body-local mm. But the **procedural** renderers (`photoRoom.ts` and friends) are written against the main viewport's **Y-up ÷100** frame, so loading them into the editor requires **×100 and `rotation.x = +π/2`** (`buildProceduralFaceLocatorModel`, `Asset3DEditor.tsx:783-784`). Invariant: any preview branch that goes through a procedural builder must apply this rotation, or the model "stands up" in the editor. The `optical_table` branch (`Asset3DEditor.tsx:~1973`) once missed the rotation and keyed off `kindId` (which would override an asset already baked to GLB); it now only takes the procedural-table path when `filePath === "primitive://table"` and applies the rotation, with everything else going through normal file loading. The COMPONENT preview (`ComponentsEditor.tsx:~2647`) still uses the old formulation.
- **catalog_id is the ticket into the BUILD list** — `GET /api/v3/assets3d` defaults to `has_v3=true` and returns only rows whose `catalog_id` is non-NULL (`v3_catalog.py:120`), and BUILD's add/edit dropdown filters again on `Boolean(a.catalogId)` (`GeometryBuilder.tsx:1129`, since saving keys on catalog_id). **An asset with a NULL catalog_id is completely invisible in BUILD** (ASSET3D still shows it — that view keys on the row UUID). This is exactly how `optical_table` disappeared; the slug `optical_table` was added back on 2026-08-14.
- **Anchor authority-level badges (2026-08-17)** — under the `anchor_id` of each row in the anchor table sit two badges, `pos` and `axis`: `●` device (values authorized by the device template, good for 1 µm / 0.1 µrad) / `◐` overridden (the template declares it but a face-pick or a typed value has overridden it) / `○` geometry (no template declaration; face-pick is limited to ~mrad by mesh triangulation). The level is derived live by `gradeAnchor` (`Asset3DEditor.tsx`) comparing the draft against the template from `deviceById(asset.deviceId)` — it is **not stored in the DB and changes no schema**; matching is anchor `id` ↔ template `role` (with `name` disambiguating repeated roles). Display only; it never blocks a save. Background and numbers in [../float64-audit.md](../float64-audit.md) §2.2.
- **viewerHints** — drives geometry filtering (`includeOnlyCentroids`, `deletedCentroids`, `recenterOrigin`); how the render side consumes it is in [rendering.md](rendering.md).
- **LOD tiers live in a sidecar table, not on this row (alembic 0122)** — `asset_lods` holds one row per (asset, level 0/1/2) with `file_path` / `tri_count` / `byte_size` / `error_mm` / `hints_digest`, surfaced read-only as `Asset3DV3Out.lods[]`. It is a separate table **because of `locked`**: most catalog assets are frozen and `lock_guard` 422s any non-`locked` write to `assets_3d`, so storing the manifest in `properties` would make regenerating a derived render artifact require a human unlock. Level 0's `file_path` mirrors this row's `file_path`, and both geometry-writing routes delete the LOD rows so tiers can never outlive their source mesh. Generation and the switching rule are in [rendering.md](rendering.md); budgets in [../objectives.md](../objectives.md) §R-4/R-5.
- **locked (freeze flag, alembic 0112)** — `assets_3d.locked` (BOOLEAN NOT NULL DEFAULT false) = a human has confirmed this asset is "complete, not to be adjusted". Each row in the Asset3DEditor list has a lock button on the right; once locked, Save/Delete are disabled and the whole form goes read-only (`pointerEvents:none`). On the backend, `PUT /api/v3/assets3d/{key}`, `PUT /api/assets/{id}` and the deletes return **422** for any change to a non-`locked` field of a locked row (`backend/app/lock_guard.py`); only a request that toggles `locked` alone (unlocking) is allowed. The same flag on kinds is covered in [kinds.md](kinds.md). **AI rule (see [CLAUDE.md](../../CLAUDE.md)): never modify or delete a locked asset — ask the user to unlock it first.**
