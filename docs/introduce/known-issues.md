- **Legacy laser-beam data lives in two places (properties.opticalSources[0].beam + the dynamic_sources column)**: both still hold a whole beam (`spectrum` / `spatialEnvelope` / …). **Migration 0113 largely defused this**: after `db_scene_loader` reads both places for the v3 trace, it **drops any key that is a defaultParams key but not Asset-tunable** (the tunable contract, see [data-model.md](data-model.md)). So non-tunable beam parameters (spectrum / spatialEnvelope / polarization / waist) **always track the Asset** and can no longer desync from leftover data; only the tunable `nominalPowerMw` / `centerWavelengthNm` are per-instance. The display-side `physics_elements.kindParams` (never persisted, derived live) still prefers the `dynamic_sources` column via `bindings.get_laser_beam_for_kind_params`, so "display" and "trace" can in theory still disagree on non-tunable parameters — but the trace side is now Asset-authoritative. See [optics.md](optics.md) and the auto-memory `laser_beam_dual_source_astigmatism`.
- **`uvicorn --reload` intermittently drops an edit (2026-08-20)**: the reloader writes `WARNING: WatchFiles detected changes in '<file>'. Reloading...` to `.claude-runtime/backend.err` and then **never finishes** — no `Started server process` line follows it — so the OLD process keeps serving :8010 and every HTTP call runs stale code. It is intermittent: earlier edits in the same session reloaded fine. **Symptom**: a backend change whose pytest passes has no effect through the API. **Diagnosis**: run the same solver **in-process** (`load_anchor_scene_from_db` → `solve_anchor_scene` with the venv python) and compare against `POST /api/v3/solver/run-from-db`; if they disagree, the server is stale, not the code — that is how the `laser_source` `main.visible` gate was cleared (in-process 15 lab segments vs 23 over HTTP). **Fix**: `.claude/skills/start-project/scripts/restart-stack.ps1 -Mode restart` — `restart-backend.ps1` sweeps the workers but then aborts on the parent's socket still owning :8010. Note `.claude/` is gitignored, so that script is machine-local, not part of the repo. See [overview.md](overview.md).
- ~~**A fibre rendered at the origin instead of at its endpoints.**~~ **Fixed 2026-08-21.** `createFiberSplineObject` reads only `SceneObject.properties.fiberNodes` then `Component.properties.fiberNodes`, and falls back to a hard-coded **0→300 mm** straight run when it finds neither — but a freshly instantiated patch cable keeps its endpoints ONLY in the fibre PhysicsElement's `kindParams.endA/endB` (what Align End A/B writes and what the backend's `_synth_fiber_slot` traces), and **nothing writes `properties.fiberNodes` until a node is edited**. So every un-edited cable was drawn at the object origin: one whose ends were at x −659…−890 rendered at 0…300, a metre away, which reads in the viewer as "the model doesn't show up". The PHY Editor COMPONENT preview looked correct throughout because it deliberately draws the catalog shape, which is what made it look like a viewer-only problem. `bindingRendererGate.buildSceneObjectFromBindings` now rebuilds the spline from the PE when neither cache has ≥2 nodes, mirroring the precedence in `sceneStore.resolveEffectiveFiberNodes` that every fibre-endpoint EDITOR already went through — the render path had simply never been pointed at it. Regression test: `three/__tests__/bindingRendererGate.fiberSpline.test.ts`.
- ~~**Every catalog placement landed on the identical point.**~~ **Fixed 2026-08-21.** `sceneStore.cursorSpawnPatch` spread `nextObjectOffset(count)` and then overwrote its x/y/z with the raw transform cursor — computing a per-placement fan and discarding it. Six patch cables placed in a row from the parts library therefore sat on one coordinate, overlapping perfectly and reading as a single cable; combined with a cursor parked off the table it looks exactly like "the models don't render". Now fanned ±80 mm around the cursor.
- ~~**A fibre Component with TWO SceneObjects silently edits the wrong cable.**~~ **Fixed 2026-08-21.** Fibre node editing was keyed on **componentId** — `enterFiberEdit(componentId)`, and `updateFiberNodes` / `insertFiberNode` / `removeFiberNode` each resolved their target with `objects.find((o) => o.componentId === componentId)`, i.e. the FIRST match — so two patch cords instantiated from one catalog Component shared an edit target and the second could not be shaped at all. **The parts library reproduced it through normal use**: `AssetLibraryPanel`'s **+** calls `ensureObjectForComponent(componentId)`, which rejects `rf_cable` / `sma_cable` / `programmable_pulse_generator` outright but happily places a **second** `fiber` object on the same catalog Component. Observed live that day on `Fiber PM PC-APC` (`FIBER0` + `FIBER1`) and `Fiber PM APC` (`FIBER1` + `FIBER2`); the earlier `FIBER_IN` / `FIBER_OUT` collision was worked around by cloning the Component per cable, which is no longer necessary. The fix is the one this entry recommended — key the edit on objectId the way `rf_cable` already does — applied across all three layers that could each pick the wrong cable (store actions, the viewer gizmo's wrapper lookup, and the five Object-panel fibre editors). See [fiber.md](fiber.md) for the invariant and `store/__tests__/fiberNodesPerObject.test.ts` for the regression test.
