# RF cable — coax (single object + per-instance spline)

> **The panoramic index is [rf.md](rf.md)** (the whole RF subsystem). Related: [timing.md](timing.md) (the RF chain AD9959→amp→switch→AOM), [optics.md](optics.md) (the RF tracer + AOM coupling), [anchors.md](anchors.md) (endpoint anchors are derived from the spline), [kinds.md](kinds.md) (rf_cable), [fiber.md](fiber.md) (fibre uses **the same** spline/endpoint architecture).
> Code: `three/loadAsset/rf_cable/`, `utils/rfCable{AnchorResolver,Alignment}.ts`, `utils/rfPropagation.ts`, backend `optical/rf_resolve.py`.

## Data model + endpoint links

One cable = **one SceneObject** with two RF ports, `rf_in` (A) / `rf_out` (B). The architecture parallels [fiber.md](fiber.md) (they share `FiberNode` + `buildFiberCurvePath`), but the data lives elsewhere:

- **The spline**: `SceneObject.properties.rfCableNodes` (a `FiberNode[]`, each with `handleInMm` / `handleOutMm`). With none, a 2-node straight line is generated (`createSmaShortCable` reads `component.properties.lengthMm`, **falling back to 150**; the kind's `default_params.lengthMm` is 152 — the two defaults disagree, but it only shows when there is no spline at all).
- **Once there is a spline, `lengthMm` no longer describes the cable**: after the user drags a node the real length is the Bezier arc length (`cableSplineLengthMm(nodes)`, `three/loadAsset/fiber/curve.ts`, measuring the same `CurvePath` the `TubeGeometry` uses, excluding the connector tips). The RF Link panel's label uses this value (see "Known issues / cautions").
- **Endpoint links**: `SceneObject.properties.rfCableEndpoints = { A, B }`, each an `RfCableEndpointLink { targetObjectId, targetAnchorId("rf_in"/"rf_out"), targetAnchorName(e.g. "CH0") }` — pinning one end to another component's RF port. Male-female mating: the cable's outward is **antiparallel** to the target's outward.

## Anchor derivation (`utils/rfCableAnchorResolver.ts`)

Anchors are marked `derivedFromRfCableEndpoint = "A"|"B"`:
- Position = the spline endpoint plus the connector tip offset (`RF_CONNECTOR_TIP_MM = 15.5` for SMA / `RF_BNC_CONNECTOR_TIP_MM = 27` for BNC).
- Direction = the spline's outward tangent.
- With no spline it falls back to the static `positionMmBodyLocal` / `directionBodyLocal` (default +X).
- `resolveLinkedRfCableEndpoint()` mates one end's node to the target port's lab pose; `nodeOffset{depthMm,sideXMm,sideYMm}` allows manual fine-tuning.

## Rendering (`three/loadAsset/rf_cable/`)

`createSmaCableSpline()` (`cable_spline.ts`): Bezier path → `TubeGeometry` (radius 1.6 mm, RG-316 coax); both ends get an **SMA / BNC** connector according to `properties.endAConnector` / `endBConnector` (or the `connectorType` fallback), with `+X` mated to the outward tangent. Connector geometry goes through `buildRfConnectorGroup()` in `connectorModels.ts`: a cached real model when the catalog has one, otherwise the procedural `sma_male_connector.ts` / `bnc_male_connector.ts`. `refreshRfCableWrapperGeometry()` updates in place when a node is dragged or a linked endpoint moves.

**The real-model connector resolver (`setRfConnectorAssetResolver()`)** maps a connector kind (e.g. `bnc_male`) onto a catalog Asset3D (first trying the slug `bnc_male` — the GLB the user uploaded — then `rf_connector_<kind>`; a `primitive://` row has no loadable mesh → returns null and falls back to procedural). Once loaded, `bakeConnectorByAnchors()` in `connectorBake.ts` bakes it: rotating the asset's `connect_out`→`connect_in` axis onto the target axis +X and moving `connect_out` to the origin (only without those two anchors does it fall back to the "rotate the longest bbox axis onto +X" heuristic). **The resolver is a module-global singleton that every viewer drawing cables must register for itself**: Lab does it in `DigitalTwinViewer.tsx`, the PHY Editor's COMPONENT preview in `ComponentsEditor.tsx` (`ComponentPreview3D`) — because the PHY Editor takes over the whole page, Lab unmounts and nulls the resolver, so without that registration the preview only draws procedural connectors, whose **shape disagrees** with the real GLB seen in ASSET3D / Lab. When the asynchronous load finishes, `subscribeRfConnectorLoaded()` notifies the preview to rebuild (`connectorEpoch` is in the scene effect's deps) and swap in the real model. Real-model meshes are wrapped by `geometryToColoredMesh(geom, THREE.DoubleSide)` — **DoubleSide** to match the ASSET3D editor (which also forces `material.side=DoubleSide`), so reversed faces in a CAD export aren't culled by FrontSide and made to look broken or blurry.

**Swapped the mesh but Object Sense still shows the old one?** Usually **iOS bfcache**: the phone restored the tab from memory without re-running JS, so the catalog store is frozen on the old `file_path`. The `pageshow` listener in `App.tsx` (`event.persisted`) forces a `location.reload()` on a bfcache restore so everything is refetched; an incognito tab is immune to bfcache and can be used to verify the data really is fresh. Fibre connectors use the same machinery (`fiberConnectorModels.ts` + `subscribeFiberConnectorLoaded()`), see [fiber.md](fiber.md).

**Connectors look low-detail (the procedural fallback) on first entry and only become complete after visiting ASSET3D and coming back?** (The real root cause, proven on 2026-06-13 with a headless preview network trace.) `useV3Catalog.fetchAll()` **used to be called only inside Asset3DEditor** — Lab (DigitalTwinViewer) and the COMPONENT preview never loaded the catalog. So a freshly opened app landing on Lab had an empty catalog store, the connector resolver's `getAssetsByKind("fiber_connector")` returned `[]` → no match → the procedural fallback was drawn, **and never retried** (no GLB load was kicked off, so no connector-loaded bump). Only visiting ASSET3D ran fetchAll and filled the catalog, so coming back finally matched and loaded the real GLB. The evidence: Lab's network fetched `/api/scene`, `/api/coils`, … but **never `/api/v3/assets3d`**, and never `sm_pc_780.glb`. The fix: (1) `App.tsx` calls `useV3Catalog.getState().fetchAll()` at startup; (2) DigitalTwinViewer and `ComponentPreview3D` subscribe to `useV3Catalog(s=>s.assets.length)` and bump `connectorEpoch` when it goes above 0, so cables drawn before the catalog arrived re-resolve their connectors. `THREE.Cache.enabled = true` (main.tsx) is just an incidental performance win (avoiding a refetch on every view switch), not the fix for this bug.

**Edited a connector asset (re-uploaded the GLB / changed an anchor) but Object Sense + COMPONENT still show the old mesh until you visit ASSET3D and come back?** The geomCache key is the connector kind / catalogId, **neither of which changes on a re-upload or an anchor edit**, so `loadConnector` / `loadFiberConnector` hit the stale cache, early-return, and keep serving the old bake — only a viewer unmount (switching to the ASSET3D tab) triggers `setResolver(null)` and clears it. `App.tsx` subscribes to `useV3Catalog` and calls `invalidateRfConnectorCache()` / `invalidateFiberConnectorCache()` whenever the `assets` array changes: that empties geomCache and fires the load listeners, so the mounted viewer bumps `connectorEpoch` → rebuilds → refetches into the empty cache → picks up the new mesh, with no manual tab dance.

## Alignment (`utils/rfCableAlignment.ts`)

`findRfCableEndpointAlignmentCandidates()`: find every RF port anchor within `toleranceMm` (25 mm) — any object's `rf_in` / `rf_out` — sorted by distance; one candidate snaps automatically, several (e.g. AD9959 CH0..CH3) raise a picker. `align_variant: none` (no free-drag alignment as optical parts have).

## RF physics: a cable is **an edge of the graph** (transparent)

RF is **not ray tracing**; it is a BFS over a port-adjacency graph (`utils/rfPropagation.ts` on the frontend, `optical/rf_resolve.py` on the backend, the same model on both sides).

- A cable is an **edge** in that graph: `rfCableEndpoints.A ↔ B`, joining two target ports. It is **currently transparent** (Phase RF.1: no dB/m, no frequency-dependent loss) — an `RfSignalState` passes through untouched.
- By contrast: `rf_amplifier` applies `gainDb` (clamped at `outputPowerMaxDbm`; exceeding it sets `saturated=true`); `rf_switch` picks the path by TTL (either a bound PPG's timing or a manual `ttlState`) and adds insertion loss.
- The chain: `rf_source` (each `rf_out` on the AD9959 = one CH seeding a signal) → cable → amplifier → cable → switch → cable → **the AOM's `rf_in` (a sink)**. `RfSignalState` carries `frequencyMhz`, `vpp`, `cumulativeGainDb`, `passthroughObjectIds` and `saturated`. At the AOM end, the backend's `resolve_aom_rf_drive()` resolves `{aomFreqMhz, rfDrivePowerW=vpp²/(8·50Ω)}` and feeds it into the Bragg solution.
- **Seed Vpp = `amplitudeScale × fullScaleVpp`**. `fullScaleVpp` and **`channels[]` are both asset coefficients** (`Asset3D.default_params`, the authoritative truth; a missing fullScaleVpp falls back to `AD9959_VPP_FULL_SCALE=1.0`), overridable per instance through `SceneObject.dynamic_sources` (they must be in the asset's `tunable_params`, which defaults to `["channels","fullScaleVpp"]`) — **the same model as optical assets**. Channel resolution chain: `dynamic_sources.channels` → `asset.default_params.channels` → the old `PhysicsElement.kindParams.channels` (legacy fallback). The AD9959 panel's (`Ad9959ObjectControls`) per-channel editing writes `dynamicSources.channels` (no longer kindParams); the chip-level PLL / refClock / sync / serial settings are still in kindParams. Both seed loops share the model (`rf_resolve.py`'s `RfNode.asset_params` / `dynamic_sources` ⇄ `rfPropagation.ts`'s `buildAssetParamsByObject`).
- The BFS is first-arrival-wins (no superposition). `/api/rf-chains/nodes` (`routers/rf_chains.py`) stores per-terminal RF chain metadata, not propagation truth.

## The kind

`rf_cable` (`primary_domain: rf`): anchors `rf_in` / `rf_out` (direction required, aperture not), `default_params.lengthMm = 152`, `align_variant: none`.

## Known issues / cautions

- **Where the RF Link panel's nodes come from (asset resolution goes through the binding tree)**: `RfLinkPanel.tsx` derives each node's ports from that object's `Asset3D.anchors` via `rfLinkPortsOf`, and the asset is resolved by **`primaryAsset(component, scene)` (`utils/componentBindings.ts`)** — first the root ComponentBinding with `targetKind="asset"`, then the legacy `component.asset3dId`. **In a binding-backed scene `component.asset3dId` is always null and the asset hangs off a binding**, so the panel's earlier direct read of `asset3dId` found no anchors for RF objects that do have an asset → blank nodes / "NO CONN" (fixed).
- **The fallback when there genuinely is no asset**: only when `primaryAsset` still resolves nothing (no binding and no legacy column) does it fall back to `rfLinkRoleAnchors(kind)`, synthesizing ports from the kind's `roles` contract so a bare RF object still shows as a node instead of being silently dropped. The cost: a synthesized port has `connectorFamily=null` (it displays "NO CONN" and `onPointerDown` early-returns, so no cable can be dragged), and multi-port roles collapse into one generic port (CH names and counts live on the asset) — full cable connectivity requires attaching an asset that carries `connectorType`.
- **Port direction reads axisX, not the legacy `directionBodyLocal`**: the outward normal used for cable alignment must come from `anchorObjectLocalPrimaryDir` (axisX → falling back to the legacy `directionBodyLocal`, `utils/anchorAccess.ts`). A device-materialized anchor **carries only `axisXBodyLocal`, with `directionBodyLocal` null**, so the earlier direct read of `anchor.directionBodyLocal` in `resolvePort` / `findRfCableAlignmentCandidates` fell back to the default `+X` → any port whose face normal isn't +X (e.g. the ad9959's CH0 facing `+Z`) had its connector rotated 90° and "wouldn't mate". The renderer and the Debug-anchors overlay always used axisX and so drew it correctly; the connection code just hadn't been aligned onto the same source. **Note that the Debug-anchors overlay deliberately skips `rf_cable` / `sma_cable`** (`DigitalTwinViewer.tsx` ~L4410: a cable's connector position comes from spline nodes, not static asset anchors, so drawing them would mislead) — which is why you can see the ad9959's directions but not the cable's.
- **Making a connection is binding-aware too**: `sceneStore.createRfCableBetweenPorts` (which drags out a cable; internally `resolvePort`) and `findRfCableAlignmentCandidates` (which snaps a cable endpoint) also resolve their asset through `primaryAsset` — previously they read `comp.asset3dId` directly (always null in a binding scene), which made `resolvePort` return null and the drag a silent no-op (ports visible in the panel, yet no cable could be created). **Note this is not unified yet**: the RF propagation display path (`rfPropagation.ts` / `rfPropagationSchedule.ts` / `ppgMounting.ts` / `aomRfDrive.ts`) still reads `comp.asset3dId` directly, so in a binding scene the panel's signal-flow animation and the AOM's upstream readout may be empty; fixing it means threading `componentBindings` into those builders while keeping parity with the backend's `rf_resolve.py` BFS.
- **The RF Link panel's length label = the actual spline arc length (fixed 2026-08-14)**: `RfEdge.lengthMm` in `RfLinkPanel.tsx` used to read `PhysicsElement.kindParams.lengthMm` (the catalog constant 152) directly, so any cable that had ever been dragged was labelled 152 mm — the live scene's RF_CABLE2 is actually 780 mm and displayed 152. It now uses `cableSplineLengthMm(properties.rfCableNodes)` (falling back to nominal only when there is no spline, which is exactly when the renderer draws a straight line); the nominal value moved into a `<title>` tooltip, handy for checking "which part number this cable should be". **The connector tips are not counted** (a tip lies beyond the end node and depends on the connector asset). Unit tests: `three/loadAsset/fiber/__tests__/curveLength.test.ts`.
- **Cables currently have zero loss and zero gain** (transparent); impedance, per-length loss and frequency curves are future fields. Length is now geometric truth, so a future dB/m or propagation delay should use it, not `lengthMm`.
- **No superposition**: when two sources feed the same port, the BFS keeps only the first to arrive.
- `RF_LOAD_Z = 50Ω` is hard-coded. **The connector tip offset is now derived from the connector asset's anchors** (`connectorTipMmFromAnchors` = `|connect_in − connect_out|`, `utils/rfCableAnchorResolver.ts`): `bakeConnectorByAnchors` puts connect_out on the spline node and connect_in at +tip, so during alignment the node must be pushed back by exactly that distance for **connect_in to land on the target port**. The hard-coded `connectorTipMmForFamily` (SMA 15.5 / BNC 27) is only true of the *procedurally generated* connectors; imported device GLBs differ (sma_male measures 25.45, bnc_male 43.5) → the old code overshot connect_in by ~10 mm (SMA) / ~16.5 mm (BNC). Both cable creation on connect (`createRfCableBetweenPorts`) and the viewer's live re-align now read the bound connector asset's anchors. **Note**: the cable's own derived RF port anchor (`resolveRfCableAnchorPosition`) still uses the hard-coded `RF_CONNECTOR_TIP_MM`, so that port marker sits short of connect_in by the tip difference; and the viewer's `applyLink` still has the `targetComp.asset3dId` binding blind spot (it early-returns in a binding scene and relies on the nodes stored at connect time).
- The spline lives in `properties` (there is no catalog default); older scenes may have no `rfCableNodes`, and newly created cables get an automatic 2-node straight line.
- The frontend and backend BFS must stay at parity (a schema change has to be made on both sides).
