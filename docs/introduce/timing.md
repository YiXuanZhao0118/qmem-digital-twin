# Time-domain simulation

> The (steady-state) RF tracer is in [optics.md](optics.md); the multiphysics modules in [multiphysics.md](multiphysics.md).

**The design premise**: time is a first-class coordinate. One "experiment run" is a trace of time evolution, not a steady-state snapshot.
- **Sequence timeline**: a Sequence = a list of Events `(t, channel, action, params)` (channel is a dotted path such as `AOM_001.rf_amplitude`; action is one of set/ramp/pulse_gate/trigger/wait/barrier). Between events each module evolves forward on its own, and cross-physics state is exchanged at event boundaries. **Steady state is the special case of an empty Sequence** (no Sequence → the existing CW evaluator runs, so nothing breaks).
- **Per-module time grids**: optical envelope (ps–100 ns sampling), RF phasor, quantum ρ(t) density matrix, thermal T(t,x), vacuum P(t) — because a single global dt is not workable. RWA/SVEA approximations are used.
- **Schema**: `PulseEnvelope` / `RFSignal` / `QuantumTrace` / `ScalarTrace` plus the `Sequence` / `SequenceEvent` tables; each kind gains optional dispersion parameters (gvdFs2, groupDelayPs, riseTimeNs, …).
- **PhysicsModule protocol**: `steady_state(scene)` + `evolve(scene, t0, t1, controls, state_in)`. The optical primitives are designed as `propagate_envelope` (split-step Fourier for GVD/TOD), `angular_spectrum_propagate` and `fiber_overlap`. `propagate_envelope` was once implemented in `optical_solver` (verified against textbook results to <0.5%), but **that file was deleted when the legacy path retired, taking the dispersion time-domain math with it (recoverable from git)**.
- **Status**: the trace schemas and optional dispersion parameters are still there; the CW path is a no-op, so there was no regression. The time-domain primitives such as `propagate_envelope` are **waiting to be reconnected** (see [known-issues.md](known-issues.md)). Later phases (quantum Lindblad, thermal ODE, timeline UI) are unfinished.

## Scrub time / timing programs / AD9959

- **Scrub time** (`ScrubTimeBar.tsx`): scene state is a function of time t.
- **TimingProgram**: a top-level row (own `id`), owned 1:1 by a PPG through `kindParams.timingProgramId`. Its `intervals` is a JSONB list of `{spinCoreStartNs, spinCoreEndNs}` HIGH windows (`[start, end)`, snapped to the 10 ns grid); the rest of the timeline is the PPG's rest level. (The older per-SceneObject `TimingBlock` list with `waveform_kind` was removed in alembic 0045 — `models/scene.py:297`.) Endpoint `/api/timing-programs` (`routers/timing_programs.py`), model `models/timing.py:26`.
  - **Interval rule, enforced on create AND update (2026-09-22)**: ascending and non-overlapping, touching allowed (`schemas._assert_ordered_non_overlapping`, `schemas.py:2424`, called by `TimingProgramBase` and `TimingProgramUpdate`). A bad list is a 422 on `POST` and `PUT`. `PUT` used to skip the check, and since `TimingProgramOut` re-applies the rule when it serialises, the PUT committed the bad list and then answered 500 — and so did every later read of that program, `GET /api/scene` included. Pinned by `backend/tests/test_timing_programs.py`.
- **Programmable Pulse Generator (PPG)**: carries a timing program and emits TTL to drive downstream devices.
  - **Its whole lifecycle lives in RF Link**: a PPG is created by right-clicking an empty `ttl_in` / `trigger_in` in the RF Link panel, and can only be removed from there. Every other entry point is sealed — `capabilityProfile.programmable_pulse_generator` (`kinds/_capabilityProfile.ts:97`) turns off `outlinerVisible`, `showRemoveObjectButton` and the gizmo, and the Object panel, the Outliner and — **since wave 3b** — the Delete key all sit behind that gate. The key used to delete any unlocked selection: clicking a PPG or an rf_cable in the 3D viewport and pressing Delete removed it out of band, which is exactly what these profiles exist to prevent, and through the orphan rule it took the PPG on a deleted cable with it. `App.tsx`'s handler now keeps only objects whose profile has BOTH `outlinerVisible` and `showRemoveObjectButton` (the two checks the Outliner row and the Remove button use; they agree on every kind, and the only two that opt out are `rf_cable` and the PPG). RF Link's Disconnect still removes one — it asks for it by name. **Cascading deletion** is the backend's `flows.plan_delete_objects`, reached through `POST /api/v3/objects/delete`: delete the main instrument → any cable pointing at it joins the doomed set, and so does any PPG plugged into it → a LEGACY PPG whose cables are all doomed goes too → and its TimingProgram goes with it (`routers/objects.py` `remove_scene_object`). See [object.md](object.md).
  - **One lifecycle, served by the backend (2026-09-22) and called by the web (wave 3b)**: `POST /api/v3/ppg/attach` (= right-click "Create Pulse & Timing here": the `canSpawnPpgHere` gate, the component choice with the `ppgHasUsableAsset` gate, the next free `CH<n>` for object and program, `ppgAttachment`, one transaction so a failure leaves no ghost program) and `POST /api/v3/ppg/{id}/detach` (= "Disconnect") — shapes in [api.md](api.md), code `backend/app/optical/rf_cables/`. `sceneStore.createPpgAtPort` is the attach call; `createProgrammablePulseGenerator` was folded into it and deleted, and with it the hand-written rollback that the transaction makes unnecessary. **The panel's "Disconnect" on a PPG goes through the generic `deleteObject`** (the same `plan_delete_objects`), so `/ppg/{id}/detach` exists for the add-on and the web does not call it. One difference by design: the backend STORES the mounted pose on the PPG (and `POST /api/v3/rf-cables/resnap` keeps it stored when the instrument moves), where the web used to store the 3D-cursor spawn pose and draw the mount live — a stored-pose client cannot re-derive it, and the web still draws the live mount either way.
  - **Naming a new PPG (fixed 2026-09-22)**: `CH<number of PPGs>`, stepped past any object name already taken, compared case-insensitively as the backend's unique-name check does (`rf_cables/flows.next_ppg_name`; the TypeScript twin went with `createProgrammablePulseGenerator`). The bare count collided as soon as a PPG other than the last was deleted — {CH0, CH1} minus CH0 gave "CH1" again, the object create failed with a 409 and no PPG was made. The name only labels the channel; channel ORDER stays positional (`ppgChannelIndex`).
  - **Name synchronisation (fixed 2026-08-13)**: the single source of truth for channel identity is the **PPG's `SceneObject.name`**; `TimingProgram.name` is a mirror for compiled output. The mirroring happens in the **store** (`sceneStore.mirrorPpgNameToTimingProgram`, called by `updateSceneObject`), not in the panel — previously only the Pulse & Timing panel mirrored it, so renaming by double-clicking a node in RF Link wrote `SceneObject.name` alone and `TimingProgram.name` drifted from there. Orphan programs (no PPG) still have the panel write `TimingProgram.name` directly.
  - **Where the pill reads and writes (fixed 2026-09-22)**: through the ownership chain both RF resolvers gate on — `dynamicSources` > the primary Asset's `defaultParams` > `kindParams` (`utils/ppgRestState.ts`: `resolvePpgRestState` reads with the exact merge of `rfPropagation.resolveElementParams`, `ppgRestStatePatch` writes **`SceneObject.dynamicSources.restState`**, every other per-instance key kept). It used to read and write the PhysicsElement's `kindParams` alone — the bottom tier — so an asset- or instance-level `restState` shadowed it and the pill flipped while the gate did not (the same bug class as the RF Link channel edits in [rf.md](rf.md) §3). `restState` need not be in the asset's `tunable_params`: neither RF resolver filters `dynamicSources` by tunability (only the optical loader does, and it never reads `restState`); the live `PPG BNC Male` asset carries no `restState` at all. A `kindParams.restState` on an older PPG still counts as the floor. Pinned by `utils/__tests__/ppgRestState.test.ts` (the pill equals the BFS rest-snapshot gate for all 27 tier combinations).
  - **Rest level is the level *outside* the blocks, not just while idle (fixed 2026-08-14)**: the `H`/`L` pill on the left of each row in Pulse & Timing sets the PPG's `restState` (see the previous bullet for where it lives), whose meaning is **`level = inInterval XOR (restState === "HIGH")`** — with rest = HIGH the blocks the user drew become LOW pulses (negative logic), and a channel with no blocks drawn sits permanently HIGH. Previously active scrub only honoured positive logic (intervals asserted HIGH and `restState` was used only for the idle snapshot when scrub was stopped), so a channel with rest = HIGH and no blocks flipped to LOW the moment you touched Scrub time, cutting the downstream switch dead. The implementation is the gate pre-pass in FE `rfPropagation.ts:528` / BE `rf_resolve.py:414` (compute each PPG's level first; the TTL pre-pass is then a lookup). The contract is written down in `types/digitalTwin.ts` `ProgrammablePulseGeneratorParams.restState` and `schemas.py` `rest_state`. A plugged-in PPG always owns that line — **it applies its rest level even with no TimingProgram bound** (it used to fall through to the switch's manual `ttlState`). The RF Link panel's TTL lines are coloured by the same level (`ppgGateHighObjectIds`, see [rf.md](rf.md) §4/§7).
  - **Plugged straight into the port, no cable (since 2026-08-14)**: the connection lives on the PPG's own `SceneObject.properties.ppgAttachment = {targetObjectId, targetAnchorId, targetAnchorName}` (contract in [`utils/ppgAttachment.ts`](../../frontend/src/utils/ppgAttachment.ts)). It is simultaneously the basis of the **3D pose** (`computePpgMountedThreePose` mates the PPG's `rf_out` to the target port, antiparallel) and an **edge of the RF graph** (the FE/BE BFS and the RF Link panel all consume it as a zero-length edge). The old model created an invisible rf_cable, which spawned a string of "invisible yet selectable / deletable / permanently hideable" bugs and has been retired; older scenes that still have the cable take a legacy fallback. Detail in [rf.md](rf.md) §7.
- **AD9959** (a 4-channel DDS RF source): timing integration takes **Option A** — tag the channel with `params.channelIndex` (0–3) inside the TimingBlock, requiring zero migrations; the AD9959-specific waveforms are `dds_single_tone` / `dds_sweep` / `dds_profile`. The player resolves the block in force per channel into a `DdsChannel`, with the static `kindParams.channels[i]` as fallback. (This is a design proposal; check against the code to see how much of it actually landed.)
- **The RF chain**: AD9959 channel → rf_amplifier → rf_switch → AOM (`utils/rfPropagation.ts`, endpoint `/api/rf-chains/nodes`), coupling into optics through the AOM's dynamicSource. The backend's copy of that map at a given scrub time — the snapshot the trace itself used, `scrubTimeNs = null` being the rest snapshot — is served by `POST /api/v3/rf/propagation`, together with the `sectionStartsNs` a client needs to mark the section boundaries ([rf.md](rf.md) §4, shapes in [api.md](api.md)).
