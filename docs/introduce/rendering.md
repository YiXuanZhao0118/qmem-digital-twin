# 渲染管線（前端）

> 相關：[asset.md](asset.md)（viewerHints）、[component.md](component.md)（binding 樹）、[optics.md](optics.md)（光束渲染來源）。

- `components/DigitalTwinViewer.tsx` 是主場景建構器。對每個 SceneObject：解析 Component + Asset → 統一走 **Binding-tree 渲染路徑**（最完整、唯一正規路徑）：`buildSceneObjectFromBindings()` → `resolveBindingTree()` → `buildBindingTreeObject()` 走整棵 ComponentBinding 樹，組出（可複合的）元件；葉節點 asset 仍由 `loadAssetObject()` 實際載入幾何，per-instance binding override（如 isolator 前/後 glan 旋轉）在 `resolveBindingTree` 內套用。
  - `shouldRenderViaBindings()`（`bindingRendererGate.ts`）**現恆為 `true`（2026-06-10 統一）**——所有元件都走 binding-tree；舊的單一資產直連 `loadAssetObject()` 分支已成 dead code，待後續連同 `Component.asset_3d_id` 一起移除。
  - ⚠️ **尚未完成**：fiber / rf_cable / isolator 的 per-instance 狀態（`fiberNodes`/`rfCableNodes`/`radiusMm`/ferrule pose/`translucentHousing`）**還沒透過 binding 樹轉送**，所以這三類目前可能以 catalog 預設 spline/pose 渲染（待補狀態轉送，見 [fiber.md](fiber.md)、[cable.md](cable.md)）。
- `three/loadAsset/index.ts`（葉節點載入器）依資產型別分派（STL/GLB/OBJ/`procedural://`）並有特例 builder（PBS252、BB1E03、AD9959、isolator）。
  - ⚠️ **無實體檔案的程序化元件也必須有 Asset3D 列＋root binding**：binding 樹是唯一渲染入口，**零 binding ＝ 空 Group ＝ 什麼都不畫**。所以程序化幾何仍要一列 `file_path = primitive://<key>` 的 asset 當 binding leaf，載入器的 `primitive://` 分支再依 **Component 的 `kindId`**（不是 asset key）查 plugin renderer（`createPrimitive` → `_renderer_bindings.ts`）。同一形狀已用在連接器（0115）與預置纜線 Component。
  - **文字標註（text_annotation）**：`sceneStore.addTextAnnotation`（`sceneStore.ts:2035`）建 Component（樣式存 `properties.text/textColor/bgColor/accentColor/fontSizePx/scaleMm`）→ 綁 alembic **0119** seed 的 `primitive://text_annotation`（`TEXT_ANNOTATION_ASSET_FILEPATH`，常數與 renderer 同檔）→ 建 SceneObject 於 transform cursor。渲染是 canvas 貼圖 billboard sprite（`three/loadAsset/passive/text_annotation.ts`，寬 = `scaleMm`、`renderOrder=100`）。**2026-08-14 修**：先前沒有 binding，2026-06-10 統一走 binding 樹後就成了「建得出、編得動、看不見」；找不到該 asset 時 store 會在建任何列之前丟錯（避免留下孤兒 Component），訊息指向 `alembic upgrade head`。編輯 UI＝`ComponentPanel.tsx:637` `TextAnnotationEditor`（寫 Component.properties）。
- 材質：`materialFor()` → `colorForComponent()`（kindId 色表 + `colorHex` 覆寫 + 裝置狀態著色）。
- **viewerHints** 驅動幾何過濾：`includeOnlyCentroids`、`deletedCentroids`、`recenterOrigin`。
- 光束渲染：`three/rayTrace.ts` → `v3TraceAdapter.ts` 消費後端 `/api/v3/solver` 輸出，發佈到 `window.__rayTraceDebug`（供 OpticalLinkViewer、BeamScope、snap-to-beam 讀取）。
  - **像散（per-axis qx/qy）**：adapter 的 `beamMode.x/.y` + `waistAtStart/EndUm`（X，qx）與 `waistAtStart/EndUmY`（Y，qy）**各軸獨立**（2026-06-11 修；先前 y 軸誤抄 qx → 永遠圓）。`OpticalLinkViewerPanel` 因此把 3D 光束畫成**橢圓錐管**（自建 BufferGeometry，X 半寬←qx、Y 半寬←qy，每軸各套 `VISUAL_FLOOR_UM`），方向用 `makeBasis` 對到 beam-local **s/p**（local X→s、Z→p；約定 `spatialModeX∥s`，長軸反了就對調 s/p）。圓形光束退化回舊的圓錐。**沿軸取樣（2026-06-11）**：錐管不再用端點 `waistAtStart/EndUm` **線性內插**（會把 segment 內部的束腰拉成直錐、漏掉透鏡焦點的收束），改成 **24 片切面**沿 `seg.beamMode` 取 `BeamScopePanel.beamWidthsUmAtPathMm(beamMode, pathLengthFromSourceMmAtStart + t·lengthMm)`——與 2D scope plot 的 `waistAtZUmAxis` **同一套解析高斯**，所以 3D 錐管與 scope plot 在 segment 內的**焦點 pinch 完全同步**（先前兩者不同步即源於此；無 `beamMode` 的舊 payload 才回退端點內插）。BeamScope 的 2D profile 熱圖同樣讀 `beamMode.x/.y` → 像散顯示為橢圓光斑。**近束腰**兩軸都被 `VISUAL_FLOOR_UM`(30µm) 夾平 → 仍圓；橢圓在下游才明顯。
  - **光束顏色覆寫（per-source，2026-06-12）**：每條 segment 的顏色由 `opticalBeams.beamColorForSource(emitterObject, wavelengthNm)` 解析——讀發射端 `SceneObject.properties.emissionVisuals` 的 `colorHex` 覆寫（雷射存 `"main"`、TA 存 `"forward"`；見 `utils/emissionVisuals.ts`），沒覆寫才回退 `wavelengthToColor(波長)`。**用發射端（emitter）不是 per-segment source**：`seg.emitterSceneObjectId`（adapter 的 `seg.emitterObjectId`）在整條鏈上**不變**（anchor_tracer.py:577 把 `emitter_id` 原樣往下傳，而 `source_id` 每段換成剛打到的光學元件），所以一個 source 的覆寫色塗滿它的**整條光束**；若誤用 `sourceSceneObjectId` 只會塗到 laser→第一個元件那一段。**兩個 live 3D renderer 都走這條**：主場景 `DigitalTwinViewer`（細線）與 `OpticalLinkViewerPanel`（橢圓錐管）。**OpticalLinkViewerPanel 的 rebuild 短路 key 必須含顏色 digest**（`colDigest`，掃所有 object 的 `emissionVisuals.colorHex`）——否則改色不改 segment 幾何 → key 不變 → `prevContentKey` 短路 → 錐管不重畫。**同理 key 還含 `rv:${RENDER_LOGIC_VERSION}`（2026-06-12）**：當改的是**繪製邏輯**（如偏振 s/p 基底修正）而非 segment 資料時，data digest 不變 → 不重畫 → 熱修後仍畫舊 marker。改繪製數學時 bump 這個常數即可強制重建（曾因此症狀：偏振箭頭一直停在舊 `up×d` 水平向，見 [polarizationMarker](#)）。UI：Optical setting → 雷射的 **Visualization** card（`_shared.tsx`，key `"main"`）/ TA 的 **Visualization** card（`TaperedAmplifierAdjustControls`，forward/backward）。注意舊的 `rayTrace.ts` 也讀 `emissionVisuals` 但已是 dead code，live 渲染不經過它。
  - **profile 世界座標 + 旋轉（2026-06-11）**：beam-scope 熱圖是**垂直於傳播方向**的橫向切面,座標標成**世界/object-sense 軸**。adapter 帶 `dirLab`（lab 單位傳播向量,object-sense X=(1,0,0)）;`BeamScopePanel` 取 `|dirLab|` 最大軸為傳播軸,另兩軸即橫向 → 標成 `Heatmap` 的 `axisLabel`（水平）/ `axisLabelY`（垂直）。內容額外**旋轉 90°**（`sampleIntensity(y,−x)`）。**僅作用於解析 profile**;**POP 焦平面繞射(Airy)視圖排除在外**——它活在透鏡焦平面自己的座標,維持不旋轉、標 `x, y (µm) · focal plane`(否則焦面圖會被誤旋轉/誤標 → 2026-06-11 回修)。**方向/標籤是約定**(qx/qy↔世界軸、旋轉向、水平/垂直)——視覺對不上就:旋轉向改 `sampleIntensity(−y,x)`、H/V 對調 `transverse[0]/[1]`。例:雷射沿 X 傳播 → 橫向軸 = Y/Z。
- **PHY Editor COMPONENT 預覽的 probe beam + 逐段偏振（2026-06-12）**：`ComponentsEditor.tsx` 的 `ComponentPreview3D.rebuildProbeBeam` 不再用前端 face/matrix5x5 近似追跡，改 POST `/api/v3/solver/run-from-component`（component frame；見 [optics.md](optics.md)）拿**後端真值** `labSegments`，逐段畫金色光束管 + **偏振 marker**（線偏雙箭頭 / 橢圓-圓偏環），所以 Faraday 旋轉、PBS s/p 分光等都是真實物理。**偏振 marker 與 Lab optical link 共用同一套** `optical/polarizationMarker.ts`（`beamLocalSPThree` + `polEllipseFromJones` + `buildPolarizationMarkers`，2026-06-12 從 `OpticalLinkViewerPanel` 抽出去重）——兩處對 Jones 的詮釋永不分歧。**`beamLocalSPThree` 必須與後端 `jones.beam_local_sp` 同基底：`s = normalize(up − (up·d)d)`（up 投影到 ⊥d 平面）、`p = d×s`，up=Z、退化用 X**。先前誤用 `s = up×d`（差 90°），把 Jones 畫在錯基底 → 45° 線偏被鏡像、看起來旋轉方向相反（2026-06-12 修，影響 link + 元件預覽兩處）。元件 root 是 identity，component-frame mm 直接落進 `probeBeamGroup` local。**近暗 branch（Glan 拒掉的偏振、Jones 強度 <0.01）跳過**不畫，避免誤導。**probe 自動對準**：先試 `computeProbeOpticalAim`（component exposedFaces 的 optical_in/out），失敗（如 IO-3-850-HP 無此 exposed faces）退回 `computeProbeAnchorAim`——用綁定光學資產 anchor 世界位置的**最遠點對**當光軸、origin 退到近端後方，確保 probe 真的穿過光學鏈。
- **相機 up / 軸向 gizmo（2026-08-14）**：viewer 世界是 **Z-up**，且 `OrbitControls` 在 **constructor 就把公轉極軸（`_quat`）從當下的 `camera.up` 定死**（`DigitalTwinViewer.tsx:2086`；之後改 `camera.up` 不會搬動極軸）。因此**所有**設相機姿態的路徑——H（Home，含還原自訂 Home）、六顆軸向按鈕（`snapCameraToView`，`DigitalTwinViewer.tsx:1820`）、開場還原——**一律用 `WORLD_UP=(0,0,1)`**（`DigitalTwinViewer.tsx:136`）。invariant：`camera.up ≡ WORLD_UP`；破壞它的症狀是「按了 ±Z 之後拖曳的轉軸跟按 H 之後不一樣」（舊 `AXIS_VIEW_CONFIG.zPos/zNeg` 曾設 `up=(0,1,0)`，2026-08-14 修，該欄位已整個移除）。±Z 視角的視線與 up 平行是**刻意**允許的退化：`Matrix4.lookAt` 會偏移基底、`Spherical.makeSafe()` 會把極角夾離極點，姿態仍有限且可拖。存 Home 仍會寫 `up`（`HomeViewPose`），但**還原時故意忽略**，避免舊資料把 roll 與極軸再拆開。
- 效能：on-demand rendering（閒置 0 renders/sec）、增量重建場景 + `objectWrappersRef` 以 (component, asset, deviceState) 參考相等做 wrapper 快取。
