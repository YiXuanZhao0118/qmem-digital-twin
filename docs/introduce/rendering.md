# The render pipeline (frontend)

> Related: [asset.md](asset.md) (viewerHints), [component.md](component.md) (the binding tree), [optics.md](optics.md) (where the beam rendering comes from).

- `components/DigitalTwinViewer.tsx` is the main scene builder. For each SceneObject it resolves Component + Asset and then takes the **binding-tree render path** uniformly (the most complete and only canonical path): `buildSceneObjectFromBindings()` → `resolveBindingTree()` → `buildBindingTreeObject()` walks the whole ComponentBinding tree and assembles the (possibly composite) component. Leaf-node assets still have their geometry actually loaded by `loadAssetObject()`, and per-instance binding overrides (e.g. the rotation of an isolator's front/back Glan) are applied inside `resolveBindingTree`.
  - `shouldRenderViaBindings()` (`bindingRendererGate.ts`) is **now permanently `true` (unified 2026-06-10)** — every component goes through the binding tree. The old direct-to-`loadAssetObject()` branch for single assets is dead code, to be removed later along with `Component.asset_3d_id`.
  - ⚠️ **Not finished yet**: the per-instance state of fiber / rf_cable / isolator (`fiberNodes` / `rfCableNodes` / `radiusMm` / ferrule pose / `translucentHousing`) is **not yet forwarded through the binding tree**, so those three may currently render with the catalog's default spline/pose (state forwarding still to be written; see [fiber.md](fiber.md), [cable.md](cable.md)).
- `three/loadAsset/index.ts` (the leaf loader) dispatches on asset type (STL/GLB/OBJ/`procedural://`) and has special-case builders (PBS252, BB1E03, AD9959, isolator).
  - ⚠️ **Procedural components with no real file still need an Asset3D row plus a root binding**: the binding tree is the only render entry point, so **zero bindings = an empty Group = nothing drawn**. Procedural geometry therefore still needs one asset row with `file_path = primitive://<key>` as the binding leaf, and the loader's `primitive://` branch then looks up the plugin renderer by the **Component's `kindId`** (not the asset key) (`createPrimitive` → `_renderer_bindings.ts`). The same shape is already used for the connectors (0115) and the pre-built cable Components.
  - **No more kind short-circuit: always go through the asset's `file_path` (2026-08-14)** — `loadAssetObject` used to begin with `if (component.kindId === "optical_table") return createNewportOpticalTable()`, **ignoring the asset entirely**, so after baking the optical_table asset into a GLB it still drew the old procedural geometry. That is now removed: an asset with `primitive://table` still goes through the `primitive://` branch → the plugin renderer (`optical_table` in `_renderer_bindings.ts`), and anything with a real file loads that file like any other asset. Invariant: **what gets rendered is decided only by the asset's `file_path`; the kind only selects the renderer for `primitive://`**. The same day, the two same-shaped special cases in the PHY Editor previews (`Asset3DEditor.tsx:~1973`, `ComponentsEditor.tsx:~2647`) were changed to key on `filePath === "primitive://table"` only, and the procedural builder's missing `rotation.x = +π/2` (Y-up→Z-up; detail in [asset.md](asset.md)) was added.
  - **Annotations (text_annotation / rect_annotation) — ordinary catalog entries since alembic 0125.** Both types now obey the param-ownership spine rule ([data-model.md](data-model.md)) instead of storing per-instance styling on the Component:
    - **Kind** (`kinds` row, `op_set_name='none'`, domains `['mechanical']`, left UNLOCKED) owns the style template in `default_params` — this is the single definition of an annotation's default size / colour / content, editable in the PHY Editor.
    - **Asset3D** (`primitive://text_annotation` / `primitive://rect_annotation`, seeded by **0119** / **0124**) carries its own copy of those defaults plus `tunable_params` = every style key, i.e. the declaration that an instance may override them.
    - **Component**: exactly ONE shared catalog row per type (`catalog_id` `text_annotation` / `rect_annotation`), with a single root binding to the asset — the binding leaf the tree walk needs (a Component with no binding renders an empty Group).
    - **SceneObject**: one per label/marking; its overrides live in `dynamic_sources`. `sceneStore.addAnnotationInstance` (used by `addTextAnnotation` / `addRectAnnotation`) therefore creates **only an object**, so adding an annotation can no longer 409 on the unique Component name and the catalog no longer grows one row per label. A rect marking spawns at the cursor's X/Y but at `TABLE_TOP_HEIGHT_MM` (860 mm, exported from `three/photoRoom.ts`) so a *table* marking lands on the table; a text label keeps the cursor's Z.
    - **What the renderer sees**: plugin renderers only take a `ComponentItem`, so `bindingRendererGate` hands them a synthetic component whose `properties` are `effectiveInstanceParams(asset, sceneObject)` = `asset.defaultParams ⊕ (dynamicSources ∩ tunableParams)` (`utils/instanceParams.ts`, the frontend mirror of `db_scene_loader`) — the same channel the glan prism already used. **The viewer's wrapper cache must see this**: `renderHintsKeyNow` (`DigitalTwinViewer.tsx`) folds in `instanceParamsKey(placement)` for annotation kinds only, otherwise editing a marking would keep serving the cached mesh (and folding it in for *every* kind would make a laser-power tweak reload its GLB).
    - **Rendering**: `three/loadAsset/passive/text_annotation.ts` is a canvas-textured billboard sprite (width = `scaleMm`, `renderOrder=100`). `three/loadAsset/passive/rect_annotation.ts` is a `ShapeGeometry` frame (outer rect + inner hole, so `lineWidthMm` is a real on-table band width — GL `linewidth` is unreliable) drawn in the **body XY plane, normal +Z** per the Z-up frame contract, plus an optional fill plane and two canvas-sprite captions. Its meshes use `polygonOffset` rather than a hidden lift, so a marking sitting exactly at the table's 860 mm top face wins the depth test while staying at the pose the user sees.
    - **Editing**: `TextAnnotationEditor` / `RectAnnotationEditor` in `ComponentPanel.tsx` share `useAnnotationParams`, which reads the merge and writes `SceneObject.dynamicSources`. Neither mirrors the caption into `component.name` any more — that row is now shared, so renaming it would rename every annotation (and 409 on a duplicate).
    - **History**: before 0125 each annotation got its own Component with the styling in `properties`; before 0119 (text) / 0124 (rect) there was no binding at all, so annotations were "creatable, editable, invisible" once everything unified onto the binding tree on 2026-06-10.

- Materials: `materialFor()` → `colorForComponent()` (a kindId colour table + `colorHex` override + device-state colouring).
- **viewerHints** drives geometry filtering: `includeOnlyCentroids`, `deletedCentroids`, `recenterOrigin`.
- Beam rendering: `three/rayTrace.ts` → `v3TraceAdapter.ts` consumes the backend's `/api/v3/solver` output and publishes it to `window.__rayTraceDebug` (read by the optical-link chrome, BeamScope and snap-to-beam).
  - **Astigmatism (per-axis qx/qy)**: the adapter's `beamMode.x/.y` plus `waistAtStart/EndUm` (X, qx) and `waistAtStart/EndUmY` (Y, qy) are **independent per axis** (fixed 2026-06-11; the y axis used to copy qx by mistake, so beams were always round). `optical/beamChain.ts` (`buildBeamChainGroup`, called by the main viewer in **optical-link display mode** — see below) therefore draws the 3D beam as an **elliptical cone tube** (a hand-built BufferGeometry with X half-width ← qx and Y half-width ← qy, each axis clamped by its own `VISUAL_FLOOR_UM`), oriented with `makeBasis` onto the beam-local **s/p** (local X→s, Z→p; the convention is `spatialModeX∥s` — if the major axis comes out wrong, swap s/p). A round beam degenerates back to the old circular cone. **Sampling along the axis (2026-06-11)**: the tube no longer **linearly interpolates** the endpoint `waistAtStart/EndUm` (which would stretch a waist inside a segment into a straight cone and miss the pinch at a lens focus); it now takes **24 slices** along `seg.beamMode` via `BeamScopePanel.beamWidthsUmAtPathMm(beamMode, pathLengthFromSourceMmAtStart + t·lengthMm)` — **the same analytic Gaussian** as the 2D scope plot's `waistAtZUmAxis`, so the 3D tube and the scope plot **pinch at exactly the same focus** inside a segment (the two being out of sync came from precisely this; only an old payload without `beamMode` falls back to endpoint interpolation). BeamScope's 2D profile heatmap also reads `beamMode.x/.y`, so astigmatism shows up as an elliptical spot. **Near the waist** both axes are flattened by `VISUAL_FLOOR_UM` (30 µm) and so still look round; the ellipse only becomes obvious downstream.
  - **Per-source beam colour override (2026-06-12)**: each segment's colour is resolved by `opticalBeams.beamColorForSource(emitterObject, wavelengthNm)` — it reads the `colorHex` override in the emitter's `SceneObject.properties.emissionVisuals` (a laser stores `"main"`, a TA stores `"forward"`; see `utils/emissionVisuals.ts`), and only falls back to `wavelengthToColor(wavelength)` when there is none. **It keys on the emitter, not the per-segment source**: `seg.emitterSceneObjectId` (the adapter's `seg.emitterObjectId`) is **constant along the whole chain** (anchor_tracer.py:577 passes `emitter_id` straight down, whereas `source_id` becomes whichever optical component was just hit), so one source's override paints its **entire beam**; using `sourceSceneObjectId` by mistake would only paint the laser→first-component segment. **Both beam renderers take this path**, and since 2026-08-17 both run in the SAME scene: thin `THREE.Line`s in wireframe / rendered mode, `beamChain.buildBeamChainGroup` elliptical tubes in optical-link mode. (Historical note: the optical-link tubes used to live in a second Three.js viewport owned by `OpticalLinkViewerPanel`, which cached its content behind a `prevContentKey` digest — so a pure recolour, or a change to the *drawing logic* itself, had to be folded into that key (`colDigest`, `rv:${RENDER_LOGIC_VERSION}`) or nothing redrew. That cache is gone: `renderRayTraces` rebuilds the beams from scratch on every scene rebuild, so no digest bumping is needed when you change the beam/marker math.)  UI: Optical setting → the laser's **Visualization** card (`_shared.tsx`, key `"main"`) and the TA's **Visualization** card (`TaperedAmplifierAdjustControls`, forward/backward). Note that the old `rayTrace.ts` also reads `emissionVisuals` but is dead code — live rendering does not go through it.
  - **Profile world coordinates + rotation (2026-06-11)**: the beam-scope heatmap is a transverse slice **perpendicular to propagation**, with axes labelled in **world / object-sense axes**. The adapter carries `dirLab` (the lab-unit propagation vector; object-sense X = (1,0,0)); `BeamScopePanel` takes the largest component of `|dirLab|` as the propagation axis, leaving the other two as the transverse pair → labelled as the `Heatmap`'s `axisLabel` (horizontal) / `axisLabelY` (vertical). The contents are additionally **rotated 90°** (`sampleIntensity(y,−x)`). **This applies only to the analytic profile**; **the POP focal-plane diffraction (Airy) view is excluded** — it lives in the lens focal plane's own coordinates and stays unrotated, labelled `x, y (µm) · focal plane` (otherwise the focal-plane figure would be wrongly rotated and mislabelled → reverted 2026-06-11). **The directions and labels are conventions** (qx/qy ↔ world axes, rotation sense, horizontal/vertical) — if the visual doesn't match, either flip the rotation to `sampleIntensity(−y,x)` or swap H/V by exchanging `transverse[0]/[1]`. Example: a laser propagating along X → transverse axes = Y/Z.
- **The PHY Editor COMPONENT preview's probe beam + per-segment polarization (2026-06-12)**: `ComponentPreview3D.rebuildProbeBeam` in `ComponentsEditor.tsx` no longer traces with a frontend face/matrix5x5 approximation; it POSTs to `/api/v3/solver/run-from-component` (component frame; see [optics.md](optics.md)) to get the **backend's ground truth** `labSegments`, and draws a golden beam tube per segment plus **polarization markers** (a double arrow for linear, an ellipse/circle ring for elliptical-circular) — so Faraday rotation, PBS s/p splitting and the rest are real physics. **The polarization markers are shared with the Lab optical link** through `optical/polarizationMarker.ts` (`beamLocalSPThree` + `polEllipseFromJones` + `buildPolarizationMarkers`, extracted from `OpticalLinkViewerPanel` on 2026-06-12 to remove the duplicate) — so the two places can never diverge in how they interpret a Jones vector. **`beamLocalSPThree` must use the same basis as the backend's `jones.beam_local_sp`: `s = normalize(up − (up·d)d)` (up projected into the plane ⊥d), `p = d×s`, with up = Z and X for the degenerate case.** It previously used `s = up×d` (off by 90°), drawing the Jones vector in the wrong basis → 45° linear polarization came out mirrored and appeared to rotate the wrong way (fixed 2026-06-12, affecting both the link and the component preview). **Scale note (2026-08-17)**: the arrow SHAFT radius is `max(size·0.08, opts.minRadius)`, and the default `minRadius = 0.05` three-units is sized for the PHY Editor's component-frame preview. At Lab scale (1 unit = 100 mm) that floor is 5 mm — thicker than the arrow is long — so `beamChain.ts` passes a span-relative `minRadius` (`span·0.00015`) instead. Symptom of getting it wrong: fat cyan clubs instead of arrows. The component root is identity, so component-frame mm land directly in `probeBeamGroup` local space. **Nearly dark branches (the polarization a Glan rejected, Jones intensity < 0.01) are skipped** rather than drawn, so they can't mislead. **Automatic probe aiming**: it first tries `computeProbeOpticalAim` (the component's exposedFaces optical_in/out) and, on failure (e.g. the IO-3-850-HP, which has no such exposed faces), falls back to `computeProbeAnchorAim` — which takes the **farthest pair** of world anchor positions among the bound optical assets as the optical axis and pushes the origin back behind the near end, so the probe really does pass through the optical chain.
- **Camera up / axis gizmo (2026-08-14)**: the viewer world is **Z-up**, and `OrbitControls` **fixes its orbit pole (`_quat`) from whatever `camera.up` is at construction time** (`DigitalTwinViewer.tsx:2086`; changing `camera.up` afterwards does not move the pole). So **every** path that sets the camera pose — H (Home, including restoring a custom Home), the six axis buttons (`snapCameraToView`, `DigitalTwinViewer.tsx:1820`), and the restore at startup — **must use `WORLD_UP=(0,0,1)`** (`DigitalTwinViewer.tsx:136`). Invariant: `camera.up ≡ WORLD_UP`; the symptom of breaking it is "after pressing ±Z, dragging rotates about a different axis than after pressing H" (the old `AXIS_VIEW_CONFIG.zPos/zNeg` used to set `up=(0,1,0)`; fixed 2026-08-14 and that field removed entirely). The ±Z views having a line of sight parallel to up is a **deliberately** permitted degeneracy: `Matrix4.lookAt` perturbs the basis and `Spherical.makeSafe()` clamps the polar angle away from the pole, so the pose stays finite and draggable. Saving Home still writes `up` (`HomeViewPose`), but **restore deliberately ignores it**, so old data can't re-separate roll from the pole axis.
- **TA port labels are anchor-driven (2026-08-18)**: `addTaPortLabels` (`DigitalTwinViewer.tsx:442`) places the INPUT / OUTPUT billboards at the `intercept_in` / `intercept_out` anchor positions (body-local mm ÷ 100 → wrapper-local three units, axes unchanged — the same convention as `addAomTiltAxisMarker`), plus a short `ArrowHelper` along each anchor's **axisX** so a flipped or mis-authored port normal is visible at a glance. It previously derived both labels from the mesh **bbox** with a hard-coded "−X = OUTPUT, +X = INPUT" special-case for the BoosTA pro GLB, so the labels ignored the anchors entirely and were simply wrong on any other TA model. Two gotchas the rewrite had to handle: (1) the asset must be resolved **binding-aware** via `primaryAsset(component, …)` — a TA imported through "+ New Component" carries its Asset3D on a root binding and `component.asset3dId` is `null`, which made the anchors invisible to the old lookup; (2) everything it adds is tagged `userData.isPortLabel`, which is both what makes raycasts skip it and what lets `stripDynamicDecorations` clean it up on rebuild — tag the arrow's children too, not just the arrow. Assets with no `intercept_in`/`intercept_out` pair fall back to the old bbox placement.
- Performance: on-demand rendering (0 renders/sec while idle), incremental scene rebuilds, and `objectWrappersRef` caching wrappers by reference equality of (component, asset, deviceState).

## Viewer display modes

`ViewerDisplayMode` (`DigitalTwinViewer.tsx:116`) = `wireframe | rendered | node-edit | optical-link`; the toolbar pills at the viewport's top-left switch it, per panel (dual view holds one each). All four render the SAME scene — a mode only changes materials, decorations and what is pickable.

- **wireframe** — every mesh's material is swapped for an unlit wireframe `MeshBasicMaterial` (`applyViewerDisplayMode`), the photo-room is hidden and the reference grid shown. The original material is stashed on `mesh.userData.__renderedMaterial` and handed back on the way out; without that stash the wireframe "sticks".
- **node-edit** — only cables (fiber / rf_cable) are interactive: clicking one opens its Bezier gizmo, other selection / transform interactions are suppressed.
- **optical-link (rewritten 2026-08-17)** — "rendered, but about the light path". It used to be an **overlay**: `OpticalLinkViewerPanel` mounted a whole second Three.js scene + camera + OrbitControls on top of the (still-running) main canvas, so the orientation gizmo drove a camera nobody could see, and only the optics the beam happened to touch were drawn, as wireframes. Now it is a plain mode of the main viewer:
  - beams are drawn by `optical/beamChain.ts` (`buildBeamChainGroup`) into the main viewer's `beamGroup` under `labRoot` — elliptical Gaussian tubes + `polarizationMarker` marks, replacing the thin `THREE.Line`s the other modes draw. Invariant: the group's parent frame must be **lab Z-up scaled by `mmToThree`**, which is exactly where the adapted `startThree/endThree` live; nothing in `beamChain.ts` applies the world swap S.
  - **optics stay at full strength, everything else is ghosted** — `opticalObjectIdSet` (`utils/opticalDomain.ts`, shared with the chrome so the two can't disagree) decides; `applyOpticalLinkGhost` clones each non-optical mesh's material at opacity 0.16 with `depthWrite:false`. It CLONES because loaders may share one material across instances — mutating in place would ghost every copy. Order matters: un-ghost BEFORE `applyViewerDisplayMode` so the wireframe swap never caches a ghosted material.
  - **ghosted objects are also unpickable** (`pickObject` filters by the same set), the node-edit rule applied to optics: a click passes through the table/mount to the optic or beam behind it.
  - each optic gets translucent **optic-surface markers** (`beamChain.buildOpticSurfaceMarkers`: pink PBS coating quad / amber Faraday rotation plane / slate generic optic face) parented to its wrapper, so they follow a drag. They carry `userData.isOpticSurfaceMarker` and are cleaned by `stripDynamicDecorations`. **Two invariants, both learned the hard way**: (1) a marker may only sit on an anchor the tracer actually hit-tests (`PRIMARY_OPTICAL_ANCHOR_IDS`, mirroring `anchor_tracer.PRIMARY_ANCHOR_IDS`) — the "else take the asset's first anchor" fallback drew faces on connectors' `connect_out` and on `rf_in`/`rf_out`, i.e. pale discs floating where no light is ever intercepted; (2) the last-resort "component has no `__bindingId` nodes" branch must enumerate only **that component's** bindings — handing it the whole scene's list made one untagged component (the fiber) sprout a marker per bound asset in the entire scene, ~35 discs stacked at its origin, sized after other components' optics. A **fiber** has no optical anchor at all under those rules — its ports are synthesized, not authored — so it takes a separate builder, `beamChain.buildFiberCouplingMarkers`, which mirrors `db_scene_loader._synth_fiber_slot`: the face sits at `kindParams.end{A,B}.posMm + (−unit(tensionHandleMm)) · tip`, with `tip` = `|connect_in − connect_out|` and the disc radius = `connect_in.apertureMm` off the bound `fiber_connector` asset (per-instance `asset3dIdOverride` honoured, as the loader does), falling back to `FIBER_FERRULE_TIP_MM` / `apertureDiameterMm`. **Keep it in lockstep with the loader** — the whole point is that the drawn face is the one the tracer couples through, so editing `connect_in` in the ASSET3D editor moves both together (verified against a live trace: markers land on the traced fiber in/out points to the mm). See [fiber.md](fiber.md).
  - **single click on a beam** publishes `scopeProbe` (other modes need a double click), which opens the beam scope in the chrome. ⚠️ **The optic wins a single click, though** (`DigitalTwinViewer.tsx:3155`, fixed 2026-08-17): the single-click path runs `pickObject` FIRST and only probes the beam when it misses. Probing first made optics hard to select — the tube runs through the middle of every element it hits, and selection is the only way to reach the Optical-setting panel. A **double click** still probes first, so a probe right at an element's face stays reachable.
  - the chrome (`OpticalLinkViewerPanel.tsx`, `.viewer-optical-link-chrome`) is UI only — optic picker + inspector drawer, link warnings, inline beam scope. The layer is `pointer-events:none` with only its panels re-enabling it, so orbiting, beam picking and the orientation gizmo (z-index 3, above the chrome's 2) all keep working.
  - **Spec sheet** (`IntrinsicSpecPanel.tsx`, the drawer's "Spec" section): reads the **bound assets**, one block per `targetKind:"asset"` ComponentBinding in `sortOrder`, honouring a per-instance `asset3dIdOverride` the way the loader does. Each block lists that asset's `default_params` **minus its `tunable_params`** (those are editable right below, off `dynamicSources`) plus `wavelength_range_nm`; assets with neither (mount/housing pieces, e.g. the isolator's front/back shells) are skipped. So a composite optic shows its internals — the IO-3-850-HP isolator lists both Glan-Laser prisms and the Faraday rod. ⚠️ **It used to read `PhysicsElement.kindParams` filtered by the frontend plugin's `intrinsicParamKeys`, keyed off the COMPONENT kind** (the layer mistake in [kinds.md](kinds.md)): only 4 plugins ever declared those keys, so in a live 12-optic scene **10 optics showed no spec at all** and the two that did were half `—` — `wavelengthRangeNm` is an Asset3D **column** and can never appear in kindParams. Physics lives on the asset (see [asset.md](asset.md)); the sheet reads it there now.
  - **optic picker** (drawer top, `.vol-picker`): every optic from `opticalObjectIdSet`, in **beam-path order** — `pathOrderFromSegments` walks the live `window.__rayTraceDebug` segments in tracer traversal order taking `sourceObjectId` then `hitObjectId` (so the emitter leads), and optics the beam misses are appended alphabetically. Order is refreshed by the same 250 ms poll that computes the link warnings, and state is only set when the id sequence actually changes. A row drives the **global** selection (`selectObject`), which is what re-points the panel — so the panel is reachable without landing a click on a small element in 3D.
  - **Mode-switch normalisation**: the `[displayMode]` effect re-applies ghost + display mode to every cached wrapper. The scene-rebuild effect does this per object, but its async run can be cancelled mid-loop, which would strand the objects it never reached with the previous mode's material.
  - a runtime **LOD tier swap** attaches a bare subtree; `integrateLodTier` re-applies the mode's material, the objectId stamp and the selection outline to it — see LOD §P1 below.

## LOD (level of detail)

> Targets and the switching rule live in [../objectives.md](../objectives.md) §R-4/R-5. This section is the implementation map.
> **Status: P0 (generation + storage), P1 (runtime switching) and P2 (catalog backfill) are all live.** An asset with no tiers renders LOD0 at every distance — that is the intended no-op, and it is what most of the catalog does, because most parts are already under the coarsest budget (see P2).

### P0 — where the tiers come from and where they live

- Tiers are generated **at authoring time, never at runtime**: one `simplify()` pass over a 500k-triangle mesh is a few hundred ms of synchronous WASM and would blow R-1/R-3 if it ran inside a frame. BUILD already welds the mesh once on save, so the two extra tiers ride along on that work (`GeometryBuilder.emitLodTiers`, called from `handleSave` on both the create and edit-in-place branches; budgets are the `LOD1_TRIS` / `LOD2_TRIS` constants at the top of that file). A tier failure is logged and reported in the save message but never rethrown — the asset is already stored, and missing tiers degrade to "always LOD0", not to lost work.
- `decimate.ts` exports `decimateWeldedGraded(welded, targets)` → `DecimatedTier[]`, each carrying `geometry` / `triangles` / **`errorMm`**. Every tier simplifies from the *original* welded source, never from the previous tier — chaining compounds quadric error and would make `errorMm` a lower bound rather than the deviation from LOD0. meshoptimizer's `simplify()` has always returned that error as the second tuple element; before 2026-08-17 the wrapper destructured `const [newIndex] = …` and dropped it. `MeshoptSimplifier.getScale()` converts the relative figure to absolute (mm, since BUILD geometry is mm). That number is R-5's whole switching input, so losing it is not cosmetic — `decimate.test.ts` guards that it comes back positive and grows with aggressiveness.
- Storage is the **`asset_lods` table (alembic 0122)**, one row per (asset, level 0/1/2), carrying `file_path` / `tri_count` / `byte_size` / `error_mm` / `hints_digest`. Invariants:
  - **level 0's `file_path` always equals `assets_3d.file_path`.** Every geometry-replacing route (`POST /assets3d/upload`, `PUT /assets3d/{catalog_id}/geometry`) **deletes the asset's LOD rows** so a stale tier can never outlive the mesh it was derived from.
  - **Not stored in `assets_3d.properties`, deliberately.** 17 of 23 assets are `locked` and `lock_guard` 422s any non-`locked` field write, so a manifest in `properties` would make generating a derived render artifact require a human unlock. A separate table sidesteps that entirely — see [asset.md](asset.md).
  - `hints_digest` pins which `viewerHints` the tiers were baked against. `includeOnlyCentroids` / `deletedCentroids` are keyed on a 0.5 mm centroid grid of the **full-resolution** mesh (`viewerHints.ts`), and decimation moves every centroid — so tiers must be generated from the **post-hint** geometry, and editing an asset's hints invalidates them.
- Delivery: `lods[]` rides on **both** `Asset3DV3Out` (the v3 catalog) and `Asset3DOut` (the `/api/scene` payload the renderer actually consumes — a manifest only on the catalog route would never reach the viewer). `AssetLod` is defined once, in `schemas.py`, because schemas_v3 imports from it and the reverse would cycle. The relationship is `lazy="selectin"` at the mapper, so no query has to remember an explicit `selectinload` — including the post-commit `session.refresh`, where a lazy load would raise `MissingGreenlet` under asyncio.
- Upload route: `POST /api/v3/assets3d/{catalog_id}/lods` (multipart, one call per tier; level 0 sends metrics only, no file).

### P1 — runtime switching

Three modules under `three/lod/`, all unit-tested:

- **`lodPolicy.ts`** — the pure rule. `pixelErrorFor(errorMm, distanceMm, viewportHeightPx, fovRadY)` and `chooseLodLevel(...)`, which picks the **coarsest** tier inside the pixel budget (τ = `LOD_PIXEL_ERROR_BUDGET`, 1 px) and applies 15 % hysteresis so an object parked on a threshold cannot flip every pass. No scene or THREE state, so the rule is testable on its own; `lodPolicy.test.ts` asserts the spec's calibration numbers directly.
- **`lodNode.ts`** — the container. **Not `THREE.LOD`**: its `raycast()` correctly tests only the active level, but picking here goes through `raycaster.intersectObjects(componentGroup.children, true)` (`DigitalTwinViewer.tsx:2489`), and that recursion descends into `LOD.children` — all three tiers — because `Raycaster` does not test `visible`; selection, hover and snap would all collect ghost hits. Instead a plain `Group` carries `userData.lod` and holds exactly **one** child. Tiers it has already built stay, detached, in `state.cache`, so orbiting back and forth does not re-parse a 20 MB GLB on the main thread. It also caches the attached tier's local bounds — `Box3.setFromObject` walks all geometry and is far too expensive to repeat per evaluation.
  - ⚠️ **`disposeObject` (`three/loadAsset/index.ts`) cannot reach the detached tiers by traversal**, so it explicitly calls `disposeLodNode` on any node it passes. Miss that and every visited tier leaks on scene rebuild. Nothing is shared *across instances* — each container owns its geometry — which is what keeps ordinary disposal correct; a cross-instance parse cache would need refcounting and is deliberately not here.
- **`lodUpdater.ts`** — the per-frame pass, called from `animate()` (`DigitalTwinViewer.tsx`) **after** `renderer.render` so every `matrixWorld` is current (evaluating first uses last frame's transforms, and on the first pass after a scene rebuild they are still identity). It sits inside the `cameraMoved || pendingRender` branch, so an idle scene costs nothing, and is further capped by `LOD_EVAL_INTERVAL_MS` (100 ms) and `MAX_SWAPS_PER_PASS` (2). Distance is `Box3.distanceToPoint` against the world AABB — the **surface**, never the centre. A landed swap calls `onSwapApplied(node)`, or the on-demand loop would never paint it.
  - ⚠️ **A landed tier is a BARE subtree and must be re-integrated (fixed 2026-08-17)**: `setLodLevel` attaches geometry the loader built *long after* `renderComponents` decorated the wrapper, so it carries none of the per-mesh conventions the rest of the object got — no `userData.objectId` / `componentId`, and its authored solid material rather than the current display mode's. Symptoms: **the object silently stops being clickable** once it switches tier (`pickObject` reads `objectId` off the hit mesh itself), and **it renders solid among wireframes** in wireframe mode (reported as "MECHANICAL0 turns solid after I move it" — moving an object changes its screen-space error, which is exactly what triggers a swap) or un-ghosted in optical-link mode. That is why `onSwapApplied` is passed the **node**: `DigitalTwinViewer.integrateLodTier` stamps the ids down the new subtree and re-runs `applyViewerDisplayMode` + `applyOpticalLinkGhost` on it. Any future per-mesh convention has to be re-applied there too.
  - ⚠️ **The selection outline is one of those conventions (fixed 2026-08-19)**: `addWireframeOutline` hangs its amber edge lines off the individual meshes, i.e. INSIDE the tier subtree, and selecting an object **pins it to LOD0** — so a selection change swaps the tier the outline lives on, every time, without the camera moving at all. Both halves break: the tier that lands is bare, so the object the user just clicked shows **no** outline; and the tier that leaves carries its outline into `state.cache`, where `stripDynamicDecorations` can never reach it (it only walks **attached** children), so the amber lines **come back on an object that is no longer selected** the next time that tier is re-attached. Reported as "the outline is on the one I clicked BEFORE" (2026-08-19; the user's first guess was undo, which is uninvolved). `integrateLodTier` therefore strips every `userData.isOutline` child off the landed tier and re-adds the outline from the **live** `selectedObjectIds` — the same `kindId !== "optical_table"` exclusion `decorate()` applies. Note this is invisible in a hidden/background tab: no `requestAnimationFrame` → no `animate()` → no LOD pass → no swap, so the outline looks perfectly correct there.

Objects start at the **coarsest** tier (`loadAssetObject` builds it that way) and are promoted from there: the cheap tier paints immediately, which also serves R-7.

**Authoring surfaces are excluded, by opt-in rather than opt-out.** `loadAssetObject` only builds an LOD node when `renderHints.enableLod` is true, and the only caller that passes it is `DigitalTwinViewer` via `buildSceneObjectFromBindings(..., { enableLod: true })`. So the PHY Editor previews, BUILD, `proceduralAssetGeometry` and any future caller get full detail by default — face-picking authors anchors off mesh triangles and is already at the ~5 mrad triangulation limit ([../float64-audit.md](../float64-audit.md) §2.2). The **selected** object is likewise pinned to LOD0 (`pinnedObjectIds`), because quadric error under-reports the loss of thin features. Physics is unaffected either way — the tracer reads anchors only ([anchors.md](anchors.md)).

Only the generic GLB path participates. The STL builders (PBS252, BB1E03, AD9959, isolator) post-process geometry in ways a decimated tier would not survive, and procedural / `primitive://` assets are cheap already.

### P2 — the catalog backfill

`frontend/scripts/backfill-lods.ts` (`npm run backfill:lods`, backend must be up; `-- --dry-run` to survey, `--force` to regenerate, `--only <slug>` to narrow). It decimates through the **same** `buildLodTiers` BUILD uses, so a tier cannot depend on which route produced it, and POSTs to the tier route — writing only `asset_lods` and new files, which is why it works on locked assets. Node needs no DOM library: the one browser API involved is `FileReader`, which `GLTFExporter.writeAsync` uses to finish a binary GLB, and a four-line shim over the native `Blob.arrayBuffer()` covers it (installing happy-dom's instead pairs *its* FileReader with Node's Blob and throws).

A GLB is many meshes under a transform hierarchy but the simplifier wants one geometry, so `scripts/lodMergeGeometry.ts` bakes world transforms and merges first, folding per-mesh material colour into vertex colours. That merge is also where the draw-call win lives — the thing R-6's ≤ 2000 budget actually responds to on a multi-part board.

**The script refuses to store a tier that has not earned its place**, and says so rather than skipping silently. Three ways a tier fails to earn it, all seen in the first real run:
- the asset is already under the coarsest budget, so the simplifier returns it untouched (18 of 24 GLB assets — the shipped catalog is mostly small parts);
- a tier cuts less than 25 % of the triangles of the finest tier kept;
- the mesh **resists** simplification: `ad9959` stops at 89 % of LOD0 for both tiers, because `LockBorder` plus a forest of thin open-bordered plates leaves nothing safe to collapse. Two 14 MB near-copies of LOD0 are worse than no tiers at all.

**First run result (2026-08-17): 4 assets carry a real LOD2** — `bnc_male`, `ppg` (64.7k → 20k, ±0.017 mm), `ks1t_step` (92.5k → 20k, ±0.129 mm), `toptica_boosta_pro` (29.8k → 20k, ±0.025 mm). Everything else is legitimately un-tiered. Re-running is a no-op for anything already tiered.
