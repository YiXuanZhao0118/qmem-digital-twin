# The render pipeline (frontend)

> Related: [asset.md](asset.md) (viewerHints), [component.md](component.md) (the binding tree), [optics.md](optics.md) (where the beam rendering comes from).

- `components/DigitalTwinViewer.tsx` is the main scene builder. For each SceneObject it resolves Component + Asset and then takes the **binding-tree render path** uniformly (the most complete and only canonical path): `buildSceneObjectFromBindings()` → `resolveBindingTree()` → `buildBindingTreeObject()` walks the whole ComponentBinding tree and assembles the (possibly composite) component. Leaf-node assets still have their geometry actually loaded by `loadAssetObject()`, and per-instance binding overrides (e.g. the rotation of an isolator's front/back Glan) are applied inside `resolveBindingTree`.
  - `shouldRenderViaBindings()` (`bindingRendererGate.ts`) is **now permanently `true` (unified 2026-06-10)** — every component goes through the binding tree. The old direct-to-`loadAssetObject()` branch for single assets is dead code, to be removed later along with `Component.asset_3d_id`.
  - ⚠️ **Not finished yet**: the per-instance state of fiber / rf_cable / isolator (`fiberNodes` / `rfCableNodes` / `radiusMm` / ferrule pose / `translucentHousing`) is **not yet forwarded through the binding tree**, so those three may currently render with the catalog's default spline/pose (state forwarding still to be written; see [fiber.md](fiber.md), [cable.md](cable.md)).
- `three/loadAsset/index.ts` (the leaf loader) dispatches on asset type (STL/GLB/OBJ/`procedural://`) and has special-case builders (PBS252, BB1E03, AD9959, isolator).
  - ⚠️ **Procedural components with no real file still need an Asset3D row plus a root binding**: the binding tree is the only render entry point, so **zero bindings = an empty Group = nothing drawn**. Procedural geometry therefore still needs one asset row with `file_path = primitive://<key>` as the binding leaf, and the loader's `primitive://` branch then looks up the plugin renderer by the **Component's `kindId`** (not the asset key) (`createPrimitive` → `_renderer_bindings.ts`). The same shape is already used for the connectors (0115) and the pre-built cable Components.
  - **No more kind short-circuit: always go through the asset's `file_path` (2026-08-14)** — `loadAssetObject` used to begin with `if (component.kindId === "optical_table") return createNewportOpticalTable()`, **ignoring the asset entirely**, so after baking the optical_table asset into a GLB it still drew the old procedural geometry. That is now removed: an asset with `primitive://table` still goes through the `primitive://` branch → the plugin renderer (`optical_table` in `_renderer_bindings.ts`), and anything with a real file loads that file like any other asset. Invariant: **what gets rendered is decided only by the asset's `file_path`; the kind only selects the renderer for `primitive://`**. The same day, the two same-shaped special cases in the PHY Editor previews (`Asset3DEditor.tsx:~1973`, `ComponentsEditor.tsx:~2647`) were changed to key on `filePath === "primitive://table"` only, and the procedural builder's missing `rotation.x = +π/2` (Y-up→Z-up; detail in [asset.md](asset.md)) was added.
  - **Text annotations (text_annotation)**: `sceneStore.addTextAnnotation` (`sceneStore.ts:2035`) creates a Component (with styling in `properties.text/textColor/bgColor/accentColor/fontSizePx/scaleMm`) → binds the `primitive://text_annotation` asset seeded by alembic **0119** (`TEXT_ANNOTATION_ASSET_FILEPATH`, the constant living beside the renderer) → creates a SceneObject at the transform cursor. Rendering is a canvas-textured billboard sprite (`three/loadAsset/passive/text_annotation.ts`, width = `scaleMm`, `renderOrder=100`). **Fixed 2026-08-14**: there was previously no binding, so once everything unified onto the binding tree on 2026-06-10 annotations became "creatable, editable, invisible". If that asset is missing, the store now throws before creating any row (so no orphan Component is left behind), with a message pointing at `alembic upgrade head`. The editing UI is `TextAnnotationEditor` at `ComponentPanel.tsx:637` (which writes Component.properties).
- Materials: `materialFor()` → `colorForComponent()` (a kindId colour table + `colorHex` override + device-state colouring).
- **viewerHints** drives geometry filtering: `includeOnlyCentroids`, `deletedCentroids`, `recenterOrigin`.
- Beam rendering: `three/rayTrace.ts` → `v3TraceAdapter.ts` consumes the backend's `/api/v3/solver` output and publishes it to `window.__rayTraceDebug` (read by OpticalLinkViewer, BeamScope and snap-to-beam).
  - **Astigmatism (per-axis qx/qy)**: the adapter's `beamMode.x/.y` plus `waistAtStart/EndUm` (X, qx) and `waistAtStart/EndUmY` (Y, qy) are **independent per axis** (fixed 2026-06-11; the y axis used to copy qx by mistake, so beams were always round). `OpticalLinkViewerPanel` therefore draws the 3D beam as an **elliptical cone tube** (a hand-built BufferGeometry with X half-width ← qx and Y half-width ← qy, each axis clamped by its own `VISUAL_FLOOR_UM`), oriented with `makeBasis` onto the beam-local **s/p** (local X→s, Z→p; the convention is `spatialModeX∥s` — if the major axis comes out wrong, swap s/p). A round beam degenerates back to the old circular cone. **Sampling along the axis (2026-06-11)**: the tube no longer **linearly interpolates** the endpoint `waistAtStart/EndUm` (which would stretch a waist inside a segment into a straight cone and miss the pinch at a lens focus); it now takes **24 slices** along `seg.beamMode` via `BeamScopePanel.beamWidthsUmAtPathMm(beamMode, pathLengthFromSourceMmAtStart + t·lengthMm)` — **the same analytic Gaussian** as the 2D scope plot's `waistAtZUmAxis`, so the 3D tube and the scope plot **pinch at exactly the same focus** inside a segment (the two being out of sync came from precisely this; only an old payload without `beamMode` falls back to endpoint interpolation). BeamScope's 2D profile heatmap also reads `beamMode.x/.y`, so astigmatism shows up as an elliptical spot. **Near the waist** both axes are flattened by `VISUAL_FLOOR_UM` (30 µm) and so still look round; the ellipse only becomes obvious downstream.
  - **Per-source beam colour override (2026-06-12)**: each segment's colour is resolved by `opticalBeams.beamColorForSource(emitterObject, wavelengthNm)` — it reads the `colorHex` override in the emitter's `SceneObject.properties.emissionVisuals` (a laser stores `"main"`, a TA stores `"forward"`; see `utils/emissionVisuals.ts`), and only falls back to `wavelengthToColor(wavelength)` when there is none. **It keys on the emitter, not the per-segment source**: `seg.emitterSceneObjectId` (the adapter's `seg.emitterObjectId`) is **constant along the whole chain** (anchor_tracer.py:577 passes `emitter_id` straight down, whereas `source_id` becomes whichever optical component was just hit), so one source's override paints its **entire beam**; using `sourceSceneObjectId` by mistake would only paint the laser→first-component segment. **Both live 3D renderers take this path**: the main scene's `DigitalTwinViewer` (thin lines) and `OpticalLinkViewerPanel` (elliptical tubes). **OpticalLinkViewerPanel's rebuild short-circuit key must include a colour digest** (`colDigest`, scanning every object's `emissionVisuals.colorHex`) — otherwise a colour change that doesn't change segment geometry leaves the key unchanged → the `prevContentKey` short-circuit fires → the tube is never redrawn. **For the same reason the key also contains `rv:${RENDER_LOGIC_VERSION}` (2026-06-12)**: when what changed is the **drawing logic** (e.g. fixing the polarization s/p basis) rather than the segment data, the data digest is unchanged → no redraw → the hot-fixed code still draws the old markers. Bump that constant when you change the drawing math to force a rebuild (this exact symptom once left the polarization arrows stuck on the old horizontal `up×d`).  UI: Optical setting → the laser's **Visualization** card (`_shared.tsx`, key `"main"`) and the TA's **Visualization** card (`TaperedAmplifierAdjustControls`, forward/backward). Note that the old `rayTrace.ts` also reads `emissionVisuals` but is dead code — live rendering does not go through it.
  - **Profile world coordinates + rotation (2026-06-11)**: the beam-scope heatmap is a transverse slice **perpendicular to propagation**, with axes labelled in **world / object-sense axes**. The adapter carries `dirLab` (the lab-unit propagation vector; object-sense X = (1,0,0)); `BeamScopePanel` takes the largest component of `|dirLab|` as the propagation axis, leaving the other two as the transverse pair → labelled as the `Heatmap`'s `axisLabel` (horizontal) / `axisLabelY` (vertical). The contents are additionally **rotated 90°** (`sampleIntensity(y,−x)`). **This applies only to the analytic profile**; **the POP focal-plane diffraction (Airy) view is excluded** — it lives in the lens focal plane's own coordinates and stays unrotated, labelled `x, y (µm) · focal plane` (otherwise the focal-plane figure would be wrongly rotated and mislabelled → reverted 2026-06-11). **The directions and labels are conventions** (qx/qy ↔ world axes, rotation sense, horizontal/vertical) — if the visual doesn't match, either flip the rotation to `sampleIntensity(−y,x)` or swap H/V by exchanging `transverse[0]/[1]`. Example: a laser propagating along X → transverse axes = Y/Z.
- **The PHY Editor COMPONENT preview's probe beam + per-segment polarization (2026-06-12)**: `ComponentPreview3D.rebuildProbeBeam` in `ComponentsEditor.tsx` no longer traces with a frontend face/matrix5x5 approximation; it POSTs to `/api/v3/solver/run-from-component` (component frame; see [optics.md](optics.md)) to get the **backend's ground truth** `labSegments`, and draws a golden beam tube per segment plus **polarization markers** (a double arrow for linear, an ellipse/circle ring for elliptical-circular) — so Faraday rotation, PBS s/p splitting and the rest are real physics. **The polarization markers are shared with the Lab optical link** through `optical/polarizationMarker.ts` (`beamLocalSPThree` + `polEllipseFromJones` + `buildPolarizationMarkers`, extracted from `OpticalLinkViewerPanel` on 2026-06-12 to remove the duplicate) — so the two places can never diverge in how they interpret a Jones vector. **`beamLocalSPThree` must use the same basis as the backend's `jones.beam_local_sp`: `s = normalize(up − (up·d)d)` (up projected into the plane ⊥d), `p = d×s`, with up = Z and X for the degenerate case.** It previously used `s = up×d` (off by 90°), drawing the Jones vector in the wrong basis → 45° linear polarization came out mirrored and appeared to rotate the wrong way (fixed 2026-06-12, affecting both the link and the component preview). The component root is identity, so component-frame mm land directly in `probeBeamGroup` local space. **Nearly dark branches (the polarization a Glan rejected, Jones intensity < 0.01) are skipped** rather than drawn, so they can't mislead. **Automatic probe aiming**: it first tries `computeProbeOpticalAim` (the component's exposedFaces optical_in/out) and, on failure (e.g. the IO-3-850-HP, which has no such exposed faces), falls back to `computeProbeAnchorAim` — which takes the **farthest pair** of world anchor positions among the bound optical assets as the optical axis and pushes the origin back behind the near end, so the probe really does pass through the optical chain.
- **Camera up / axis gizmo (2026-08-14)**: the viewer world is **Z-up**, and `OrbitControls` **fixes its orbit pole (`_quat`) from whatever `camera.up` is at construction time** (`DigitalTwinViewer.tsx:2086`; changing `camera.up` afterwards does not move the pole). So **every** path that sets the camera pose — H (Home, including restoring a custom Home), the six axis buttons (`snapCameraToView`, `DigitalTwinViewer.tsx:1820`), and the restore at startup — **must use `WORLD_UP=(0,0,1)`** (`DigitalTwinViewer.tsx:136`). Invariant: `camera.up ≡ WORLD_UP`; the symptom of breaking it is "after pressing ±Z, dragging rotates about a different axis than after pressing H" (the old `AXIS_VIEW_CONFIG.zPos/zNeg` used to set `up=(0,1,0)`; fixed 2026-08-14 and that field removed entirely). The ±Z views having a line of sight parallel to up is a **deliberately** permitted degeneracy: `Matrix4.lookAt` perturbs the basis and `Spherical.makeSafe()` clamps the polar angle away from the pole, so the pose stays finite and draggable. Saving Home still writes `up` (`HomeViewPose`), but **restore deliberately ignores it**, so old data can't re-separate roll from the pole axis.
- Performance: on-demand rendering (0 renders/sec while idle), incremental scene rebuilds, and `objectWrappersRef` caching wrappers by reference equality of (component, asset, deviceState).
